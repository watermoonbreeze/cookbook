- **营养级别评定** `FoodGroup.nutritionLevel`（`shared/domain/FoodGroup.kt:172`）**只看食物组多样性**（蛋白/主食/蔬果三支柱 + ≥5 大类=优），**与热量/宏量/慢病目标无关**——这是首页色系墙、餐食卡片底色的唯一口径。P3 待办「卡路里达标度纳入评级」尚未落地。

- **今日营养卡** `NutritionTodayCard`（`NutritionWall.kt:58`）：🔥热量/目标/达标 + 三大宏量占比条 + 克数图例。目标来自**主要关注成员** BMR×活动系数（Mifflin-St Jeor），达标±15%。

- **菜品详情营养卡** `DishInsightsSection`（`DishDetailScreen.kt:288`）：库存/忌口(🚫不适合·⚠慎吃·✅有益·💚健康)/记录/营养标签/🔥热量+宏量+覆盖率「(估算，X/Y 料有数据)」+ 一句免责。

- **忌口/推荐** `HealthRuleEngine`（`shared/ai/HealthRuleEngine.kt`）：avoid（红字置底）/limit（⚠注意限量）/recommend（✓利于调养）/cookingCautions（🧂少盐少糖，调料转做法提示）。**家庭病种并集已实现** `FamilyRepository.allEnabledCareIds()`，但**避让文案只写「健康档案建议避免」，不标是对谁**。营养互补 `NutritionBalance` 基于**近7天**餐食宏量偏差评分，**非「今日缺口」**。

# 一、可先落地（安全项，可无人值守直接做）

低风险、不碰健康语义拍板、多为文案/展示层。

### [🔴][低][S] 修正家庭统计「谁没吃」的过时文案（说了不保存其实已持久化）
**现状**：`FamilyStatsScreen.kt:134` 文案「点成员名可标「没吃」…（仅本次查看，不保存）」，但实际已写入 `day_absentee` 表并跨会话持久化（`FamilyRepository.setAbsent`）。
**痛点**：明确的错误陈述——用户被告知"不保存"，实际会保存，反而不敢用或产生不信任。慢病 app 尤其忌讳"说一套做一套"。
**建议**：改文案为「标记后保存到当天，重开仍在；再点一次取消」。顺带确认与首页/卡片份额估算一致（同一 `day_absentee` 源，已一致）。
**落地**：单文件一行文案改；不迁移、不碰免责红线。

### [🔴][低][S] 色系墙加「今日为什么是这个色 + 缺什么」一句解读
**现状**：色系墙/今日卡只给颜色和级别词（较单一/尚可/均衡/营养优），`FoodGroup.nutritionSummary` 已能算出「优质蛋白/主食·碳水/蔬菜·膳食纤维/水果·维生素」已覆盖项，但**首页未用来做「缺口提示」**。
**痛点**：非专业用户看到"较单一"不知道该补什么；健康价值断在"知道不好"却"不知道怎么办"。
**建议**：今日卡（或色系墙标题下）加一行**如实、非推荐性**的缺口文字，基于已覆盖 vs 三支柱：如「今天有主食+蔬菜，还缺优质蛋白」。措辞只陈述"缺哪一类食物组"，不推荐具体菜/不给营养承诺（守 `nutritionSummary` 现有"不含推测性内容"的克制原则）。级别0（无记录）不显示。
**落地**：`HomeViewModel` 用现成 `groupsOf`/`PROTEIN_GROUPS` 派生缺失支柱文案，`NutritionTodayCard` 加一行；纯展示，不迁移。**属如实归纳非医嘱，不越免责红线**。

### [🟡][低][S] 忌口/慎吃标注「对谁」（家庭多成员）
**现状**：`HealthRuleEngine` 已按家庭病种并集算 avoid/limit，但 UI（AI推荐 `avoidText`、详情忌口区）只写「健康档案建议避免」，不标是并集里的哪位成员。方案文档 4.7 明确期望「五花肉·爸爸忌口」。
**痛点**：多成员家庭里，用户不知道这道菜是因为谁被标红——影响决策（"是娃忌口还是我忌口？娃那餐不吃就行"）。
**建议**：avoid/limit 命中项后缀成员名：「⛔忌口：五花肉（爸爸·高血脂）」。数据侧需把「care 分类→成员」映射带出（`family_member`+`member_care` 已有表）。展示层只多一段文字。
**落地**：需 repo 侧补一个「命中 care 分类→哪些启用成员」的查询（纯新 SELECT，**免迁移**）；UI 拼接。**中等改动但语义安全**——只是把已有并集逻辑归因展示。可先做单人/自己场景（无家庭成员时省略后缀），家庭归因作为增量。

### [🟡][低][S] 功能设置「健康膳食」加分组级免责总说明 + 「?」展开详解
**现状**：`FeatureSettingsScreen.kt` 各项只有副标题内联文字，无「?」展开、无分组级免责。方案文档已拟好总说明「这里的评估基于公开营养公式估算，仅供日常参考，非医嘱」但**未落地**。
**痛点**：合规与信任——健康功能集中地却没有一句统一免责；副标题被塞满长文字（如热量数值那条），违背苹果"点到即止"。
**建议**：①分组标题下加一行灰字总免责。②副标题精简到<20字，详细口径移入「?」弹层（复用营养表已有的 AlertDialog+滚动长文模式，`NutritionTableScreen` 的 ⓘ 弹框可直接复刻）。
**落地**：`InsetGroup` 加副标题槽 + 复用 AlertDialog；纯 UI。**正向补强免责红线**。

### [🟡][低][S] 菜品详情/角标的「估算」可信度做成一致的视觉标记
**现状**：可信度分散——营养表用「已核/估算」、详情用括号「(估算，X/Y 料有数据)」、餐食角标**无任何估算标记**（静默估算）。
**痛点**：同一套数据三种呈现，用户对"这个热量准不准"没有稳定预期；角标完全不提示"这是估算"易被当精确值。
**建议**：统一一个轻量标记语言：数字后跟 `≈`（已在角标用🔥+约）、覆盖不全时统一「估算」小灰标（可点开一句"部分食材缺营养数据"）。角标至少补一个「约」字（现已有"约X千卡"，达标行也保持"约"）。
**落地**：文案/小标记层；不迁移。**强化"非精确"表达，守红线**。

### [⚪][低][S] 活动水平/BMR 目标就地给「这数怎么来的」一键说明
**现状**：家庭卡显示「🔥每日目标约X千卡」，`ActivityLevel.desc` 已有久坐/轻度…说明，但目标数字本身无解释入口。
**痛点**：用户不知 2556 千卡是怎么算的、可不可信，容易当成硬指标。
**建议**：目标数字旁小「?」→弹「按 BMR×活动量估算（Mifflin-St Jeor 公开公式），非医嘱」，把方案 4.1–4.3 大白话化。
**落地**：复用弹框；纯展示。

# 二、需确认 / 涉健康语义需拍板 / 建议真机

改评级算法、动推荐口径、或改变健康提示强度，需产品拍板，部分需真机验证。

### [🔴][中][M] 营养级别评级纳入「热量达标 + 关键慢病指标」（P3 核心待办）
**现状**：`FoodGroup.nutritionLevel` 纯多样性；`健康膳食统计维度体系.md` 三节已设计好综合评分 `score = w_div·多样性 + w_cal·热量达标 + w_macro·宏量均衡 + w_chr·慢病指标未超标`，并要求**向后兼容**（无身体数据/无营养数据退回纯多样性）。
**痛点**：色系墙"绿"目前可能名不副实——三支柱齐但热量爆表/钠严重超标（高血压者）仍显"均衡绿"，对慢病家庭是**误导性绿色**，与 app 核心健康价值冲突。
**建议**：按已设计口径分档降级：填了身体数据→热量偏离目标降一档；关键指标超标（高血压钠超标/痛风嘌呤超标/糖尿病高GI）再降档；宏量严重失衡（如碳水>70%）降档。**数据越全越准，缺数据不惩罚**（退回现行为）。措辞上级别词可保留，但需内部准确。
**落地**：改 `nutritionLevel` 签名或新增 `nutritionLevelV2(groups, totals?, target?, careFlags?)`，色系墙/卡片/统计统一改口径。**需拍板**：降档规则的阈值与措辞（避免制造健康焦虑）；**需真机看色系墙整体观感**是否变太"红"。**碰健康语义边界**——评级更严须同步免责"仅供参考、非诊断"。属产品级决策，不宜无人值守直接改。

### [🔴][中][M] 推荐从「近7天均衡」升级到「补齐今日缺口」
**现状**：`NutritionBalance.score` 基于**近7天**宏量偏差；今日已吃缺口（如今天只吃了主食）不驱动推荐。方案维度体系里"补齐今日缺口"是明确目标但未落地。
**痛点**：慢病家庭最需要的是"今天晚饭该补什么"——中午吃了两碗面，晚上推荐应偏蛋白+蔬菜；现在只按一周趋势推，当日针对性弱。
**建议**：在 `RecommendationDataSource` 增「今日已吃 totals」输入，`NutritionBalance` 或新因子按**今日**缺口给候选加分；逐菜理由从"🥗补营养搭配"升级为"🥗今天缺蛋白，这道补"。保留7天作为长期偏好，今日缺口作为即时因子（可加权组合）。
**落地**：取数层加"今日 totals"，打分因子扩展（`RecommendationWeights` 已因子化，加因子成本低）。**需拍板**权重与是否覆盖现有风格；**涉健康语义**（"缺什么"表述须如实、非医嘱）。建议真机验证推荐结果是否更贴合。

### [🟡][中][M] 忌口提示"保留+告知"策略在**记菜/选菜**入口的一致性与克制度
**现状**：忌口菜现为"保留+置底+标红"（AI推荐已做）。但**记菜/选菜（DishPicker）流程**里是否同等显性标红、会不会打扰，未在推荐外统一。详情页 `DishInsightsSection` 有🚫不适合，但那是"主动查看"。
**痛点**：家庭日常快速记菜时，若每道忌口菜都跳醒目红字可能打扰（"我就是想记录爸爸偶尔破戒吃了五花肉"）；但完全不提示又失去健康守护价值。要在"告知 vs 不啰嗦"间取苹果式平衡。
**建议**：记菜选菜列表里忌口菜用**克制标记**（小红点/小标签，非整行红字），点开才展开"对谁忌口"；**记录动作本身不拦截**（撤销优于确认，家庭 app 不替用户做健康决定）。详情/推荐保持现有显性。
**落地**：DishPicker item 加轻量标记；需 care 命中数据透传到 picker。**需拍板**标记强度（用户对"啰嗦"敏感）；建议真机走一遍记菜流看是否顺手。

### [🟡][中][M] 今日营养卡：宏量占比条加"目标参照 + 一句解读"
**现状**：`NutritionTodayCard` 宏量条只画蛋白/脂肪/碳水实际占比 + 克数，`NutritionBalance` 已有目标 20/28/52% 但卡片**没展示目标线、没解读偏离**。
**痛点**：用户看到三色条不知道"我碳水是不是太多了"；有目标口径却没用在最该用的地方。
**建议**：宏量条上叠目标刻度（或加一句"碳水偏高、蛋白偏低"的如实解读，参考中国居民膳食指南，标"参考"）。措辞守"参考、非医嘱"。
**落地**：`NutritionTodayCard` 加目标标线/解读文案；纯展示。**碰膳食指南引用**——须标来源"参考中国居民膳食指南整理"，不写成硬性医嘱。

### [🟡][中][L] 「膳食统计」独立页（各维度达标概览 + 慢病专项）
**现状**：家庭统计只有热量+宏量+7天柱状；`健康膳食统计维度体系.md` 二节设计了完整维度（纤维/钠/钾/钙/嘌呤/GI/多样性/慢病适宜），`NutritionRepository.totalOf` 已能加总这些字段但**无消费页**。
**痛点**：慢病家庭真正关心的钠（高血压）、嘌呤（痛风）、GI（糖尿病）**目前无处可看**趋势——核心慢病价值缺一块承载面。
**建议**：`我的·实用工具`加「膳食统计」页：今日/近7天各维度概览（热量/宏量/纤维/钠/嘌呤/GI），按**关注成员病种**高亮相关维度（痛风者突出嘌呤、高血压突出钠），每维度给参考区间（<2000mg 钠等，标来源）+ 达标/超标色。
**落地**：新页 + VM，数据全来自现成 `NutritionRepository` + `CalorieTarget`；查询多为已有加总（**大概率免迁移**）。**需拍板**信息密度（避免变成让人焦虑的体检报告）；**碰健康语义**，参考区间须标来源+免责。体量 L 因是新页。

### [🟡][中][M] 数据可信度：pending/verified 在"消费点"分级表达，而非只在营养表
**现状**：`review` 字段（verified/pending）只在营养表 ⓘ 弹框整体说明"标已核者权威"，菜品详情/角标**不区分**这道菜的营养是权威值还是估算值。
**痛点**：信任分层缺失——一道全是 verified 食材的菜和一道全 pending/兜底估算的菜，给用户的可信度应不同，现在一视同仁。
**建议**：菜品营养卡覆盖率旁按 verified 占比给一句"数据较可靠/含较多估算"（不显具体百分比避免精确假象）；`DishNutrition` 已有 coveredCount/estimated，可扩展带 verified 计数。
**落地**：`dishNutrition` 聚合时统计 verified 占比；详情加一句。**正向强化免责**，但**需拍板**措辞避免让用户觉得数据不可用。

### [⚪][中][M] 家庭档案：焦点成员/多病种"并集来源"透明化
**现状**：忌口按全家并集，但用户在档案页看不到"当前生效的忌口清单来自哪些成员/病种的合并"。
**痛点**：多成员时忌口越来越多，用户困惑"为什么这也不能吃"，无处溯源。
**建议**：家庭页或设置加只读「当前全家忌口一览」：按成员分组列出各自病种→忌口食材，让并集可解释。
**落地**：只读汇总页，数据现成；**需拍板**是否值得单开入口。

# 建议优先落地 Top 5
