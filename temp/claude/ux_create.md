# 四大"创建/记录"流程 · 第二层体验深挖

> 范围：新建食材 / 新建菜品 / 记一餐(加餐) / 新建餐次。基于真实代码，未改任何代码。
> 上一轮已落地项不重复，只在其基础上更深一层。每条含：现状(引文件/行) → 痛点 → 建议 → 落地提示 + 标注【安全项 可无人值守】/【需确认·真机】。

## 一、新建食材（IngredientEditorDialog）

### [P0][低风险][S]【安全项】新建食材"添加食材"入口每味都强制走详情弹层，多味连加很累
- 现状：`IngredientPickerScreen.kt:344-346` 点任一食材 `onClick = { selectedIngredient = ing }`——**先弹全屏详情 sheet**，再由 sheet 顶部按钮决定是否加入。多选虽支持(`selectedIds`+底部栏 364-376)，但每加一味都要"点→详情弹出→点加入→关详情"，连加 5 味 = 15+ 次点击。
- 痛点：录菜时最高频的动作是"快速勾几味食材"，却被详情弹层挡住，违背"少操作"。详情适合"想了解这食材"，不该是加料默认路径。
- 建议：食材卡加**直接勾选热区**（卡片右侧 checkbox / 整卡点击=toggle 选中，名称区/长按=看详情）。选择模式下"点卡=勾选"，详情降为次入口（如卡片右上"ⓘ"或长按）。confirm 一次性批量加入已在底部栏成立，把入口理顺即可。
- 落地：改 `IngredientCard` 的 onClick 语义 + 传 `onToggle`；`selectionMode` 下点击 toggle，非选择(管理页)保持进详情。DishPicker 的 `DishRow` 已是"点=toggle、无强制详情"的正确范式，对齐它即可。

### [P1][低风险][S]【安全项】连续新建多个食材：存完即关，回列表还要再点"+新建"
- 现状：`IngredientPickerScreen.kt:492-495` 保存成功（`lastSavedIngredientId != null`）后 `createDialogOpen=false; editingIngredient=null`——**编辑器直接整个关闭**。备菜/整理食材库时常要一口气录好几样（如"香菜/小葱/姜/蒜"），每样都要重新"+新建→填名→选大类→保存→再+新建"。
- 痛点：批量建材是低频但强场景（新用户初次整理、买了一批新菜），流程每样重来一遍很啰嗦。
- 建议：保存按钮旁加**"保存并继续"**次按钮（`TextButton`）：保存后**不关弹层**，只清空 name/alias/图片/营养，保留上次选的营养大类与单位（同类食材常连着建，默认继承更省），并给 Snackbar "已保存「X」，可继续录入"。主"保存"仍存完即关。
- 落地：`IngredientEditorDialog` actions 加第二按钮；VM `saveIngredientEditor` 加 `keepOpen` 参数或让 Screen 侧监听 `lastSavedIngredientId` 时区分两种意图（继续则重置字段不关 dialog）。注意红线：VM 并发写回用最新 `_state.value.copy`。

### [P2][低风险][S]【安全项】长表单：详情/营养/调养三大低频区默认全展开，压迫感重
- 现状：`IngredientEditorDialogs.kt:295-346` "详情说明"(5 个多行框)、"营养素每100g"(11 个数字框)、"调养建议"三大区**全部默认平铺**在一屏 verticalScroll 里。快速建材只需"名+大类"，却要滚过一长条空输入框。
- 痛点：与菜品页 A7"更多信息可选默认折叠"（`NewDishScreen.kt:323-336`）不一致——菜品已经学会折叠低频区，食材页没跟进。新用户看到十几个营养字段会以为"必填"，产生录入压力。
- 建议：把"详情说明""营养素""调养建议"三区整体收进**"更多信息（可选）"折叠块**（复用菜品页同款交互：有内容自动展开、编辑既有食材自动展开）。基础信息 + 营养大类保持常显。
- 落地：直接照搬 `NewDishScreen.kt:325-368` 的 `hasMore`/`moreExpanded` 折叠模式包住这三个 `EditorSection`。零迁移、纯 UI。

### [P2][低风险][XS]【安全项】"营养大类"与"其它分类"文案层级易混
- 现状：`IngredientEditorDialogs.kt:259/283` 相邻两区："营养大类（必选）"9 个 FilterChip + "其它分类（可选）"按钮进弹层。两者都叫"分类"，用户不易分清"我为什么要选两次分类"。
- 痛点：概念重复，家庭用户认知负担。
- 建议：营养大类区标题弱化"分类"字眼（如直接叫"这是哪类食材"），"其它分类"改叫"打标签/自建归类（可选）"并入上条的折叠块，减少并列两个"分类"块的困惑。
- 落地：纯文案 + 归入折叠。

## 二、新建菜品（NewDishScreen）

### [P0][低风险][S]【安全项】配料录入：加食材同样被详情弹层挡（同食材流程根因）
- 现状：`NewDishScreen.kt:388-398` "添加食材"打开 `IngredientPickerScreen`，其内点食材仍走详情弹层（见 §一 P0）。录一道家常菜常 6-10 味料，每味都经详情，很拖沓。
- 痛点：菜品页是"配料录入"最高频入口，卡在这里放大了 §一P0 的痛。
- 建议：同 §一P0——picker 选择模式下"点=勾选、批量 confirm"。修一处 `IngredientCard` 即同时改善食材页与菜品页两个流程。
- 落地：与 §一P0 是**同一改动**，优先级并列 P0。

### [P1][中风险][M]【需确认·真机】配料"用量+单位"：只能改克数，非克类食材录入不顺
- 现状：`NewDishScreen.kt:286-288` 每味料用 `GramStepper`，写死 `"$grams g"`（`GramStepper` 内 `valueText = "$grams g"`，onDelta ±5）。可点数值直接输整数克。
- 痛点：食材本身有 `defaultUnitId`（蛋/水果→个、奶→ml，`IngredientEditorDialogs.kt:125-134` 建材时已按大类预选好单位），但录菜配料时**一律按克**，"2 个鸡蛋""1 根葱""半碗米"都要用户脑内折算成克。与建材时精心设的默认单位脱节。
- 建议：配料行的量词跟随该食材的 `defaultUnitId`（有则显 "2 个"步进、无则回退 g）；营养折算用已存的 `pieceGram`（单件克重，建材页 `nPiece` 已录）换算成克供统计。至少让计件类食材（个/根/片）能按件录。
- 落地：需读 `DishIngredient` 是否带 unit、`GramStepper` 泛化为按单位步进；涉及营养克数折算，改动面较大且影响统计，**建议先出方案确认 + 真机验证折算正确**。

### [P2][低风险][S]【安全项】"配料组/步骤模板/导入"三个复用入口分散，最短路径不直观
- 现状：配料组入口在"食材清单"标题右（`NewDishScreen.kt:257`）、步骤模板在"操作步骤"标题右（`:586`）、导入整菜在顶栏（`:124`）。三个"一键复用"能力分处三地。
- 痛点：新用户不知道"快记一道菜"可以先"导入相似菜再改"这条最短路径，导入被弱化成顶栏纯文字。
- 建议：食材清单为空且菜名已填时，在空态卡（`:269-274` "还没加食材"）内联一行提示"从相似菜导入配料 →"或"套用配料组 →"，把复用能力在用户正卡住时前置。非空不显。
- 落地：空态卡加一个 `TextButton` 触发 `importPickerOpen`/`ingredientGroupSheetOpen`。纯 UI。

### [P2][低风险][XS]【安全项】"快记一道菜"最短路径已不错，但保存态无"这就够了"引导
- 现状：菜名一填即可保存（`:134` enabled 只看 name），无食材会弹提示（`:133/419`）。折叠"更多信息"也做了。
- 痛点：新用户不确定"只填菜名+食材算不算记好了"，容易过度填写步骤/图片。
- 建议：食材清单下、"更多信息"上，加一行极轻提示"填了菜名和食材就能记了，步骤/图片有空再补"。降低录入焦虑，呼应家庭定位。
- 落地：一行 `Text` bodySmall。可选、极低成本。

## 三、记一餐 / 加餐（AddDayFoodScreen）

### [P0][中风险][M]【需确认·真机】餐次块内联"最近常吃"快捷 chips —— 上一轮 Top 未做，落地细化
- 现状：`AddDayFoodScreen.kt:436-456` 空块只有三个纵向按钮（添加菜品 / AI 推荐 / 从收藏组合选）。"最近常吃"chips 只活在 `DishPickerScreen.kt:143-166`——**要先点"添加菜品"进全屏 picker 才看得到**。家庭每天吃的菜高度重复，却每次都要多进一层弹层再勾。
- 痛点：记一餐从"加号→选块→点添加菜品→(全屏 picker)→找/勾常吃菜→完成"至少 4-5 步，其中最常见的"就吃昨天那几样"没被前置。这是四流程里回报最高的一处。
- 建议：空块内（"添加菜品"按钮上方）内联一排**横滑"最近常吃"chips（取 top 5-6）**，点 chip 直接把该菜加进本块（`vm.addDishes(block.id, listOf(dish))`），免开 picker。已加入的 chip 变选中态或消失。数据源复用 DishPicker 已有的 recent 查询，提到块级即可。想找更多再点"添加菜品"进 picker。
- 落地：AddMealVM 加一个 `recentDishes` 状态（复用 recent 查询）；MealBlockCard 加 `recentChips` slot + `onQuickAdd`。中风险在于 recent 计算要按当前餐次/时段更准（可先不做时段过滤，纯最近去重）。**建议真机确认 chips 与实际常吃吻合**。

### [P1][低风险][S]【安全项】多菜快速勾选：picker 里点菜"点一个→关一个"感知，非累积勾
- 现状：多选模式下 `DishPickerScreen.kt:194-210` `DishRow` 点击 toggle、底部有已选横条（`SelectedDishesBar`），交互本身是累积的——这点没问题。但**确认按钮"完成"要求 `state.selected.isNotEmpty()`**，且加菜后需手动点右上"完成"回块。
- 痛点：相对小。主要是"完成"在右上角、家庭单手操作够不着；且没有"选够了自动带回"的快捷。
- 建议：保持多选累积；把"完成"做成**底部大按钮**（已选横条那一行右侧或底部固定），单手可达。次要项。
- 落地：把 confirm 从 TopAppBar actions 移/复制到底部 `SelectedDishesBar` 区。低风险纯布局。

### [P1][低风险][XS]【安全项】备注框每块常显，低频却占纵向空间
- 现状：`AddDayFoodScreen.kt:494-504` 每个餐次块底部**常显**"备注（可选）"输入框，即使 99% 的餐不写备注。
- 痛点：多块时（早中晚一次记）三四个空备注框拉长页面，与"简洁去噪"相悖。菜品页已把低频项折叠，餐次块没跟进。
- 建议：备注默认收起为一个小"+ 备注"文字按钮，点了才展开输入框；已有备注则直接显示。
- 落地：block 内加 `noteExpanded` 局部态（`block.note.isNotBlank()` 时默认展开）。纯 UI。

### [P2][低风险][XS]【安全项】时间选择：加餐默认当前时间已很好，但"选择时间"按钮文案在有值时仍像未选
- 现状：`AddDayFoodScreen.kt:418-422` 时间按钮 `block.mealTime?.formatForUi() ?: "选择时间"`。加餐默认取 nowTime（`AddMealViewModel.kt:387`），所以恒有值、显 "14:23"。逻辑没问题。
- 痛点：极小。按钮只显时间数字，用户不一定意识到"这是可点改的用餐时间"。
- 建议：按钮加个"用餐 14:23"前缀或时钟图标已有（`Schedule` icon 在），可保持。基本可不动，列此为一致性核对项。
- 落地：可选文案微调。

## 四、新建餐次（自定义餐次类型）

### [P1][中风险][M]【需确认】用户无法新增自定义餐次类型（如"下午茶"），"加餐"是唯一兜底
- 现状：餐次类型全部预设——`PresetDataSeeder.kt:187-206` 固定 6 类（早/上午/中/下午/晚/宵夜，均 `isFixed=1`）+ 1 个 `SNACK "加餐"`（`isFixed=0`，可手选时间）。`MealType` 模型（`MealRecord.kt:11-17`）无 source 可编辑维度暴露给 UI，**全项目无 createMealType/insertMealType 的 UI 入口**（只有 seeder 调）。用户想记"下午茶""夜跑后补给"只能都归到"加餐"。
- 痛点：家庭作息各异（有人固定"下午茶"、有人分"早茶/夜宵"）。当前只能全塞"加餐"，食历里一堆"加餐"无法区分。餐次是记录的基本维度，缺自定义是结构性空缺。
- 建议：分两步。①**轻量先行（安全）**：既然已有 `SNACK "加餐"` 可自由改时间，允许给加餐块填一个**一次性小标签/别名**（存进 meal_record.note 或新增 label，食历显示"加餐·下午茶"），零表结构改动即可区分。②**完整（需确认）**：做"餐次管理"设置页（我的→设置内），支持增/改/删自定义餐次类型（source='user'、可设默认时间/是否固定），下拉里与预设并列。需加 meal_type 的 source 列迁移 + 软删逻辑。
- 落地：①改 note/加轻量 label 字段——低风险可先做；②涉及新表列/迁移/管理页，**必须出方案 + 加迁移单测**（红线：改 `.sq` 加列要同步 CREATE+N.sqm+所有插入点+软删只删 user）。建议先做①验证需求，②排期。

### [P2][低风险][XS]【安全项】默认餐次/时间无处集中查看与管理
- 现状：各餐次默认时间硬编码在 seeder（`:190-195`），用户看不到也改不了"我家早餐其实 8:30"。每次记都要手动改时间。
- 痛点：家庭作息固定，却每次记早餐都显 07:30 要手改，重复劳动。
- 建议：配合上条"餐次管理"页，让用户改各餐次默认时间（存 user 覆盖），一次设好长期省事。或最小做法：记某餐次时间后"记住这个时间为默认"的一次性 chip。
- 落地：依赖 §四P1 的餐次管理页；或偏好 JSON 存"各餐次默认时间覆盖"（红线推荐：单行低频配置存 `user_preferences` JSON 免迁移）。

## 五、跨流程一致性核对

### [P1][低风险][XS]【安全项】保存反馈：三流程用 Toast，餐次移除用 Snackbar，撤销能力不统一
- 现状：食材保存无成功 Toast（靠关弹层）；菜品保存 `Toast "已保存"`（`NewDishScreen.kt:93`）；餐食保存 `Toast "已保存"`（`AddDayFoodScreen.kt:135`）；但**移除菜品用 Snackbar+撤销**（`AddDayFoodScreen.kt:259-262`）。撤销只覆盖了"移除菜品"，删步骤/删食材/删标签均无撤销。
- 痛点：反馈渠道混用（Toast vs Snackbar），撤销覆盖不全。厨房场景误删多，撤销价值高却只在一处有。
- 建议：①保存成功统一走**Snackbar**（可承载"查看/撤销"动作，Toast 不能）；②食材保存也补成功反馈；③删配料/删步骤这类破坏性操作补 Snackbar 撤销（复用移除菜品的 `showSnackbar+ActionPerformed` 范式）。
- 落地：Toast→Snackbar 是纯替换（NewDish/食材页需引 SnackbarHost）；撤销扩展按现有范式逐点加。分批安全做。

### [P2][低风险][XS]【安全项】返回守卫：菜品页有"放弃未保存"守卫，食材/餐食页无
- 现状：`NewDishScreen.kt:81-82` 菜品页 `isDirty()` 时弹"放弃未保存的更改"守卫；食材编辑器（`IngredientEditorDialogs.kt:167` 直接 `onDismiss`）和餐食页（`AddDayFoodScreen.kt:168` 直接 `onBack`）**无守卫**，填一半误触返回即丢。
- 痛点：一致性缺口。食材/餐食页同样是"填了一半"高损失场景。
- 建议：食材编辑器、餐食页比照菜品页加 dirty 守卫（有输入才拦）。
- 落地：各自加 `isDirty` 判断 + 复用菜品页的 AlertDialog 范式。低风险。

### [P2][低风险][XS]【安全项】空态引导：餐次"收藏组合"空态已优化，食材配料组空态偏简
- 现状：餐食收藏组合空态给了操作引导（`AddDayFoodScreen.kt:524-525`）；菜品配料组空态仅"还没有配料组"（`NewDishScreen.kt:688`）、步骤模板"还没有可用模板"（`:766`）——无"怎么建"的引导。
- 建议：配料组/步骤模板空态比照收藏组合，补一句"点右上＋，把常用配料/步骤存成组合，下次一键套用"。
- 落地：纯文案。

## 建议优先落地 Top 6

1. **【P0·安全】食材/菜品 picker 点击=直接勾选，去掉强制详情弹层**（§一P0＝§二P0，一处改动改善两大流程，回报最高）
2. **【P0·需确认真机】餐次块内联"最近常吃"快捷 chips**（§三P0，家庭高频"就吃常吃那几样"，免进 picker，上一轮 Top 未做）
3. **【P1·安全】食材"保存并继续"连续建材**（§一P1，批量整理食材库不再每样重来）
