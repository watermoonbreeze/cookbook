## 核心链路现状速览

- **入口**：底栏正中 `CenterPlusFab`（`MainScaffold.kt:346`）→ `Routes.addMeal()` → `AddDayFoodScreen`，无参数=纯新建。
- **新建默认日期**：`resolveNewMealDate()`（`AddMealViewModel.kt:442`）——有今天/未来餐食则接在"最后餐食+1"，否则上午→今天、下午/晚上→明天。
- **新建默认餐次块**：`loadMealsForDateInternal`（:462）空日期时 `newBlock(firstOrNull{code=="BREAKFAST"})` —— **永远默认早餐**。
- **默认时间**：早餐块默认 07:30（`isFixed` 固定餐次带 `defaultTime`）。
- **选菜**：点"添加菜品"→ `DishPickerScreen` 全屏 Dialog（最近常吃 chips + 喜爱横滑 + 全列表 + 搜索 + 完成）。
- **保存门禁**：`canSave = mealTypeId!=null && mealTime!=null && dishes.isNotEmpty()`（每块）。

## 一、记录一餐（最高频，重点）

### [🔴][风险 低][体量 S] 新建默认餐次应按当前时段智能推断，而非永远早餐
**现状**：`loadMealsForDateInternal`（`AddMealViewModel.kt:461-464`）与 `resolveNewMealDate` 割裂——日期已按"上午/下午"分流，但**餐次块恒为 BREAKFAST**。晚上 19 点点 + 记晚饭，进来却是"早餐 / 07:30"，用户必须手动改餐次+改时间两步。
**痛点**：家庭"刚吃过就记"是绝对高频，最该顺的路径反而每次要纠正 2 个字段；07:30 这种明显错误的默认时间还容易误存脏数据。
**建议**：新建空块时按当前钟点映射默认餐次（如 <10 早餐 / 10–14 中餐 / 14–17 下午餐 / 17–21 晚餐 / else 宵夜或加餐），映射到对应固定餐次的 `defaultTime`；若目标日期是"明天/未来计划"（`resolveNewMealDate` 返回未来），则退回早餐（计划从早排起更自然）。逻辑集中在一个 `defaultMealTypeFor(date, nowHour)` 私有函数，`addMealBlock` 的首块也复用。
**落地提示**：`AddMealViewModel.loadMealsForDateInternal`（:461）+ 新增 `DateTime.currentHour()` 判定（已有该 API，见 :449）。纯 VM 逻辑，单测可覆盖（把 nowHour 提为参数，遵守项目"today/now 提参"红线）。**安全项，可无人值守**。

### [🔴][风险 低][体量 M] "选菜"应能一步完成整餐，减少"进选择器→选→完成→再回填"的往返感
**现状**：空块只有"添加菜品 / AI 推荐 / 从收藏组合选"三个纵向 TextButton（`AddDayFoodScreen.kt:443-463`）。选菜必须先进全屏 `DishPickerScreen`。而 DishPicker 里已经有"最近常吃"chips 和"喜爱"横滑（`DishPickerScreen.kt:143-189`）——这些恰恰是家庭复选率最高的菜。
**痛点**：最高频的"就那几道常吃菜"被藏在弹窗二级；每记一餐至少 4 次点击（添加菜品→选 N 道→完成→[改餐次/时间]）。
**建议**：在餐次块内**内联一行"最近常吃"快捷 chips**（取该餐次或全局最近 6–8 道），点一下直接加入本块、无需进弹窗；"添加菜品"退为"更多/搜索"入口。既贴合苹果"高频前置、低频收纳"，也把典型记一餐压到 1–2 次点击。
**落地提示**：复用 `DishRepository.observeRecentDishes`（HomeViewModel 已用）；块内 `LazyRow(FilterChip)`，onClick→`vm.addDishes(block.id, listOf(dish))`。**需真机验证**（视觉密度/横滑手感），建议先出方案确认。

### [🟡][风险 低][体量 S] 移除强制"选时间"错误红字，与已有"默认当前时间"策略统一
**现状**：`MealBlockCard`（`AddDayFoodScreen.kt:430-437`）当 `mealTime==null` 显红字"请选择用餐时间"。但 A2 改造后固定餐次带 `defaultTime`、加餐带 `nowTime()`，`newBlock`/`setMealType` 都不会产生 null time——该红字实际几乎不触发，属残留。
**痛点**：一处"看起来像错误"的死分支，也和"合理默认、不强制"的设计相悖；万一触发反而阻断保存。
**建议**：确认 `mealTime` 恒有默认后删除该红字分支；时间作为可点按钮展示当前值即可（现已是 `block.mealTime?.formatForUi() ?: "选择时间"`）。
**落地提示**：`AddDayFoodScreen.kt:430-437`。删前 grep 确认无路径把 time 置 null。**安全项**。

### [🟡][风险 低][体量 S] 保存按钮禁用态缺乏"为什么不能存"的引导（空态）
**现状**：顶栏"保存"按 `state.canSave` 置灰（`AddDayFoodScreen.kt:176`），条件是"至少一块有菜"。刚进页面无菜时按钮灰，用户不知道差什么。
**痛点**：苹果式做法是"要么给默认让它可用，要么明确告知缺什么"，纯置灰是最弱反馈。
**建议**：无菜时不必额外文案（选菜引导已在块内），但可在块内"添加菜品"区维持 accent 主色引导视线（现已 primary 色，OK）；**更值得做的是**：若用户点了灰按钮无反应，家庭用户会困惑——可让按钮始终可点，点击时若无有效块弹 Toast"先添加至少一道菜"。低成本提升可发现性。
**落地提示**：`AddDayFoodScreen.kt` CapsuleButton 去 enabled、`vm.save()` 内已有 `drafts.isEmpty() return`，补一个 state 提示。**安全项**。

### [🟡][风险 中][体量 M] 编辑既有某天时日期锁死，改期只能"删了重记"
**现状**：编辑既有餐食 `isEditingExisting=true` → 日期按钮 `enabled=false`，显"编辑中不可改"（`AddDayFoodScreen.kt:208-221`）。而新建/复制场景 `setDate` 已支持"改到空日期=移动、占用则提示"（`AddMealViewModel.kt:146-168`，保存时删旧日期）。
**痛点**：用户记错了日子（把周三的饭记成周四）时，编辑态完全改不了，只能删掉重记一遍，违背"撤销/纠错优于重来"。移动逻辑其实已在 VM 里实现，只是编辑入口被 UI 挡死。
**建议**：编辑态也允许改日期，复用现成的"移动到空日期 / 占用则提示"逻辑（`loadedFromDate` 已支撑保存时删旧）。红线是"防改日期导致数据错乱"，但 VM 的移动+删旧路径正是为此设计，风险可控。若怕误触，可保留一次二次确认。
**落地提示**：放开 `enabled = !state.isEditingExisting` 限制；回归测"编辑→改到空日期→保存"删旧是否正确（有单测基础）。**需确认+真机**（涉及数据移动，谨慎）。

## 二、查看历史（食历）

### [🟡][风险 低][体量 S] 食历卡片"复制/编辑/删除"三图标信息密度偏挤，弱化次要操作
**现状**：`DayMealCardView` 单行头放了 日期+角标+复制+编辑+删除三个 34dp 图标（`DayMealCardView.kt:105-114`）。复制、删除都是低频，编辑是中频。
**痛点**：三个同权重图标并列，视觉噪音；删除（红）与复制同排易误触；不符合苹果"主操作显、破坏性操作收纳"。
**建议**：卡片行内只留最高频的"编辑"（或整卡点击即进编辑）；复制+删除收进**长按 ActionSheet**（项目已有 `ActionSheet`/`SheetAction` 组件，破坏性用 error 红）。既减噪又天然防误删，与已建的苹果组件库一致。
**落地提示**：`DayMealCardView.kt`；`onCopyClick/onDeleteClick` 改由 ActionSheet 触发。经验红线提到"长按 ActionSheet"已是既定模式。**需真机**（长按手感/可发现性），先确认。

### [🟡][风险 低][体量 S] 食历顶部日期范围点击=月历，但"跳到今天"缺一键入口
**现状**：食历顶栏只有一个"日期范围"按钮开月历（`FoodTimelineScreen.kt:130-137`）；滚动加载历史/未来靠上下拉。想快速回到"今天"要么翻月历点，要么手动滚。
**痛点**：家庭最常问"今天/最近吃了啥"，回到今天是高频诉求，却没有直达。
**建议**：顶栏加一个"今天"文字按钮（或范围按钮长按=回今天），调用已有 `vm.jumpToDate(today)`。极低成本。
**落地提示**：`FoodTimelineScreen.kt` actions 区加 TextButton→`vm.jumpToDate(DateTime.today())`。**安全项**。

### [⚪][风险 低][体量 S] 空食历引导文案与实际入口位置对应，但可更"可操作"
**现状**：空态"还没有任何餐食记录\n中间 + 号开始记录"（`FoodTimelineScreen.kt:142`）。文案 OK，但只是文字，用户视线要自己找底栏中间。
**建议**：空态里放一个主行动按钮"记第一餐"（CapsuleButton）直接触发 `onEditMealDate(today)` 或导航 addMeal，比"找 + 号"更少一步。
**落地提示**：`EmptyState` 支持传 action slot 或直接在 timeline 空分支放按钮。**安全项**。

## 三、复制 / 复用菜单

### [🟡][风险 低][体量 S] "复制某天"落地到"最后餐食+1"的目标日期不够显性，易困惑
**现状**：`loadCopyFrom`（`AddMealViewModel.kt:410-433`）复制目标日 = `max(最新餐食+1, today)`，并设 `minSelectableDate` 锁住更早日期。用户从食历某天点"复制"，进来看到的却是一个"未来某天"的草稿，且日期可改但下限被限。
**痛点**：复制的心理预期常是"照这天再吃一次（今天/明天）"，落到"排在整个食历最后"可能反直觉；且"为什么只能选某天之后"没有即时解释（仅改期冲突时才提示）。
**建议**：复制进入后在日期区下方常驻一行浅色说明"已按你的记录顺延到 X 月 X 日，可改（不能早于现有餐食）"；或复制时给"今天/明天/顺延"三个快捷日期 chip 让用户一眼选定，减少开日历。
**落地提示**：`AddDayFoodScreen.kt` 日期区（:206-222）下加说明行，读 `state.minSelectableDate`；chip 方案走 `vm.setDate`。**安全项**（纯提示）/ chip 方案需确认。

### [🟡][风险 中][体量 M] 收藏组合复用入口偏深，"整餐照搬"的高价值能力不够显性
**现状**：收藏组合只在餐次块内（空块 TextButton"从收藏组合选"，有菜时右下"选择组合"）（`AddDayFoodScreen.kt:460, 494`）。首页/食历无"一键复用收藏组合成新的一餐"的直达。
**痛点**：组合是"少操作达成目的"的杀手锏（一键 N 道菜），但埋在记一餐的二级块里，很多用户不会发现/不会用（空态引导已加，但入口仍深）。
**建议**：评估在首页"计划"区或 AI 推荐旁增设"我的常吃组合"轻入口（横滑组合卡→点即新建一餐草稿并预填）。让复用能力前置到首页高频视线内。
**落地提示**：`comboRepo.listCombos()` 已有；首页加一节 `LazyRow` 组合卡→导航 addMeal 预填。**需确认**（信息层级取舍，别把首页塞满）。

## 四、首页信息层级

### [🔴][风险 低][体量 M] 首页看不到"今天吃了什么"——最该一眼可见的信息缺席
**现状**：标题"今天吃什么"，但首页 `LazyColumn` 顺序是：AI 推荐卡 → (营养色系墙) → 🔥热门 → ⏱最近 → 📅计划(今天+未来)（`HomeScreen.kt:111-266`）。计划区 `observeTodayPlusFuture` 含今天，但今天餐食被排在"热门/最近/一周计划入口"之后，且和未来计划混在一节。
**痛点**：家庭最核心的两个问题"今天吃了啥 / 今天该吃啥"，前者被下沉到很靠后、后者靠 AI 卡间接承载。"热门/最近"是发现型内容，占了首屏黄金位，挤走了当天状态。这是首页最大的层级错位。
**建议**：首屏顶部独立一节"今天"——直接展示今天已记的餐（复用 `DayMealCardView`），空则给"今天还没记，记一餐"的主行动卡；把"热门/最近"下移为发现区。让首页第一屏回答标题的承诺。
**落地提示**：`HomeViewModel` 拆一路 `todayCard`（`observeTimelineWindow(today,today)` 已有类似用法）；`HomeScreen` 顶部新增 item。**需确认**（首页结构调整，先定稿再动）。

### [🟡][风险 低][体量 S] AI 推荐卡长期占首屏第一位，权重可能高于其真实使用频率
**现状**：AI 推荐 `Surface` 是 `LazyColumn` 第一个 item（`HomeScreen.kt:111-143`）。
**痛点**：若"今天吃了啥/该吃啥"节前置（上一条），AI 入口与它争首屏。AI 是增值功能非每日必用。
**建议**：随上一条重排，把 AI 推荐放到"今天"节之后（作为"该吃啥"的辅助），而非绝对置顶。保持卡片形态即可。
**落地提示**：调整 `HomeScreen.kt` item 顺序。**安全项**（纯排序，无逻辑）。

### [⚪][风险 低][体量 S] 首页缺"快速补记昨天/前天"入口
**现状**：首页计划区只 today+future；补记过去某天要进食历翻。
**建议**：低优先。若"今天"节做了，可在其旁给"补记其他日期"小链接直接开日历+addMeal。
**落地提示**：可选，随首页重构一起评估。**安全项**。

## 五、一致性 / 审美 / 反馈

### [🟡][风险 低][体量 S] 移除菜品有撤销 Snackbar，但删除整天餐食是"不可撤销硬确认"，两套心智
**现状**：移除单菜=Snackbar 撤销（`AddDayFoodScreen.kt:255-263`，苹果式）；删整天=AlertDialog"此操作不可撤销"硬确认（`HomeScreen.kt:282-295`、`FoodTimelineScreen.kt:179-192`）。
**痛点**：同一 App 内两种删除范式并存；"撤销优于确认"是既定准则，删整天反而退回确认弹窗。
**建议**：删整天也改"先删+Snackbar 撤销"（软删/缓存该天数据，撤销即恢复；超时才真删）。若整天删除实现成本高，至少统一为一致范式或都用 ActionSheet。
**落地提示**：涉及 `deleteDayMeals` 的可恢复性，需 repo 支持"暂存待删"。**需确认**（数据可恢复性设计）。

### [🟡][风险 低][体量 S] 保存反馈用 Toast，与 App 内 Snackbar 体系不统一
**现状**：保存成功用 `Toast.makeText`（`AddDayFoodScreen.kt:135`），食历复制也用 Toast（`FoodTimelineScreen.kt:109`）；而移除撤销用 Material Snackbar。
**痛点**：Toast 是系统级、样式不受控、不跟随苹果化主题；两套反馈不一致。
**建议**：统一收敛到 Snackbar（页面已有 `SnackbarHostState`）。保存成功可 Snackbar"已保存"，甚至带"查看"跳食历。
**落地提示**：`AddDayFoodScreen.kt` 用现成 `snackbar` 替 Toast。**安全项**。

### [⚪][风险 低][体量 S] 餐次下拉用 OutlinedButton+DropdownMenu，可评估换分段/ActionSheet 更苹果
**现状**：餐次选择是 `MealTypeDropdown`（OutlinedButton 展开 DropdownMenu，`AddDayFoodScreen.kt:589-628`）。
**痛点**：下拉菜单偏 Android 传统；餐次是低基数固定项（6–7 个），更适合 ActionSheet 或胶囊选择。
**建议**：低优先，视觉打磨项。可换 `ActionSheet`（已有组件）承载餐次选择，或高频餐次直接分段。
**落地提示**：复用 `ActionSheet`/`SegmentedControl`。**安全项**（视觉），但非痛点，排后。

## 建议优先落地 Top 5

1. **[🔴S 安全] 新建默认餐次按当前时段智能推断**（改早餐恒定→按钟点映射餐次+时间）——最高频路径省 2 步纠正，纯 VM 逻辑可单测，零风险。
2. **[🔴M 需确认] 首页"今天"节前置**——让首页第一屏真正回答"今天吃了啥/该吃啥"，修复最大的信息层级错位。
3. **[🔴M 需真机] 餐次块内联"最近常吃"快捷 chips**——把最高频复选菜前置到块内，记一餐压到 1–2 次点击。
4. **[🟡S 安全] 保存反馈 Toast→Snackbar 统一 + 删除范式统一**——收敛反馈体系，撤销优于确认贯彻到底。
5. **[🟡S 安全] 食历"回今天"一键入口 + 移除残留"请选时间"红字**——两处低成本顺手度修复。
