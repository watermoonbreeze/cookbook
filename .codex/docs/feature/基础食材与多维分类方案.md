## 数据库落地

- `ingredient`：基础食材主表。[AI生成]
- `food_category`：多维分类树，`dimension` 区分 general/nutrition/gi/purine/sodium/fat/crowd 等。[AI生成]

## JSON 维护方式

- 分类数据维护在 `shared/src/commonMain/resources/seed/food_categories.json`。[AI生成]
- 食材数据维护在 `shared/src/commonMain/resources/seed/ingredients.json`。[AI生成]
- 分类 JSON 使用稳定 `code` 维护父子关系，食材 JSON 使用分类 `code` 维护多分类绑定，避免中文名称调整后关系失效。[AI生成]
- 每个食材必须维护 `code/name/emoji/categories`；`emoji` 是没有拍照时的默认展示图标。[AI生成]
- `ingredient.emoji` 已落入数据库字段，UI 展示优先级为：缩略图/照片 > 数据库 `emoji` > `FoodEmoji.kt` 名称兜底 > 通用 `🥗`。[AI生成]
- `PresetDataSeeder` 可重复执行：已有食材不会重复插入，但会补齐 JSON 中新增的 emoji 和分类关系；软删除的同名预设食材会恢复为有效。[AI生成]
- Android 运行时和 JVM 单元测试均通过 `SeedResourceLoader` 读取同一份 JSON；测试侧有文件路径兜底，避免资源打包差异影响回归测试。[AI生成]

## 食材分类编辑规则

- 采用方案 A：只开放用户自建的普通分类编辑，判断条件为 `source=user`、`dimension=general`、`crowd_type_id IS NULL`。[AI生成]
- 预设分类、营养维度分类、慢病人群分类保持只读，避免用户误改基础数据后影响慢病筛选和 JSON seed 兼容性。[AI生成]
- 用户分类删除使用软删除：`food_category.status=0`，并将 `ingredient_category` 中对应关系置为 `status=0`；不删除食材本体。[AI生成]
- 如果用户分类下仍有子分类，先阻止删除，提示用户先处理子分类，避免产生不可见层级。[AI生成]
- 食材选择页左侧固定虚拟分类顺序：`全部`、`最近使用`、`管理分类`、真实分类树。[AI生成]
- `最近使用` 是虚拟分类，不写入 `food_category`，不可添加子类、不可编辑、不可删除；数据来自 `ingredient.last_referenced_at`，只要食材被保存进菜品就会更新最后引用时间，按该时间倒序展示。[AI修改]
