## 一、重构目标

本轮食材模块不再基于当前粗粒度分类继续小修，而是按 `日常食材维度.md` 重新建立“食材知识库 + 统一食材选择器”。

核心目标：

1. 尽可能利用 `日常食材维度.md` 中的食材、分类、营养维度、调养维度。
2. 食材页和菜品中新建/编辑菜品时选择食材，必须使用同一套食材浏览、筛选、详情和选择逻辑。
3. 食材支持多分类归属：一个食材可同时归属常规、营养、调养、自定义分类。
4. 自定义不是隔离体系，而是用户创建内容的聚合视图。
5. 新增/编辑食材表单按新维度重新设计，不沿用旧的简单弹框。
6. 食材展示名称统一为 `名称(别名)`，别名为空时只显示名称。

## 二、顶部主分类

顶部主分类固定为以下顺序：

```text
最近 / 常规 / 营养 / 调养 / 自定义
```

### 2.1 最近

- 只展示最近使用食材。
- 最近使用不再出现在其他主分类下面。
- 数据来源：食材被菜品引用、被加入餐食、被用户选择等行为产生的最近引用时间。

### 2.2 常规

按 `日常食材维度.md` 的“维度一：常规食材分类”建立多级分类树。

用于回答：这个食材在日常饮食里属于哪一类。

### 2.3 营养

按 `日常食材维度.md` 的“维度二：按营养素功能分类”和部分营养分级建立分类树。

用于回答：这个食材有什么营养特点。

### 2.4 调养

按 `日常食材维度.md` 的“维度三：慢病管理分类”和后续 13 类疾病/人群食物清单建立分类树。

调养不只包含慢病，也承接后续所有按病种、人群、身体状态、饮食目标区分的食材选择。

### 2.5 自定义

自定义是用户创建内容的聚合入口：

- 展示所有用户创建的分类。
- 展示所有用户创建的食材。
- 只有自定义 Tab 下展示 `+ 管理分类`。
- 后续用户新增分类统一可在自定义中管理。

注意：自定义不是独立封闭分类体系。用户创建的分类/食材如果挂载到常规、营养、调养中的某个节点，也必须同步出现在对应正式分类下。

调养建议等级统一为：

| 等级 | 展示 | 含义 |

| `limit` | 黄灯限量 | 需要控制量、频次或特定场景 |

## 六、自定义规则

### 6.1 自定义 Tab 的定义

自定义 Tab 查询：

- `source=user` 的分类。
- `source=user` 的食材。

它是聚合视图，不是唯一归属。

### 6.2 用户新增分类

新增分类时需要选择挂载位置：

- 可挂到常规、营养、调养中的任意节点下。
- 也可仅作为自定义根分类存在。
- 无论挂到哪里，都会在自定义 Tab 中显示。
- 如果挂到正式分类树中，也必须在正式分类树对应位置显示。

示例：

```text
用户新增分类：香草类
挂载位置：常规 > 蔬菜类 > 叶菜类

展示位置：
- 自定义 > 香草类
- 常规 > 蔬菜类 > 叶菜类 > 香草类
```

### 6.3 用户新增食材

新增食材时可以选择多个分类归属。

示例：

```text
用户新增食材：紫苏叶
别名：苏叶
分类：
- 常规 > 蔬菜类 > 叶菜类 > 香草类
- 营养 > 膳食纤维丰富食物
- 调养 > 慢性胃炎与消化性溃疡 > 黄灯限量

展示位置：
- 自定义 > 用户食材
- 常规对应分类
- 营养对应分类
- 调养对应分类
```

## 七、食材展示名称规则

所有食材展示统一使用：

```text
名称(别名)
```

规则：

- 别名为空：只显示名称。
- 别名不为空：显示 `名称(别名)`。

示例：

```text
西红柿(番茄)
红薯(甘薯、番薯)
土豆(马铃薯)
青椒(柿子椒)
鸡胸肉
```

建议在领域模型中提供统一方法：

```kotlin
Ingredient.displayName
```

所有列表、卡片、详情、菜品食材清单、选择结果、搜索结果都使用该展示名。

## 八、新增/编辑食材表单

新增/编辑食材不能沿用旧的简单弹框，应改为完整页面或全屏 Sheet。

### 8.1 基础信息

- 食材名称
- 别名
- 图片
- 默认单位
- 来源：预设/用户

### 8.2 常规分类

- 多选。
- 从常规分类树中选择。
- 支持用户自定义分类挂载后的节点。

### 8.3 营养分类

- 多选。
- 从营养分类树中选择。
- 初期只选择标签，不录入精确营养数值。

### 8.4 调养分类

- 多选。
- 每条调养归属需要包含：
  - 调养分类节点
  - 建议等级：推荐/限量/避免
  - 原因说明

### 8.5 做法与处理信息

- 常见做法
- 处理建议
- 食用注意
- 保存建议
- 通用健康说明

这些字段进入食材详情页展示。

## 九、统一食材浏览器

食材页和菜品选择食材必须统一，不再保留旧选择逻辑。

建议抽象为：

```text
IngredientBrowser
├── mode = manage       食材页
├── mode = select       菜品中新建/编辑菜品选择食材
└── mode = multiSelect  后续“用这些食材找菜”
```

三种模式共用：

- 顶部主分类：最近 / 常规 / 营养 / 调养 / 自定义
- 左侧多级分类树
- 食材列表
- 食材详情
- 搜索
- 筛选
- 展示名规则

差异只在底部操作：

| 模式 | 操作 |
---|---|
| `manage` | 新增食材、编辑食材、管理自定义分类 |
| `select` | 选择食材、完成、返回菜品编辑 |
| `multiSelect` | 选择多个已有食材，找能做的菜 |

## 十一、seed 数据策略

不建议在 Kotlin 代码里硬写大量食材。

建议拆为：

```text
seed/ingredient_categories.json
seed/ingredients.json
seed/ingredient_category_rel.json
seed/ingredient_care_rules.json
seed/ingredient_details.json
```

### 11.1 分类 seed

从 `日常食材维度.md` 结构化生成。

每个分类必须有稳定 code，例如：

```text
regular_vegetable_leaf_cruciferous
regular_aquatic_fish_freshwater
nutrition_iron_heme
care_gout_recommend
```

### 11.2 食材 seed

每个食材必须有：

- code
- name
- alias
- default_unit
- emoji 或图片占位
- source=preset

### 11.3 分类关系 seed

食材和分类关系单独维护，避免一个食材 JSON 过长。

### 11.4 调养规则 seed

调养规则独立维护：

- 食材 code
- 调养分类 code
- 建议等级
- 原因
