## 1. 总原则与状态口径

| 口径 | 含义 | 编码动作 |
|---|---|---|
| `READY` | 已有决策和方案，可进入 Reality Verification 后冻结 L7 蓝图 | 可以由 luna 执行冻结后的蓝图 |
| `RESEARCH` | 需查代码、权威资料、性能/兼容性或 UX 证据 | 只研究；产出 ADR/方案，不能编码 |
| `DECIDE` | 仍有产品、健康、隐私或战略选择 | 只提供选项与推荐；等待用户决策 |
| `PARKED` | 已明确延后、二期或外部条件未具备 | 不排期，不生成实施蓝图 |
| `CLOSED-PENDING-DEVICE` | 自动化和 ARCH 已收口，只有统一真机清单待验 | 不重复修代码；末期统一真机验收 |

已完成项（L2、Bug-5305、Bug-2119、Bug-3393、OBS-NEXT、P5-A）不再排入代码队列；它们仅随末期真机清单验证。`Phase 6`、iOS 编译、二期账号/订阅明确为 `PARKED`。

## 2. 依赖顺序（唯一执行顺序）

`R0 治理回写` → `R1 已冻结餐食体验` → `R2 AI 可靠性缺陷` → `R3 数据规模基础` → `R4 健康/营养口径` → `R5 推荐与周计划` → `R6 记录/库存语义` → `R7 交互一致性` → `R8 AI 能力扩展` → `R9 战略/二期` → `R10 统一真机验收`。

同一箭头左侧未达到“ARCH_ACCEPTED / AUTOMATED_GATES_PASS”前，右侧不得开始编码。各批可做研究，但不得提前实施。所有批次均遵守：代码、自动化证据、功能档案回写、`feature_sync_check --range`、独立旗舰复核、真机项登记缺一不可。

## 5. 各批次蓝图的机械模板（luna 可执行门槛）

任一 `READY` 批次由 sol 重新核实现状后，必须新建 `docs/feature/<批次>_实施蓝图.md`，达到项目 L7 而非只引用本册。首屏必须写 `ROLE_CONTRACT`：ARCH=sol 冻结/复核，CODE=luna 仅按 allowlist 实施，旗舰 REVIEW 独立审查。最低内容：

1. 任务卡：目标、非范围、基线 SHA、前置批状态、上一批延后项归宿。
2. `§0.1` L7 颗粒度勾销表、独立挑战台账及裁决。
3. 机器可解析 `allowlist` 固定块；逐文件“新增/修改/禁止改”的唯一操作。
4. `INV-<批次>-NN`：状态、数据真相源、并发/取消、用户可见副作用、兼容和隐私不变量。
5. `STEP-<批次>-NN`：每步精确输入、改动点、禁止动作、产出；不得留“视情况”。
6. `T-<批次>-NN`：测试夹具、动作、精确断言和命令；真机 `DEV-<批次>-NN` 按前置/步骤/预期/失败日志模板追加到唯一清单。
7. CODE 交付映射：蓝图 ID → 文件:符号 → 测试 ID → commit；REVIEW 只能写通过/阻断/缺证据，并以 AF 回填同一蓝图。

## 6. 方案讨论结论与细化次序

本节给出 sol 后续逐批产出 L7 文件时应采用的**唯一推荐方向**。若新 Reality 事实推翻其中任一条，必须先登记 Q 并修订本册/ADR，不能由 luna 自行换方案。

| 批次 | 子批次顺序 | 推荐方案（已讨论结论） | 冻结时必须补齐的研究证据 |
|---|---|---|---|
| R1 | UEN 修复 → 日期月历复用 → 首页合并 → 联调 | 复用既有路由、`MealRecordRepository` 与 Calendar；今天固定占位、未来最多两天；AI selector 普通切换不取消生成 | 现有三份 canonical 蓝图、当前 call-site、日期占用规则和 UI 截图 |
| R2 | 总超时/取消 → 健康建议失效 → 规则解析回归 → 语音生命周期 → 文案与模板 | 每次请求有“总超时 + 单次 read 超时”；generationId 是所有异步回写唯一护栏；失败保留原文、由用户确认规则回退；语音入口只在权限/实例/释放三态可证明后恢复 | `VoiceRecognizer` 生命周期、真实失败日志、NDJSON 状态图、规则样例语料及 token 限制 |
| R3 | seed round-trip → 数据分页 → 来源/交叉核对 → 小批扩量 → 大批扩量 | 把 staging/校验/发布脚本作为数据唯一入口；先 DB LIMIT/OFFSET 与搜索下推，再允许 5000+；原始值、标准化值、来源、置信度分离 | 生产线 schema、性能基线、每来源许可/可用性、全量 diff 报告 |
| R4 | 历史口径 ADR → 数据缺口审校 → 评估器 → 展示/透明 → 扩病种 | 默认推荐“记录时快照 + 显式重算入口”，不静默改历史；先高血压已有闭环，再糖尿病/痛风，最后高血脂 schema；调味料只在有来源时展示“限量” | 权威指南原文、阈值适用人群、每食材来源、迁移与旧记录兼容策略 |
| R5 | R6 缓存 → R2 口味 prompt → 规则降级提示 → 推荐解释 → 周计划营养线 | 先做用户已拍板、零 schema 的 R6/R2；排序只能消费同一健康/营养真相源；偏好仅显式反馈、可查看/关闭；不自动补改模型菜品 | 可复现候选集与固定随机种子、权重表、性能数据、健康回归矩阵 |
| R6 | 餐状态机 ADR → 吃完度数据模型 → 外食/库存 → 迁移 → P5-B Reality | 将计划、实际、取消、外食、未吃建成显式状态和事件；库存只在用户确认实际摄入时结算，并要求幂等撤销 | 状态转换表、SQL 迁移演练、多人分摊和库存一致性测试 |
| R7 | 小型 affordance/文案 → 共享 Form → 家庭切换 → 时间线/趋势 → Mine/适老整体审计 | 先低风险且可回归的小项，后抽共享 UI；不把 Material3 升级混进业务 UI 批 | Apple-UX 规格、无障碍/字体缩放矩阵、所有受影响路由与截图基线 |
| R8 | 别名归一 → 条码/OCR → AI 预览入库 → 流式能力横展 → 多轮/端侧模型 | 确定性本地映射优先；任何 AI/OCR 结果均“预览→用户确认→来源留痕”；云端默认关闭/透明，端侧为可选能力 | 隐私数据流、离线失败路径、schema 兼容、成本/延迟、端侧包体与设备矩阵 |
| R9 | ADR/商业验证，不编码 | 透明规则可公开，壁垒放在体验、数据治理和服务；所有二期项用最小用户验证再决定投入 | 商业假设、版权许可、平台成本与授权记录 |
| R10 | 按功能段执行 → 失败归因 → 回归 → 再验 | 严格复用唯一真机清单；日志/截图须关联 DEV ID，不以口头结论关闭 | 设备型号、系统/API、安装包 SHA、日志和截图 |
