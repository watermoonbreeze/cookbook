### D-01 · 只交付 Android（iOS 暂缓）｜生效
- 背景：KMP 架构可跨平台，但资源有限、优先打磨核心。
- 选项：A 双端并行 / B 先 Android。
- 决定：B。iOS target 注释，`actual` 与 framework 验证留待启用前。
- 影响：DI 平台化/KMP 日志等 iOS 就绪项**降为低价值**（→[07](07_项目现状.md)）。

### D-02 · 色系墙只看膳食结构、不关联热量/慢病｜生效
- 背景：热量是"个人"概念（需身体数据），慢病提示需病种；色系墙是"全家结构"视图。
- 选项：A 色系墙升级为热量/达标热力图 / B 色系墙保持纯结构、热量与慢病走个人视角今日卡。
- 决定：B（用户拍板）。
- 影响：`NutritionLevelEvaluator` 服务今日卡；`FoodGroup.nutritionLevel` 保持纯结构。"首页可视化=色系墙热力图"**不做**（冲突）。

### D-03 · 正向营养素只加信息、不改级别｜生效
- 背景：慢病深挖想体现"钾/纤维有益"，但钠钾比/纤维抵消 GI **无国标换算**。
- 选项：A 正向抵消负向罚分/改级别 / B 正向只追加温和提示、不动级别、不因不足下调。
- 决定：B。守免责红线，避免自造标准。
- 影响：高血压钾、糖尿病纤维均"锦上添花"；痛风/高血脂属不同性质。（→[20](20_健康与算法逻辑（专属）.md)）

### D-04 · 忌口/限量/调养只按主料判定｜生效
- 背景：规则层无逐食材克数，按全部食材判会让"含盐"的每道菜都忌口。
- 选项：A 按全部食材 / B 只非调料 / C 只主料(isMain)。
- 决定：C（用已 populated 的 is_main 作占比代理）。调料忌口转"少盐"做法提示不剔除菜。
- 影响：`HealthRuleEngine`/`gatherForPlan`/详情页三处统一口径。

### D-05 · 规则先筛 + AI 只在安全集内组合｜生效
- 背景：LLM 可能编造/违忌口。
- 决定：代码规则引擎筛出"安全候选(可做+不犯忌)"并打分，AI 只在候选集内组合并解释；JSON 校验菜 id 必在候选内；无网/失败纯规则兜底。
- 影响：忌口/份数红线由代码保证，模型无权绕过。

### D-06 · 嘌呤用定性、不设数值三级｜生效
- 背景：嘌呤"低/中/高"三级**无国标阈值**（WS/T 560-2017 只给"应避免/限制/可选择"定性清单）。
- 决定：care 规则与评级器用定性（avoid/limit/recommend），标"非国标·惯例"；GI 用 FAO/WHO(55/70)。
- 影响：痛风 care 规则、`NutritionLevelEvaluator` 嘌呤分支均定性。（→[20](20_健康与算法逻辑（专属）.md)）

### D-07 · 保存餐食预览｜**所有保存都预览**（2026-07-18 二次确认，最终）
- 背景：`AddDayFoodScreen` 同时承载"记一餐/实录"(isPlan=false，date≤今天，记已吃)与"计划"(isPlan=true，date>今天，排未来餐)。曾在"仅计划预览"与"全部预览"间反复。
- 决定：用户 2026-07-18 理清场景后二次确认——**所有保存餐食（实录 + 计划）都先弹"保存前预览"确认**。
- 影响：`AddDayFoodScreen` 保存 onClick = `{ previewOpen = true }`（无条件预览）。

### D-08 · 小型结构化配置存偏好 JSON 免迁移｜生效
- 背景：身体数据等单行低频配置若建表要迁移。
- 决定：`@Serializable` data class 序列化进 `user_preferences` 一个 key（`ignoreUnknownKeys`），加改字段零迁移。
- 影响：`BodyMetrics` 等走此模式，不新建表。

### D-09 · 商业化路线：一期不变现·二期AI双轨·不做电商toB（2026-07-19 用户拍板）｜生效
- 背景：竞品+商业模式调研——慢病 C 端付费难、头部靠 to B、纯社区变现失败；家庭工具宜"高频留存+克制变现"。
- 选项：聚合合并/激进变现/克制变现。
- 决定：①一期只争粘度不变现 ②二期最小化可选账号+AI **双轨**(内置默认AI订阅 + 用户自带Key永久免费)·核心记菜/推荐/**忌口健康安全能力永久免费** ③**不做电商导购、不主动追 toB**(保持产品纯粹防反感) ④对外文案温和化(不显性标"三高痛风"病名·用"健康管理/慢病家庭") ⑤守合规三硬线(不宣疗效/科普购物分页/数据最小必要)。
- 影响：→ `竞品对比与商业化规划.md`(战略单一真相源)·文案准则(§2.5温和化)·未来账号/AI订阅工程。定价待用户 AI 套餐成本定。

### D-10 · 数据源战略：家常菜食材线走权威成分表·不接超市（2026-07-19）｜生效
- 背景：用户观察多 App 数据完整度不足、华为/薄荷有百万级预包装库、问能否对接盒马/胖东来。
- 决定：**两条线分开**——①家常菜食材线(主战场·仅几千条·对齐《中国食物成分表》本地内置·契合本地优先) ②预包装线(轻量·条码/OCR/按需·不自建百万库)。**不接超市**(商超无营养API·无案例·爬取违ToS)·**不买第三方库**(违本地优先)。差异化不在库大小而在"中式家常菜定量营养+慢病忌口决策"。
- 影响：→ `竞品对比与商业化规划.md §三·五`·餐次/忌口数据扩充只用已有食材(不接外部)。

### D-11 · 多人关注：多选+当前查看指针·非聚合·零 schema（2026-07-19）｜生效
- 背景：夫妻俩都三高想分别盯各自达标/慢病；热量/份额是个人概念·加总无意义且碰健康免责红线。
- 决定：`is_focus` 单选→**可多选**(约束≥1)+**当前查看指针**(存偏好JSON·今日卡与报告共用)·`resolveViewing` 收口(签名不变下游几乎不动)·**不做聚合合并**·**零 schema 迁移**·**1人零变化**。家庭页只管"关注谁"、切看交今日卡/报告切换器。
- 影响：→ 04数据层(`FOCUS_VIEWING_MEMBER_ID`)·03界面(§9.23)·`FamilyRepository.resolveViewing/toggleFocus`。

### D-12 · 菜品餐次为可存储多值属性·Matcher降默认推断器（2026-07-19）｜生效
- 背景：早餐推炒菜不合理；`MealSlotMatcher` 原按菜名临时猜。
- 决定：新增 `dish_meal_slot`(多对多·指向 meal_type)·Matcher **降级为"生成默认值的推断器"**(新建/回填推断初值·之后以存储值为准)·预设菜 seed 打标(回填只补空·`SEED_LOGIC_VERSION`+1)·**恒非空兜底正餐**·食材餐次一期不做。数据扩充**只用已有食材**(营养已覆盖·零编造·引用完整性单测)。
- 影响：→ 04数据层(dish_meal_slot)·03界面(§9.21)·20健康算法(AI推荐查关联)。
