### D-01 · 只交付 Android（iOS 暂缓）｜生效
- 背景：KMP 架构可跨平台，但资源有限、优先打磨核心。
- 选项：A 双端并行 / B 先 Android。
- 决定：B。iOS target 注释，`actual` 与 framework 验证留待启用前。
- 影响：DI 平台化/KMP 日志等 iOS 就绪项**降为低价值**（→[07](07_项目现状.md)）。

### D-02 · 色系墙只看膳食结构、不关联热量/慢病｜生效
- 背景：热量是"个人"概念（需身体数据），慢病提示需病种；色系墙是"全家结构"视图。
- 选项：A 色系墙升级为热量/达标热力图 / B 色系墙保持纯结构、热量与慢病走个人视角今日卡。
- 决定：B（用户拍板）。
- 影响：`NutritionLevelEvaluator` 服务今日卡；`FoodGroup.nutritionLevel` 保持纯结构。"首页可视化=色系墙热力图"**不做**（冲突）。

### D-03 · 正向营养素只加信息、不改级别｜生效
- 背景：慢病深挖想体现"钾/纤维有益"，但钠钾比/纤维抵消 GI **无国标换算**。
- 选项：A 正向抵消负向罚分/改级别 / B 正向只追加温和提示、不动级别、不因不足下调。
- 决定：B。守免责红线，避免自造标准。
- 影响：高血压钾、糖尿病纤维均"锦上添花"；痛风/高血脂属不同性质。（→[20](20_健康与算法逻辑（专属）.md)）

### D-04 · 忌口/限量/调养只按主料判定｜生效
- 背景：规则层无逐食材克数，按全部食材判会让"含盐"的每道菜都忌口。
- 选项：A 按全部食材 / B 只非调料 / C 只主料(isMain)。
- 决定：C（用已 populated 的 is_main 作占比代理）。调料忌口转"少盐"做法提示不剔除菜。
- 影响：`HealthRuleEngine`/`gatherForPlan`/详情页三处统一口径。

### D-05 · 规则先筛 + AI 只在安全集内组合｜生效
- 背景：LLM 可能编造/违忌口。
- 决定：代码规则引擎筛出"安全候选(可做+不犯忌)"并打分，AI 只在候选集内组合并解释；JSON 校验菜 id 必在候选内；无网/失败纯规则兜底。
- 影响：忌口/份数红线由代码保证，模型无权绕过。

### D-06 · 嘌呤用定性、不设数值三级｜生效
- 背景：嘌呤"低/中/高"三级**无国标阈值**（WS/T 560-2017 只给"应避免/限制/可选择"定性清单）。
- 决定：care 规则与评级器用定性（avoid/limit/recommend），标"非国标·惯例"；GI 用 FAO/WHO(55/70)。
- 影响：痛风 care 规则、`NutritionLevelEvaluator` 嘌呤分支均定性。（→[20](20_健康与算法逻辑（专属）.md)）

### D-07 · 保存餐食预览｜**所有保存都预览**（2026-07-18 二次确认，最终）
- 背景：`AddDayFoodScreen` 同时承载"记一餐/实录"(isPlan=false，date≤今天，记已吃)与"计划"(isPlan=true，date>今天，排未来餐)。曾在"仅计划预览"与"全部预览"间反复。
- 决定：用户 2026-07-18 理清场景后二次确认——**所有保存餐食（实录 + 计划）都先弹"保存前预览"确认**。
- 影响：`AddDayFoodScreen` 保存 onClick = `{ previewOpen = true }`（无条件预览）。

### D-08 · 小型结构化配置存偏好 JSON 免迁移｜生效
- 背景：身体数据等单行低频配置若建表要迁移。
- 决定：`@Serializable` data class 序列化进 `user_preferences` 一个 key（`ignoreUnknownKeys`），加改字段零迁移。
- 影响：`BodyMetrics` 等走此模式，不新建表。

### D-09 · 商业化路线：一期不变现·二期AI双轨·不做电商toB（2026-07-19 用户拍板）｜生效
- 背景：竞品+商业模式调研——慢病 C 端付费难、头部靠 to B、纯社区变现失败；家庭工具宜"高频留存+克制变现"。
- 选项：聚合合并/激进变现/克制变现。
- 决定：①一期只争粘度不变现 ②二期最小化可选账号+AI **双轨**(内置默认AI订阅 + 用户自带Key永久免费)·核心记菜/推荐/**忌口健康安全能力永久免费** ③**不做电商导购、不主动追 toB**(保持产品纯粹防反感) ④对外文案温和化(不显性标"三高痛风"病名·用"健康管理/慢病家庭") ⑤守合规三硬线(不宣疗效/科普购物分页/数据最小必要)。
- 影响：→ `竞品对比与商业化规划.md`(战略单一真相源)·文案准则(§2.5温和化)·未来账号/AI订阅工程。定价待用户 AI 套餐成本定。

### D-10 · 数据源战略：家常菜食材线走权威成分表·不接超市（2026-07-19）｜生效
- 背景：用户观察多 App 数据完整度不足、华为/薄荷有百万级预包装库、问能否对接盒马/胖东来。
- 决定：**两条线分开**——①家常菜食材线(主战场·仅几千条·对齐《中国食物成分表》本地内置·契合本地优先) ②预包装线(轻量·条码/OCR/按需·不自建百万库)。**不接超市**(商超无营养API·无案例·爬取违ToS)·**不买第三方库**(违本地优先)。差异化不在库大小而在"中式家常菜定量营养+慢病忌口决策"。
- 影响：→ `竞品对比与商业化规划.md §三·五`·餐次/忌口数据扩充只用已有食材(不接外部)。

### D-11 · 多人关注：多选+当前查看指针·非聚合·零 schema（2026-07-19）｜生效
- 背景：夫妻俩都三高想分别盯各自达标/慢病；热量/份额是个人概念·加总无意义且碰健康免责红线。
- 决定：`is_focus` 单选→**可多选**(约束≥1)+**当前查看指针**(存偏好JSON·今日卡与报告共用)·`resolveViewing` 收口(签名不变下游几乎不动)·**不做聚合合并**·**零 schema 迁移**·**1人零变化**。家庭页只管"关注谁"、切看交今日卡/报告切换器。
- 影响：→ 04数据层(`FOCUS_VIEWING_MEMBER_ID`)·03界面(§9.23)·`FamilyRepository.resolveViewing/toggleFocus`。

### D-12 · 菜品餐次为可存储多值属性·Matcher降默认推断器（2026-07-19）｜生效
- 背景：早餐推炒菜不合理；`MealSlotMatcher` 原按菜名临时猜。
- 决定：新增 `dish_meal_slot`(多对多·指向 meal_type)·Matcher **降级为"生成默认值的推断器"**(新建/回填推断初值·之后以存储值为准)·预设菜 seed 打标(回填只补空·`SEED_LOGIC_VERSION`+1)·**恒非空兜底正餐**·食材餐次一期不做。数据扩充**只用已有食材**(营养已覆盖·零编造·引用完整性单测)。
- 影响：→ 04数据层(dish_meal_slot)·03界面(§9.21)·20健康算法(AI推荐查关联)。

### D-13 · AI 显式语义优先，本地能力只做规范化与兜底（2026-08-04）｜生效
- 背景：AI 结构化结果再次被本地菜名正则拆解，会破坏菜品层级、食材和调料语义；但本地库仍须保证引用、去重和数据质量。
- 选项：A AI 与本地规则双重解析并互相覆盖 / B AI 结果优先，本地仅校验与入库；缺失时才规则补全。
- 决定：B。AI 已给出食材/调料/做法/份量时保留原结果，仅做别名归一、查重、校验、新增或引用；规则模式、AI 缺字段/矛盾/低置信才调用菜名语义解析生成候选，并向用户展示来源。
- 影响：→ [20 核心实体能力层](20_健康与算法逻辑（专属）.md)；AI 记餐、手工创建和自动生成的统一能力层改造必须遵守此边界。

### D-14 · AI 记餐双阶段：AI 主导解析，健康建议仅展示（2026-08-04）｜生效
- 背景：用户希望 AI 尽量还原时间、餐次、菜品、食材/调料/做法及营养信息，并结合健康档案给建议；直接把完整档案交给解析请求会扩大隐私面，也会让不确定的模型意见干扰真实进食记录。
- 决定：①第一阶段 `meal-log.v2` 宽松解析，菜名是唯一硬门槛，AI 显式语义优先，本地只归一/校验/预览/入库；②本机 `HealthSafetyReport` 是健康事实与安全提示真相源；③第二阶段 AI 建议需本次单独同意，仅接收去标识化最小摘要；④建议在确认餐食下方以“查看建议”展开，纯会话展示、不持久化；⑤建议或其请求失败均不阻断真实餐食入库，计划/推荐的既有硬红线不变。
- 影响：→ [02 流程](02_业务流程全景.md)、[03 交互](03_界面与交互.md)、[20 算法](20_健康与算法逻辑（专属）.md)、[21 网络与隐私](21_AI与网络请求策略（专属）.md)；后续实现须新增显式同意、会话清除、脱敏诊断和规则日期/时间切分测试。

### D-15 · AI 记餐日期以添加页所选日期为唯一锚点（2026-08-04）｜生效
- 背景：模型可能把设备当天写入无日期输入；确认页的重新输入或预览首日反写也会丢失用户选择的日期，导致记录落错日。
- 决定：用户原文出现绝对日期才采用解析结果的 `date`；仅出现星期时映射至所选日期所在自然周；没有日期时统一落至所选日期并只展示一条锚定提示。所选日期贯穿输入、重新输入、预览和确认，模型不得覆盖它。
- 影响：`MealDateAnchorPolicy` 是共享真相源，AI 与规则降级共用；`AiMealPrompt` 只将所选日期作为锚点传给模型；异常反查见 [05](05_诊断地图.md)，网络行为见 [21](21_AI与网络请求策略（专属）.md)。

### D-16 · AI 记餐长输入采用“分段请求 + NDJSON 流式确认”（2026-08-05）｜生效
- 背景：整周餐食一次性整体 JSON 容易被 `max_tokens` 截断；整体 schema 失败会让用户看不到已生成的有效内容，也不利于确认页渐进反馈。
- 决定：快速记限制≤200字；周期记按周/日期分段，每段≤200字并逐段请求；云端模型按场景放大输出 token，覆盖一周餐食；优先使用 NDJSON/JSONL 流式协议，每行可独立校验并实时进入确认页；整体 JSON 只作为兼容输入，由本地适配为同一扁平确认结构。
- 影响：后续实现需改 `AiMealPrompt`、`CloudAiRuntime`、`AiMealParser`、`AiMealInputViewModel` 和 `AiMealInputSheet`。保存只允许已解析且合法的餐食实体；健康建议仍仅展示不入库。实现接口、状态机、编码规范和验收门禁见 `feature/AI记一餐_周期记_NDJSON流式开发规范.md`；B1/B2 的 Runtime 单 call 取消边界、fallback 单来源归属、disconnect 取消竞态、首帧 IO/HTTP 分类重试和确定性测试约束已完成八审，B3 只认 `feature/AI记一餐_周期记_NDJSON流式_B3会话实施蓝图.md`，并受 D-17 的冻结蓝图门禁约束。

### D-17 · 多模型开发以“冻结实施蓝图”替代开放式编码（2026-08-05）｜生效

- 背景：用户日常追问"全景图新鲜度怎么长期保持"，引出四轮递进调查（均由独立 Opus agent 执行，ARCH 只做事实核对与最终整合，不越权替用户拍板）：①既有 `review_freshness.py`（STALE/ANCHOR-MISMATCH）机制设计本身合理，但"发现问题后没人处理"是真正缺口；②用户提出"git diff 驱动更新全景图"的直觉——调查证实 Code→Feature 反查确实是 Phase 1 设计过、但从未被任何阶段认领的能力，且用现有 13 个 `project_graph/features/*.yaml` 的 `match:` glob 对最近 3~8 周真实提交实测机械覆盖率 68~84.5%，补 20 条 glob 即可到 ~100%，证明"便宜且可行"，但"逐 commit 触发"是错误粒度——git diff 范围可结合，等价于"批次收口时对 `<基线>..<head>` 查一次"，成本低 20 倍且信息量相同；③深挖发现 cookbook 已有 `project_graph/`（Phase 1/2 FROZEN，13 Feature/109 WorkItem/98 Verification）在做几乎同一件事，且其 Phase 3（生成视图）已停摆、被 D-21 禁止主动重启，`match:` 数据本身有用但整个 Graph 系统被证实是全项目最陈旧的一层（自 08-11 未再更新），而 D-23 建的 `projectReview/features/*.md` 反而随真实开发批次持续新鲜；④用户据此明确要求"只要一份真相源，不要两份"，并给出目标结构（每功能一个文件夹，装界面/实现/待办/缺陷/方案）+ 硬约束"新鲜度维持不能靠文字规则，必须是机械代码门禁"，由 Opus 出正式落地方案，ARCH 按用户三条现场决策收口定稿并直接执行迁移（过程见 `temp/claude/全景图重构方案_草稿.md`，此为完整设计记录，本条为归档摘要）。
- 选项（Project Truth 归属）：A 维持 Project Graph 为 Truth，projectReview 降级引用它 / B 两者并存、各自权威一部分 / C Project Truth 整体移交 `projectReview/features/`，Project Graph 整体归档退休。
- 选项（新鲜度机制形态）：A 保留纯软信号（页脚 STALE 提示，靠人自觉处理）/ B 加"复核至 sha"抑制字段缓解告警疲劳（第一轮 Opus 建议，未采纳）/ C 机械硬阻断——git diff 命中 Feature 的 match 路径后，要求对应功能文件夹必须同批更新，缺失即阻断批次 ACCEPT，不允许"我觉得没影响"这类主观免责。
- 选项（触发时机）：A 逐 commit 触发（git hook）/ B 批次收口时触发（挂在已有的 `BLUEPRINT_STATE.md` ACCEPT 关卡 + 会话交接）。A 被否决：本项目多机器协作、无 CI，hook 不随 clone 走，装了的机器有效、没装的机器静默失效——"看起来已覆盖但实际没有"比完全没有机制更危险，且逐 commit 相对逐范围检查零信息增益、只多 20 倍调用成本。
- 决定：Project Truth 归属选 **C**——`project_graph/` 整体 `git mv` 至 `.ai-context/_archive/project_graph_20260819/`（Phase 1/2 FROZEN 状态、61 个校验测试、历史决策完整保留，只读存档，不再被任何工具引用）；13 个 yaml 的 `match:` 字段值一次性内联抄入对应 `projectReview/features/<F-ID>/STATE.yml`，不再有"降级为字典源、留一条外部引用"这种设计——两个目录+一条引用关系仍然是两份真相源，仍有漂移空间（本条决策本身的起因之一，就是"projectReview 和 project_graph 其实是一个，可能是某次会话的 AI 自主创建了第二份"）。新鲜度机制选 **C**（机械硬阻断），新增 `.ai-context/tools/feature_sync_check.py`：C1 UNMAPPED（改动文件无功能归属）、C2 BEHIND（命中某功能但其文件夹未同批更新）、C3 FAKE-BUMP（`synced_to` 推进但无实质内容变化且未声明 NOOP）、C4 STRUCT（文件夹结构/白名单/ID 唯一性等）、C5 BACKLOG（历史欠账，软信号）、C6 INDEX-STALE（`功能路径索引.md` 的生成段落后于各功能 `20_实现.md` 的"代码落点"，回应用户"功能路径索引要跟着全景图同步更新，且必须是机械检查不是提醒"这条追加要求）。触发时机选 **B**：主承重挂在 `BLUEPRINT_STATE.md` 批次转 `ACCEPTED` 时（硬阻断，取代原 G1 三选一里的 `DEFER`/`N/A` 免责选项——原设计实测命中率 0/2，因为"要不要回写"是主观判断，两个免责选项让人本能地全选它们；新设计把"这批命中了哪些功能"变成 git diff 算出来的客观事实，人无权判断，只剩"真的做了(SYNC-OK)"或"确认无需做+写≥15字理由留痕(SYNC-NOOP)"两条路），会话交接挂 `--backlog` 软信号（C5，结果进 `SESSION_交接.md` 第六节）。
