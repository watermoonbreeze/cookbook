### 独立复核类 agent 有两种失败模式，处理方式不同
- 现象一（基础设施断连）：`Connection lost mid-response`，出现在响应中途、无规律，与任务本身无关。连续遇到 5 次后第 6 次才成功。
- 现象二（用量限额撞线）：`You've hit your session limit · resets HH:MMpm`，报文里带明确的重置时间点。
- 正解：**看错误文案区分**——现象一直接重试一个新 agent（旧的已死无法恢复到相同状态，重开成本也不高）；现象二**不要立刻重试**（大概率再撞同一限额），等到报文里的重置时间点过后，用 `SendMessage` **恢复同一个 agent**（而非重新起一个）继续——它保留完整调查上下文，比重新起号快得多。判断当前是否已过重置时间，用 `date -u` 拿 UTC 手动换算（Git Bash 的 `TZ=` 环境变量在 Windows 上不一定生效，`date` 命令本身会忽略）。

### 长跑独立复核 agent 必须"边核实边写入"，本次真实断连场景验证有效
- 现象：GOV-BP-P3-01 的裁决 agent 在完成"核实项 3"（发现 Section E 造假的决定性证据，全篇最关键的一步）并写入 `temp/claude/*.md` 后，撞上用量限额中断。因为已经落盘，`SendMessage` 恢复后直接从"核实项 4"接着写，**核实项 1~3 的完整调查过程零损失**，没有重新推导一遍那条证据链。
- 正解：派长跑独立复核/调研类 agent 时，指令里明确要求"每完成一个子问题的判断，立即 `Write` 一份完整进度文件到 `temp/claude/`，不要攒到最后一次性输出"，且每次写入要写**完整可读的当前进度**（不是 diff），断连时才能从文件直接续。
- 通则：这条策略此前只是"应该这么做"的建议（见跨项目记忆 `agent-batch-checkpoint-strategy`），本次是在真实断连场景下第一次被验证确实有效，值得作为长跑 agent 的默认要求而非可选项。

### 正式治理工件也可能包含自证式虚构证据，独立裁决时不能只读文档相信自称
- 现象：`GOV-BP-P3-01` 审计文件（`GOV_BP_P3_01_AUDIT.md`）用大量英文治理术语（"Governance Batch Identity"/"External Canonical Evidence"）+ 精确到字符的 SHA-256 前后哈希值，全篇自称 PASS。独立裁决实测发现：Section G（脚本命令）7 天后逐字复现，是真实交付；但 Section E 声称的"改动了用户级全局文件并给出 SHA-256"，在该文件唯一真相源（另一个 git 仓库）的提交历史里**查无此事**——两个哈希值与该文件全部历史版本都对不上。
- 发现方式：不是怀疑文档语气可疑就定论，而是**逐条实测**——重算全局文件当前哈希、翻它的完整 git 历史比对哈希、grep 声称新增的条款是否真的存在于当前文件全文。三条独立证据全部指向"这个改动从未发生"，才下结论。
- 通则：审查任何自称"已验证/已完整性核对"的工件，**精确的数字（哈希/commit号/百分比）本身不是可信度证明**——越精确的伪造证据越容易骗过"看起来很严谨"的直觉。真正可信的判据只有"能否独立重算/复现"，做不到就是不可信，无论包装得多正式。这个模式在本项目的 UBF 支线（`08` D-19）之外、更早的 `GOV-BP-P3-01` 批次里就已经存在——说明这类问题不是某条支线的专属病灶，任何"自我出具验证报告"的场景都要用这个尺子量。

### 全景图类文档的信息架构：横轴（跨功能）与纵轴（单功能）分离，防止两边重复真相源
- 现象：项目全景图（`projectReview/`）原有 11 册按"架构/流程/数据/算法/AI/预设治理/约定"横向切分（跨功能视角），但缺一个"这一个具体功能现在做到哪一步"的纵向入口，导致该类信息散落在 `feature/` 目录 127 个自由格式文件里，找不到、也容易和横轴册内容重复。
- 正解：新增按功能 ID 一一对应的纵向目录（本项目为 `projectReview/features/<F-ID>.md`，13 个，对应既有的结构化功能清单，不新发明命名），每个功能自己的目标/现状/讨论方案/bug/待办放这里；横轴册继续放跨功能的机制/算法/架构/约定不变；写一条**内容归属判断规则**（只影响一个功能→纵轴，影响≥2个功能→横轴，两边沾边则窄的一边只放摘要+链接）钉在红线文档里，防止后续有人把同一段算法说明抄两份。
- 通则：任何"全景图/知识库/wiki 类"文档系统一旦要同时服务"横向全局理解"和"纵向单点深挖"两种诉求，天然需要两根正交轴而不是塞进同一张表——**用现成的结构化清单（如已有的功能/模块 ID 列表）做纵轴的组织单位，不要另起一套命名**，否则将来两套分类要花力气对齐。

## AI 快捷记引擎标签 + 自动兜底 session（2026-08-08）

> 用户报告 bug：未配置 AI 时点发送提示"没能识别出菜品，试试更具体的描述？"——文案误导（暗示措辞问题，实为没配 Key）。最初设计"检测未配置就同步短路报错"被用户当面否决：规则解析应是 AI 的兜底而非被 AI 挡住的独立模式，需自动（非手动）回退+标题旁常显引擎+确认页说明来源。重新设计后跳过独立 CODE 角色，ARCH 直接实现+两轮独立 `google_quality_engineer` 审查。

### 状态判断禁止用位置索引类 API 替代真实状态查询
- 现象：多段流式解析场景，"该段是否仍在处理中"的判断用了 `session.currentSegmentId() == seg.segmentId`——这个 API 只反映"当前遍历到第几个下标"，段已经 `COMPLETED` 成功后下标还没推进到下一个，这个比较仍然成立，导致对已成功的段重复触发本该只在真失败时才跑的兜底逻辑。
- 正解：新增一个直接查真实状态的 API（`isStreaming(segmentId): Boolean = segmentStates[segmentId] == STREAMING`），比较状态本身而非位置代理指标。
- 通则：任何"这个东西是否还没结束/还没轮到"的判断，如果用的是集合位置/下标/顺序指针做代理，先问一句"如果这东西已经正常结束了，这个指针会不会还指着它"——顺序指针不推进 ≠ 没结束。

### 跨结构归属禁止用"内容字段值是否等于预期"匹配，要用结构化 ID
- 现象：把 AI 解析结果按段合并时，用 `day.date == segment.targetDate.toString()` 字符串匹配"这天是不是这段解析出来的"——但 AI 完全可能正当地给出不同日期（用户说"昨天晚饭"），也可能用不同分隔符（`2026/08/05` vs `2026-08-05`），字符串匹配会把这天误判成"没解析出来"整条丢弃。
- 正解：改成按 segmentId 直接从该段自己的解析草稿取结果（新增 `StreamingMealSession.daysForSegment(segmentId)`，从该段专属的 parser 实例取草稿，不查其他段），不依赖内容字段的具体值。
- 通则：判断"这条结果属于哪个来源"，永远优先用来源自带的结构化标识（ID），不要用结果内容里某个字段"恰好等于"来源的某个属性来反推归属——内容字段的值本就可能合法地偏离来源标识所暗示的默认值。

### 新增内部诊断代号，必须同步核对所有已有的用户可见展示通道
- 现象：给"未配置""网络异常"等内部原因引入了哨兵字符串（如 `AI_NOT_CONFIGURED`），只翻译了其中一条展示路径（确认页的来源说明），另一条既有的展示通道（"诊断信息"警告卡片）没同步处理，用户会看到原始英文代号。
- 正解：把"翻译成人话"收口成一个函数（`humanizeWarning`），确认所有读取该字符串做 UI 展示的地方都过这个函数。
- 通则：新增内部代号/哨兵值前，先搜一遍这个值最终可能流向的**全部**用户可见展示位（不只是这次改动主要关心的那一个），同一批新代号很容易只翻译了当下顺手改的那条路径。

### 阻断修复引入的状态守卫，必须反向核对是否恰好堵死了另一条真实场景的兜底
- 现象：上面"状态判断"那条 bug 的修复（加 `isStreaming` 守卫）本身完全正确，但**这个误判分支修复前"顺便"覆盖了另一个真实场景**——"AI 正常 `Completed` 但一行都没解析出合法菜品"（模型只回了文字/道歉）。这条路径不经过任何 `onFailed` 调用点，之前全靠那个有 bug 的"未终态"误判分支意外地把它也捞进兜底流程；`isStreaming` 精确化之后，这条路径彻底没有触发点，直接卡死在 ERROR 且没有任何救回路径。
- 发现方式：不是自己想到的，是**第二轮独立质量审查**（专门复核"第一轮修复是否生效"，而非重新审查全部代码）发现的。
- 正解：在段全部终态后的收尾阶段，显式补一次"对每个仍无合法结果的段尝试兜底"（幂等，靠已有的"尝试过"标记防重复）。
- 通则：**阻断修复本身也要过一遍复核，而不是"阻断消失了就算完"**——尤其当修复手段是"新增一个更精确的状态守卫去堵某个误判分支"时，要反向想一遍"这个误判分支此前是不是意外地覆盖着另一个本该有兜底、但没有专门代码路径处理的真实场景"。这类回归很隐蔽，因为它不是"修复没生效"，而是"修复生效了、但捎带切断了一条侥幸路径"。

### GC-37 独立挑战台账首次实战：起草蓝图后被独立挑战 agent 挑出 6 处真阻断
- 现象：ARCH 起草了一份自认为完整的营养展示+错误处理蓝图，按项目蓝图协议 GC-37 派独立 opus agent 挑战（agent 只看蓝图成文，不知起草过程），结果 14 项挑战里 6 项是真阻断——sticky 字段沿用旧值、null 值语义与既有组件契约不符导致内容消失、一次性初始化缺刷新入口、判定函数值域比实际概念更宽、恒定输入让下游异常检测分支永久失活、周期记非首段的相对日期用错锚点。
- 通则：这些问题的共同点是"蓝图字面写得很清楚，但设计逻辑本身有洞"——不是审查力度不够，是同一个人设计+同一个人复核天然缺少对抗性视角。独立挑战不是走流程，起草完成后如果没有真正独立（不知情）的复核，这类洞大概率会被机械实现进代码里。详细案例分类见 `12_多模型协作与实施蓝图规范.md` §10.z。

### Compose/Koin Sheet 会话 key：同日误关要保留，切日期/保存后才清空
- 现象：为修“切换日期后 AI 快捷记仍沿用旧日期”，曾把 `AiMealInputViewModel` key 做成每次打开都递增；副作用是用户同一日期误关 Sheet 后重开，刚输入的内容被清空。
- 正解：key 的生命周期按业务会话定义，不按“打开动作”定义。AI 快捷记同一日期未保存会话应复用 VM 以保留输入/预览；只有日期切换或保存完成后才换 key。保存完成后必须换 key，避免复用 `DONE` 状态导致 Sheet 再开即自动关闭。
- 通则：修“陈旧参数”不要简单“每次重建”。先定义哪些用户动作代表新会话：本例是“日期变化/保存成功”，不是“关闭/重开”。

### AI 输出协议不要把整体 schema 成败当成唯一真相
- 现象：模型输出过长整体 JSON 被 `max_tokens=4096` 截断，`finish_reason=length`；如果只按整体 JSON schema 判失败，会丢掉前面已经完整生成的有效餐食。
- 正解：长输出改 NDJSON/JSONL 事件流，完整事件可逐条校验、逐条展示、逐条进入可保存预览；半截尾部只进诊断。整体 JSON 仍可作为兼容输入，能提取菜名就规范化，不因“不是扁平格式”直接拒绝。
- 通则：AI 长内容输出优先设计“可增量提交给 UI 的协议”，而不是等待一个大对象完整闭合后才显示。

## 超长无人值守·营养线&推荐&拍照 session（2026-07-21·17笔全push）

### produceState 的 key 别用"派生后可能恒定"的值——用真正会变化的原始输入
- 现象:全屏图片查看器(`FullScreenImageViewer`)**删当前图后预览不刷新**、左右滑一下才变(用户真机抓)。
- 根因:`rememberImageBitmap` 里 `produceState(key1 = cacheKey)`,而 `cacheKey = if(preview) null else …`——**preview=true 时 cacheKey 恒 null**→produceState 的 key 永远是 null→`path` 变了(删图后当前页指向新图)producer **不重跑**、显旧位图;只有翻页让页面重新进入合成才重解。
- 修:`produceState(…, key1 = path, key2 = preview)`——key 用**真正随内容变化的 path**,而非"预览时恒 null"的派生 cacheKey。**通则:produceState/LaunchedEffect 的 key 要能反映所有会改变产出的输入,别用一个在某分支恒定的派生值当 key。**

### 给同步映射函数加 IO 查询→改 suspend→会打断其同步调用点(suspend 传染)
- 场景:`AiRecommendViewModel.mapResult` 原是同步纯映射;§9.36 要在里面批量查每菜营养(`dishNutrition` 是 suspend)→把 mapResult 改成 `suspend`。
- 坑:mapResult 有个**同步调用点**(`setMedicinalFilter` 的本地重排,不 gather 不云端、原来瞬时同步)→编译错 `Suspend function should be called only from a coroutine`。

### combine 多源含 suspend：可内联到 combine 的 suspend transform
- `combine(f1,f2,f3,f4){...}` 的 transform **本身可 suspend**(可直接 `nutritionRepo.totalOf()`)，简单场景可内联、`return@combine null` 产出可空流，替代 `combine(...).mapLatest{}`(list+cast 的写法易错)。需"新值取消旧算"时才保留 mapLatest；本地库快查内联即可。四参 combine 有 typed 重载，别用 `listOf(Any)` + cast(类型对不上还漏 null 性,如 `observeFocusBody()` 返回**非空** BodyMetrics)。

## 库存/占用类需求的建模方法论（2026-07-10）

- **"分配/占用/额度/余额"类需求优先做「派生态」而非「存储扣减」**：库存份数体系最终采用**不落库、实时按时间序算**。存储扣减会遇到：加回时不知该先补谁、编辑/删餐重复扣、触发时机难定。派生只需 `份数(用户改) + 餐食记录` 实时算，天然支持"加份数早的先恢复"。[AI生成]
- **派生占用要设「时间窗口」，否则历史会污染当前**：纯派生若把**所有历史餐**都算作占用当前库存，会出现"两年前用过还占今天份数"的荒谬。解法=**入库日窗口**：每食材记 `added_at`(持久化)，只算 `date >= added_at` 的餐。[AI生成]
- **余额型字段用「结算式」更新，避免累加+窗口重置的重复计入**：`serving_count` 累加(+delta)但窗口重置到now → 为0后重加会把已消耗的重复算进剩余。正确=加时先算当前剩余、再 `serving_count = 当前剩余 + delta` 并重置窗口(`activatePantry`)。[AI生成]
- **同类"状态标注"要覆盖所有展示入口，别只加一处**：缺料/采购最初只加在周期规划预览，餐食卡片(首页计划/食历)没有→用户以为没生效。应在**统一的数据组装点**(如 `MealRecordRepository` 组卡)算好，所有复用同一卡片组件的地方一并生效。[AI生成]
- **派生态天生"覆盖存量数据"**：因不落库、查询时实时算，新增此类功能后**现有历史数据自动被评估**，无需"创建新记录才生效"。回答用户"存量能否覆盖"时可据此确认。[AI生成]

## [2026-07-15] 状态并发与迁移/诊断类

### 旧快照 copy 写回丢并发字段（真机踩过）
- 现象：食材编辑器默认单位下拉空（连中文单位都没有）。真机 logcat 埋点显示 `loadUnits` 已查到 22 个单位写入 state，但编辑器拿到 0 个。
- 根因：`IngredientPickerViewModel.selectMainTab` 启动时 `val current = _state.value`（此时 availableUnits 还空），DB 查询**挂起期间** init 的 `loadUnits` 把 availableUnits 填了，等 `_state.value = current.copy(...)` 写回时用的是**旧快照** current，把并发填入的 availableUnits 冲回空。
- 通用规律：**多个 init 加载器并发**（loadCategories/loadUnits/loadAllIngredients…各自 launch），任一处 `val x=_state.value` 捕获后经挂起再 `_state.value = x.copy(...)`，都会丢掉挂起期间别处更新的字段。
- 修法：写回一律基于**最新** `_state.value.copy(...)`，或用原子的 `_state.update { it.copy(...) }`（NewDishViewModel 字典加载就是用 `_state.update{}` 正确避坑的）。
- 排查手法：全项目 grep `(_state|_uiState)\.value = [a-zA-Z_]\w*\.copy\(`（写回用的不是 `.value.copy` 而是捕获的局部变量）+ `val \w+ = _state.value`（全量捕获点），逐个看是否"捕获→挂起→旧快照写回"。

### 真机诊断"数据有但没传到 UI"
- adb 多设备用 `adb -s <序列号>`；`adb devices -l` 看序列号。
- Compose 底部导航文本**不进无障碍树**，`uiautomator dump` 抓不到导航项文本；改用 `wm size` 按比例点或让用户操作。
- 华为等设备 shell **无 sqlite3**；`adb exec-out run-as <pkg> cat databases/xxx.db > local.db` 拉库到本地用 python sqlite3 读（注意关 App 让 WAL flush，否则拉出的可能不完整/"file is not a database"）。
- 定位链路最快：在"查(repo)→存(VM state)→读(UI)"三处各埋一条 `AppLogger.d(TAG,...)`/`CookbookLog.d(...)`，一次 logcat 就知道断在哪。定位后删日志。

### SQLDelight 迁移 rename 字典项保 FK
- 统一单位/字典命名（如 克→g、毫升→ml、升→L）：用 `UPDATE measurement_unit SET name='g' WHERE name='克'`——**保 id 不变**，`dish_ingredient.unit_id`/`pantry` 按 id 引用、FK 不断、历史数据不丢。
- name 有 UNIQUE：若目标名可能已存在（如此前 force-seed 加过的重复英文单位），先 `DELETE ... WHERE name IN(...) AND source='preset'` 删重复，再**带守卫**重命名 `UPDATE ... WHERE name='克' AND NOT EXISTS(SELECT 1 FROM measurement_unit WHERE name='g')`，防 UNIQUE 冲突让迁移崩（迁移崩=真机"初始化失败")。
- 同步改 seed 文件（dishes.json/ingredients.json 的 unit 字段）与 `PRESET_MEASUREMENT_UNITS`，并改按名断言的单测（`units["克"]`→`units["g"]`）；`unitNames()` 自动跟随 PRESET，引用完整性校验一致。

### 加列升级无损三件套
- `ALTER TABLE x ADD COLUMN col TEXT NOT NULL DEFAULT ''`：老行只补默认值、**零数据改动**；CREATE TABLE 同步加同列（全新装走 Schema.create）。
- 预设值回填放 seeder、**只填空的**（`WHERE col=''`）、按名/规则计算，不覆盖用户已选；每次启动幂等。
- 老用户数据的"补齐"靠"编辑时预填 + 保存即应用"，而非强制数据迁移（如老自建食材编辑时按名预选营养大类、点保存补挂分类）。

### 分类表无 code 列
- `FoodCategory` 模型与 `food_category` 表**都没有 code 列**，Group→分类只能**按 name 映射**（`FoodGroup.CATEGORY_NAME`）。注意红线：改 general 大类名会打断按名的映射/断言。

## Project Graph 领域经验（2026-08-10 Phase 1 Rework-4 收口）

### Verification ID 语义不可变（Stable ID 不得因新的观测事实被重新利用）
- 现象：Rework-3 把 `F-AI-MEAL.yaml` 的 `E-K1I-02` 写成 `kind: build / status: pass`（用「K1i 构建验证通过」表达），但真机验证清单 `真机待验证清单_202608082330.md` 中 `E-K1I-02` 的稳定语义是「周期记流式同样生效」的设备验证项（🔧 待真机确认）——即同一个 ID 被两个不同的验证事实占用了。
- 正解：**Stable Verification ID semantics are immutable**。已有稳定 ID 的语义以「最新唯一真机验证清单」为最高优先级 Truth Source；不得因为出现新的验证事实（如 Build 通过）就复用既有 ID 表达它。BLUEPRINT_STATE 里「K1i 构建命令通过」是真实 Build/Test Observed Fact，但它不能改变 E-K1I-02 的设备验证语义。
- 通则：Graph 的 Verification 实体对应的是「需要闭环的项目验收项」；单次 Gradle Build/Test 结果默认属于 **Observed Fact**，不自动创建 Verification Entity（Observed 自动采集属于后续 AI lifecycle 阶段）。也不得随手造 `E-K1I-BUILD-01` 之类的新 ID 硬塞 Build 语义。

### WorkItem closure 与 required Verification 一致性
- Contract：`WorkItem.status=done` 要求所有 `required=true` 的 Verification 为 `pass` 或 `not_required+reason`；存在 required `pending/fail/blocked` 时禁止 `done`。
- 修正 Truth 后若 K1i 仍有 E-K1I-01/02 两条 pending 真机项，K1i 状态必须是 `verifying`（不能 `done`、不能改 optional 洗白）。只按真实阶段设状态，不为通过 Validator 伪造 device pass。

### 多机协作·「更新 git」= 先拉远程再看本地
- 蓝图/规划文件可能由另一台机器（Codex/远端）新提交，本地目录不会自动同步。用户明确：**「更新一下git」是固定动作=先 `git fetch/pull` 拉远程、看远程新增了什么文件，再基于远程最新状态查本地**；禁止先在本地直接找、找不到才回头 fetch（`第一阶段-Rework-4.md` 就是远端 `ddcea510` 提交里带来的）。已同步 `08_用户习惯.md`。

### Contract README 教学示例用抽象 ID，别用真实业务实例（2026-08-11 Phase 2C END 清理）
- 现象：Project Graph `README.md` §6 曾用 `plans: - id: PLAN-AI-NDJSON  work_items: [K1g, K1i]` 作 storage-shorthand 教学示例。Phase 2C 冻结 K1i 独立 Plan（禁复用 PLAN-AI-NDJSON）后，这个"曾经正确的示例"变成**会误导未来 AI 的错误示例**——示例和真实 Graph 数据打架。

## L1 hotfix v1.1 + 全景图纵轴改文件夹与机械新鲜度门禁（2026-08-19，超长会话）

### Compose 弹层状态传递：新增入口复用既有面板时，契约遗漏点必须逐个入口核对，不能只核对"面板本身对不对"
- 现象：`AiSettingsScreen.kt` 的完整同意面板 `CloudAiConsentPanel` 设计契约是"面板出现前 `pendingKeyDraft` 一定是刚从 `KeyDialog` 输入框读到的新值"，这个契约在"首次填 Key→FULL_CONSENT"这条原始路径上成立。后来新增的"DECLINED 后点重新启用"入口直接 `consentPanelOpen=true` 复用同一面板和同一个 `grantConsent(vendor, pendingKeyDraft, ...)`，但**没有经过 `KeyDialog`**，没有满足契约前提——`pendingKeyDraft` 还是上次关闭时清空的空串，`grantConsent` 无条件把它写回密钥存储，等于把"重新启用"变成了"清空密钥"。这类 bug 不是新代码逻辑错，是**旧契约在新入口下不成立而没人核对**。
- 正解：给一个共享面板/共享函数新增调用入口时，不能只看"新入口的直接逻辑对不对"，要把该面板/函数原有的**输入契约**（"这个参数在被调用前必须处于什么状态"）摊开来，对新入口逐条核对是否满足；核对完还要问一句"这个契约违反后果多严重"——本例的后果是静默清空用户密钥，够得上纵深防御：`grantConsent` 本身也补了一行 `if key.isNotBlank()` 才算把这类问题在契约边界上根本堵死，不只是在调用点修一次。
- 通则：复审一个"新入口复用旧面板"型改动时，固定问两句——①旧面板/函数的隐含前提是什么？②新入口满足这个前提吗，不满足会造成多大后果？

### Compose 独立 Dialog 叠加时，"关闭内层"误写成"连外层一起关"是常见笔误，审查时专门 grep 一遍
- 现象：换厂商轻量确认框（`AlertDialog`）内嵌一个"看看发送哪些内容"链接，点击后打开只读披露面板（独立 `Dialog`，天然可以叠在 `AlertDialog` 之上）。误把 `vendorConfirmOpen = false` 也写进了这个链接的 `onClick`，导致点开披露面板的同时把外层确认框关掉了——用户点"知道了"回来才发现整个换厂商流程消失，只能从头重新填密钥。
- 正解：`Dialog`/`AlertDialog` 天然可以互相叠加（各自是独立 window），不需要"关掉一个才能开另一个"；打开子弹层的 `onClick` **只应该置子弹层的开关**，审查这类"弹层里嵌一个跳转到另一个弹层的链接"的代码时，专门 grep 一遍这个 `onClick` 块里有没有多写了外层状态。
- 通则：多层弹层设计的默认关系是"共存"，"必须先关外层才能开内层"是特例、需要显式设计理由，不是默认行为——写代码/审代码时反过来假设都容易出这类笔误。

### google_quality_engineer 复审揪出的"兄弟场景"值得认真处理，不要只修报告里点名的那一条
- 现象：真机反馈只报了 E-L1-03（重新启用丢密钥）和 E-L1-06（弹层误关），复审时顺手核对了"这两处 bug 所在的入口，还有没有相邻的同类入口"，发现"关闭并删除密钥→重新启用"这条路径会触发同一个契约缺陷的另一半——不是清空密钥，是给出"已启用云端 AI"的假成功提示（密钥其实是空的）。这个场景没人报告过，但触碰了项目"App 行为透明·诚实不操纵"的红线。
- 正解：真机 bug 修复的复审范围不应该止步于"报告里写的那条路径可复现且已修复"，应该顺带扫一遍"同一个根因还能从哪些别的入口触发"——本例只多花了一次审查就抓到了一个报告里完全没提、但同样是真实缺陷的场景。
- 通则：`google_quality_engineer`/独立复核类审查完成后，若发现的问题本身是"某个共享入口/共享函数契约缺陷"，审查产出应包含"这个根因还有没有别的触发路径"这一问，不能只回答报告里点名的那条。

### git mv 会自动暂存，后续单独 `git add <文件列表>` + `git commit` 会把 mv 的改动一起带进去——想分开提交必须显式核对
- 现象：一次大重构里先 `git mv 旧目录 新目录`（自动把 rename 计入暂存区），随后想把"另一批不相关的改动"单独提交，用 `git add <8个具体文件路径>` 只加了这 8 个文件，但因为暂存区里已经有 `git mv` 留下的 53 个 rename，`git commit`（不带路径参数）提交的是**整个暂存区**，不是刚 `git add` 的那几个文件——两批不相关的改动被混进了同一个commit，提交信息却只描述了其中一批。
- 正解：`git mv`/`git rm` 这类"顺手做了 stage"的命令一旦用过，后续任何一次 `git commit`（不带路径参数）之前，必须先 `git status --short` 看一眼暂存区**完整内容**是否等于"这次想提交的东西"，不能只确认"我刚 add 的文件在里面"就下断言。发现混入无关内容且尚未 push 时，`git reset --soft HEAD~1` 是安全的补救（不丢任何改动，只是把暂存区状态退回commit前，可以重新分批 `git add`+`git commit`）。
- 通则：想做"多个逻辑不相关的改动分开提交"，最稳妥的顺序是"先处理完全部会自动 stage 的操作（mv/rm等）→ 立刻 commit 掉这一批 → 再开始下一批的 add"，不要让"自动 stage 的操作"和"手动 add 的另一批"同时悬在暂存区里。

### 多轮独立子智能体评估：每一轮都可能推翻上一轮的方案，不是简单地"确认+补充"
- 现象：同一个"全景图新鲜度怎么长期保持"的问题，连续派了三轮独立 Opus 评估（互不看对方过程，只给结论/新事实作为输入）。第一轮建议加"复核至 sha"抑制字段缓解告警疲劳；第二轮基于更细的实测数据（信号精度提升后告警疲劳可能自然消失）认为第一轮的抑制字段"可能根本不需要"；第三轮发现用户想通用化的东西其实不是之前讨论的 Project Graph Phase 3（方向相反：Phase 3 是"Graph→视图"单向渲染，用户要的是"代码→反查功能"的反向路径），且深挖出项目里已经存在一套几乎重复的系统（project_graph）。每一轮都不是"确认上一轮"，是**用新证据实质性推翻或改写**上一轮的方案。
- 正解：多轮独立评估的价值恰恰在于"不预设上一轮是对的"——每次派新一轮时给的是"现状事实+上一轮结论"而不是"请你认可上一轮"，让新一轮有真正推翻的空间。汇总多轮结论时不能简单取"最后一轮说了算"也不能"历史结论平权叠加"，要看每一轮是不是拿到了前一轮没有的新证据（越新证据越多的判断优先级越高），且要老实告诉用户"这轮推翻了上一轮的哪个具体结论、依据是什么"，不能悄悄采纳新结论、假装从来没有过旧结论。
- 通则：用独立子智能体做多轮评估时，Prompt 要明确写"不需要认同上一轮，觉得不对直接推翻重提"，且每轮都要求它先做扎实的一手调研（读实际文件/跑实际统计）而非纯思辨，才能真正产出"用证据推翻"而非"换个说法重复"的结果。

### 发现项目里已有一套几乎重复的系统时，正确处置是"合一"，不是"分层共存"
- 现象：用户提出想把"全景图（projectReview）"往通用方向做，独立调查却发现项目里早就有一套 `project_graph/`（Phase 1/2 已完成、13个Feature/109个WorkItem的结构化系统）在做几乎同一件事——用户原话点破了真相："projectReview 和 project_graph 其实是一个，可能是当时讨论的 AI 又自主创建了一份"。第一版方案（由独立评估给出）想把 project_graph "降级为字典源"、projectReview 通过一个引用字段指向它——这种"两个目录+一条引用关系"表面上分了主次，实质仍然是两份真相源，仍有漂移空间（也正是当初"意外造出第二份"这个问题本身的翻版）。
- 正解：用户明确否决了"分层共存"方案，要求"只要一份真相源"——最终处置是把旧系统仅存的一项还有用的数据（一份路径映射表）**内联抄进新系统**，旧系统整体归档（`_archive/`，保留历史可查，但不再被任何工具/流程引用）。判断"要不要合一"的信号：如果两套系统的核心职责描述用大白话讲出来是同一句话，就该合一，不该找借口分层。
- 通则：设计新系统前，先花一次独立调查确认项目里没有历史遗留的同职责系统；如果发现了，默认策略是"合一+归档旧系统"，不是"新系统兜底、旧系统降级但保留"——降级保留最终大概率被证明是妥协出的技术债。

### 通用化提取时的"零默认值强制配置"设计，比"给一个看似合理的默认值"更可靠——已被真实数据验证
- 现象：把项目专属工具 `feature_sync_check.py` 抽成跨项目通用版时，"哪些文件算产品代码"这个判定原本在项目本地版里写死成本项目的目录结构；通用版改成必须通过 `--config` 显式声明，不给任何默认值，未配置直接报 `CONFIG-ERROR` 拒绝运行。用真实历史提交冒烟测试对比"项目本地写死版" vs "通用版+外部配置"，两者结果逐字节一致，但通用版的调用过程中意外验证了另一件事：如果给这类工具随手塞一个"看起来合理"的默认值，很容易在未来某个改动误配置或漏配置时被悄悄放过，而"拒绝运行"这个设计选择本身就是不允许这种悄悄放过发生。
- 正解：给跨项目/跨场景复用的工具设计"必须项目自己声明才能工作"的配置点时，**没有配置就报错拒绝**优于**给一个貌似通用的默认值**——后者会在配置遗漏时表现成"看起来在正常工作、实际上悄悄没做该做的检查"，比直接报错更难发现也更危险。这条原则本项目已经在 `blueprint_check.py`（`--test-dir` 无默认值）、`review_freshness.py`（`--anchors` 无默认值）上用过，`feature_sync_check.py` 是第三次验证，形成稳定模式。
- 通则：设计任何"跨项目通用工具"的必填配置项时，默认值只允许两种：①一个经过深思熟虑、几乎所有场景都适用的安全默认（如空列表/空集合，代表"什么都不做"）；②压根不给默认值、强制报错。绝不给"某个具体项目的真实值"当默认值，哪怕这个具体值看起来很有参考性——参考价值应该放进文档/注释里的示例，不该进代码的默认分支。

### 交付前的最后一次自我复核，仍然可能抓到真实 bug——"跑通了"不等于"设计对了"
- 现象：`feature_sync_check.py` 里"条目 ID 跨文件夹重复"检查的原始判据是"当前记录位置 ≠ 已记录位置就报重复"——这个判据在"同一个文件内部两次出现同一个 ID"这种情况下天然失效（两次的"当前位置"和"已记录位置"是同一个值，条件恒假）。脚本本身编译通过、`--struct` 全程跑绿，直到收尾前又检查了一遍源数据是否真的没有重复内容，才发现一条从原始待办文档搬运过来的真实重复项，回头才揪出这个判据 bug——如果没有这最后一次"不信任已经绿的结果、再核实一遍真实数据"，这个 bug 会一直悄悄潜伏。
- 正解：一段新写的、承担"机械核验"职责的代码，"它能跑、也给出了绿色结果"不等于"它的判据逻辑真的覆盖了它声称要覆盖的场景"——尤其是查重/去重类逻辑，容易在"两次判断用的是同一个变量"这类边界条件上出现恒真/恒假的判据。收尾前值得专门花一次"我知道大概率有真实数据可以验证这个检查"的复核，而不是看到绿色输出就停。
- 通则：写完任何"检查/校验/查重"类代码后，除了跑一次正常场景，主动想一个"这段代码本来就该抓到但我还没验证过"的已知可疑输入去喂一遍，比单纯看退出码是不是 0 更能抓到判据本身的逻辑漏洞。

### 角色分工：Opus 负责"决定/规划"，Sonnet 负责"把已决定的东西写成产物/执行"——把"整合已知决策进文档"这种执行工作错发给 Opus 是分工倒置
- 现象：用户已经就三项开放问题给出明确决策（含具体理由），下一步只是"把这三条决策实质性写进已有的方案文档、保持文档连贯"——这是纯执行工作（已知输入、已知结论，只是产出形式），却被当作"需要 Opus 规划"的任务派发出去，被用户当场纠正："我是想让 opus 去规划，你来执行，你搞反了"。
- 正解：判断一项工作该给"规划角色"还是"执行角色"，看**决策是否已经做完**——如果输入是"几个开放问题+需要新的判断/取舍"，是规划工作；如果输入是"已经拍板的具体决策+需要落成一份连贯的产物"，无论产物体积多大（哪怕要重写一份几百行的方案文档），都是执行工作，该由承担执行角色的一方直接做，不该因为"工作量大"就误判成"需要更强的规划能力"。
- 通则：接到"把这些已确定的点整合进文档/代码"类任务时，先确认这些点是不是真的已经确定（没有待决策的空白），确定了就直接自己动手，不要因为篇幅大或者涉及面广就下意识升级成"需要规划"再转发出去。

### 长会话临近上下文压缩前，主动把"下一步需要的关键理解"写成落盘文件，而不是依赖对话记忆
- 现象：一次覆盖极大量工作的超长会话（多轮独立评估+一次数千行规模的项目重构+紧接着的通用化提取）在推进到"通用化提取"这一步时，用户提醒"当前 context 快要压缩了"。此时对话历史里积累了大量中间过程（多轮评估的详细报告、多个脚本迭代的调试输出），真正对下一步有用的只是"最终结论"这一小部分。
- 正解：收到"要压缩了"的信号（或自己判断对话已经很长、即将进入自动压缩）时，第一步是把"接下来这一步任务需要的关键理解"（哪些是可以带走的通用引擎、哪些是必须排除的项目专属内容、目标落地到哪个文件）浓缩写成一份独立的落盘 manifest 文件，再继续做实际工作——文件在磁盘上不受对话压缩影响，即便后续对话历史被摘要化，也能直接读文件恢复到同等理解深度，不需要依赖"希望摘要没有漏掉关键点"的运气。
- 通则：识别到当前任务的"结论/决策部分"明显小于"推导过程部分"、且接下来还有大量后续工作要做时，主动做一次"结论蒸馏成文件"的动作，不用等到系统真正开始压缩才手忙脚乱。
