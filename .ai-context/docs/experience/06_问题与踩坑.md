## 推荐/菜系/自建菜打磨（2026-07-12）

- [2026-07-12] **自建菜不被库存推荐的根因=食材同名不同 id**：`createUserIngredient` 每次裸 INSERT 不去重，用户新建菜时又建同名食材(如"五花肉")→ 得到与预置食材不同的 id；库存推荐预筛按 `ingredient_id` 精确匹配 → 对不上、漏推该菜。修：①createUserIngredient 新建前按去空格名 `selectActiveIngredientIdByName` 复用已有 id(治本，复用时也补绑本次分类，INSERT OR REPLACE 幂等)②推荐 gather 按名扩展 pantryIds **和 shortageIds**(同名副本也算在手/不足，修存量脏数据)。教训：**凡按 id 匹配的地方，都要防"同名多 id"**；名扩展要成对做(在手 + 不足 一起扩，否则耗尽食材经副本被当充足推前无警示)。
- [2026-07-12] **data class 插入字段会打断"位置参数"调用方**：给 `PlanDish` 在中间插 `isMeat` 字段，测试里 `PlanDish(id, name, ..., avoid, breakfast)` 位置参数把 `breakfast` 错位映射到 `isMeat`，早餐逻辑静默失效、测试挂。改动 data class 字段顺序后，**全仓搜位置参数构造(尤其测试 helper)**，改用命名参数。
- [2026-07-12] **关键词判类别用裸单字会误伤同字异义**：判荤用裸"蟹"会把"蟹味菇"(食用菌)判成荤；"参/血/肚"同理。改用具体名(海参/鸭血/猪肚/田螺)。凡 `name.contains(单字)` 分类，先扫 seed 里有无"含该字的异义食材"。("鱼香茄子含鱼"经核实不误判，因只看主料名、味型不进主料)
- [2026-07-12] **推荐"换一换"分批**：旧 rotate 按平移 2 个 → 批次严重重叠。改按整批 N(=10)分页(rotation%批数, drop(start), 上层 take(N)): 下一批不重复、末批不足、全推完循环。≤1批时换一换回同批(符合"全推完再循环")。改分页语义后，旧"换一换必不同"的断言要按">N候选"重写。

## 库存份数 + 推荐可做性（2026-07-10 打磨）

- [2026-07-10] **库存"加1份没反应"**：结算式 `addServings`(份数=当前剩余+delta,重置窗口) 在**当天有餐用到该食材**时，重置后当天餐立即把新加的扣回→剩余仍旧、视觉无变化。修：`份数=当前剩余+delta+今日已占用`(补回重置窗口会再次扣减的今日餐)，既保留结算式对"历史欠账"的正确性，又保证"加N份→剩余可见+N"。派生库存模型的加减，务必推演"今天餐/历史餐"两种占用对可见值的影响。
- [2026-07-10] **"某食材只对应1道菜就不推荐"是误判**：库存推荐不显示某菜的真因是 `HealthRuleEngine` 判可做性要求**该菜全部非调料食材都在库存**(`nonSeasoning.all{在手}`)，缺一味辅料整菜被 `mapNotNull` 丢弃(如有五花肉却不推红烧肉)。放宽为**主料齐即可**(缺辅料记 missingNames 降权+标"还需采购")，无主料菜按非调料齐兜底。排查"推荐里没有某菜"先看可做性门槛，而非找不存在的数量阈值。
- [2026-07-10] **改可做性语义会连带改单测断言**：HealthRuleEngine 单测直接编码了"非调料齐才可做"，放宽后 2 个用例(缺辅料剔除)必然失败——语义变更时同步改测试断言(缺辅料→仍可做+missingNames，缺主料→剔除)，别只改实现。

## SQLDelight/JUnit/协程/跨设备合并（2026-07-10 选择性同步）

- **SQLDelight 单列 SELECT 返回列类型本身(List<String>/List<Long>)，不是行包装**：`SELECT d.name ...` 的 `executeAsList()` 是 `List<String>`，`.map{it.name}` 报"Unresolved reference: name / inferred Unit"。单列直接用，多列才生成数据类。[AI生成]
- **JUnit4 `@Test` 方法必须返回 void**：`fun x() = runBlocking { ... }` 若 block 末尾是**返回非 Unit 的断言**(如 `assertNotNull(v)` 返回 v)，则方法返回非 Unit → `InvalidTestClassError: should be void`。末尾补 `Unit` 或以 `assertEquals/assertTrue`(返回 Unit)收尾。[AI生成]
- **suspend 函数内的 local `fun` 不能调 suspend 函数**：需声明为 `suspend fun`(local)，否则"Suspension functions can be called only within coroutine body"。[AI生成]
- **跨设备合并按名匹配 + ID 重映射**：两设备自增 ID 不同，不能带 ID 直插。按自然键(name)匹配：命中复用其 id、缺则建，建"旧名→目标id"映射；依赖行(dish_ingredient/收藏/餐食)经映射重指。选某域**自动带依赖**(库存→食材, 收藏/餐食→菜品+食材)保证引用完整。整库=替换、选择性=合并。接收端**自动识别包类型**(zip 里有无 `data.json`/`cookbook.db`)避免改传输协议。[AI生成]
- **AlertDialog 里同向嵌套 verticalScroll 会互相冲突**(内层滚不动/底部被遮)：只在**一层**加滚动(通常外层弹框内容 Column)，内层去掉。[AI生成]

## 库存/占用类需求的建模方法论（2026-07-10）

- **"分配/占用/额度/余额"类需求优先做「派生态」而非「存储扣减」**：库存份数体系最终采用**不落库、实时按时间序算**。存储扣减会遇到：加回时不知该先补谁、编辑/删餐重复扣、触发时机难定。派生只需 `份数(用户改) + 餐食记录` 实时算，天然支持"加份数早的先恢复"。[AI生成]
- **派生占用要设「时间窗口」，否则历史会污染当前**：纯派生若把**所有历史餐**都算作占用当前库存，会出现"两年前用过还占今天份数"的荒谬。解法=**入库日窗口**：每食材记 `added_at`(持久化)，只算 `date >= added_at` 的餐。[AI生成]
- **余额型字段用「结算式」更新，避免累加+窗口重置的重复计入**：`serving_count` 累加(+delta)但窗口重置到now → 为0后重加会把已消耗的重复算进剩余。正确=加时先算当前剩余、再 `serving_count = 当前剩余 + delta` 并重置窗口(`activatePantry`)。[AI生成]
- **同类"状态标注"要覆盖所有展示入口，别只加一处**：缺料/采购最初只加在周期规划预览，餐食卡片(首页计划/食历)没有→用户以为没生效。应在**统一的数据组装点**(如 `MealRecordRepository` 组卡)算好，所有复用同一卡片组件的地方一并生效。[AI生成]
- **派生态天生"覆盖存量数据"**：因不落库、查询时实时算，新增此类功能后**现有历史数据自动被评估**，无需"创建新记录才生效"。回答用户"存量能否覆盖"时可据此确认。[AI生成]

## 库存份数 / SQLDelight方言 / 代码审核修复（2026-07-10）

- **SQLite 3.18 方言不支持 UPSERT**：`INSERT ... ON CONFLICT(col) DO UPDATE` 报 `',' expected, got 'ON'`(SQLDelight dialect `sqlite_3_18`，UPSERT 是 3.24+)。累加/幂等 upsert 改**两步**：`INSERT OR IGNORE ...`(靠 unique index 忽略重复) + `UPDATE ... SET x = x + :delta`，放**同一事务**(`db.transaction{}`)保证原子。[AI生成]
- **新迁移文件命名 = 当前最大 `N.sqm` + 1，别被"版本号"误导**：`N.sqm` 迁移 vN→vN+1。现有到 `12.sqm` → 当前 `Schema.version=13` → 新迁移文件是 **`13.sqm`**(不是 14)。看目录里最大序号 +1 命名，命名错会漏迁移/版本错乱。加列同时改 `.sq` 的 `CREATE TABLE` + 建 `N.sqm ALTER`(新列 ALTER ADD 安全)。[AI生成]
- **派生态 > 存储式扣减**（当需求含"撤销/按时间序恢复/重算"时）：库存"占用/不足"若真去改库存数字(存储扣减)，加份数时无法知道该先补哪个、且整日编辑会重复扣。改为**不落库、实时按序算**(份数只用户改；占用=遍历所有餐食菜品按 date→meal_time→created_at→sort_order 排队，rank>份数即不足)，加份数后自动重算天然"早的先恢复"。凡"分配/额度/占用"类需求先想能否派生。[AI生成]
- **DB 恢复必须原子(带回滚)**：`copyTo(currentDb, overwrite)` 覆盖主库后若后续步骤失败，原库已丢、新库不完整。覆盖前把现有库存到 staging 回滚区，覆盖失败即还原。恢复关的是**单例 driver**，close 后无热重建 → 恢复后需重启应用(UI 提示/或强制重启)。[AI生成]
- **Java 阻塞 socket 的 `accept()`/`read()` 协程 `cancel()` 无法中断**：靠 `close()` socket 抛异常解阻塞(cancel 只设标志)。持有 socket 引用供 reset/onCleared 关闭；读要设 `SO_TIMEOUT`(掉线未发 FIN 会永久阻塞)；区分"主动取消"与"真实异常"(用 volatile 标志)，否则真实错误被静默吞。[AI生成]
- **KMP：可测纯逻辑放 `shared/commonMain` 不放 androidApp**：androidApp 无测试源集→纯逻辑(协议编解码/阈值判定/分配算法)零覆盖。下沉 shared 后纳入 `:shared:testDebugUnitTest`，平台只留系统采集/UI。[AI生成]
- **Kotlin `if(x) a++; b++` 分号内联易被误改**：`?.let { if(c) a++; b++ }` 两句都在 lambda 内(当前对)，但后人若移出/删判空语义静默变。统计类逻辑用显式花括号。[AI生成]

## AI 云端接入 / 联网的坑（2026-07-09）

## 编辑页空白要区分路由 id 与数据加载失败

[2026-06-04]

## 改 .sq 表结构必须同步加 .sqm 迁移（否则旧库升级缺列，真机才暴露）

[2026-07-06]
- 给 `ingredient` 加 `reason` 列时只改了 `Cookbook.sq`（进入 `Schema.create`），**漏了对应 `N.sqm` 迁移文件**。结果：全新安装正常（建表带列），旧库升级后缺列，凡读写 `reason` 的查询报 `no such column: reason`（已失效列表、菜品读食材 `selectIngredientsOfDish`、软删写 reason 全挂）。[AI生成]
- **单元测试用 `RepositoryTestDatabase.create()` = `Schema.create(driver)`，直接建最新结构、不走迁移链**，所以测试全过而真机升级失败。改 schema 的改动，光靠现有单测无法发现缺迁移。[AI生成]
- 规则：**任何 `.sq` 表结构变更（加列/改列/建表）必须同时新增 `N.sqm` 迁移**；`Schema.version` 由迁移文件数决定（`gradle` 里的 `version=8` 是无效残留属性）。[AI生成]
- 补救幂等补列（本次采用）：在 `DatabaseDriverFactory.android.createDriver()` 建驱动后 `runCatching { driver.execute(null, "ALTER TABLE ... ADD COLUMN ...", 0) }`，列已存在时忽略 duplicate column。适合"schema 已含列但部分旧库缺列且版本号已被占用"的补救；正常演进仍应走 `.sqm`。[AI生成]
- 建议：长期可开启 SQLDelight `verifyMigrations`，让"schema 与迁移不一致"在构建期暴露，而不是等真机。[AI生成]
- **[2026-07-06 已证实·阶段0结论]** SQLDelight 2.0.1 的 database 块**没有 `version` 属性**；`Cookbook.sq` 的运行时 `Schema.version` **由 `*.sqm` 迁移文件数自动推导**（1~N.sqm ⇒ version=N+1）。旧代码 `create("CookbookDatabase"){ version = 8 }` 里的 `version` 泄漏成了 **Gradle 项目版本**（`Project.version`），与 DB 毫无关系——是"版本号"误解的根因，已删除。判断真实 DB 版本**只看生成的 `CookbookDatabaseImpl.Schema.version`**，别信 build.gradle。[AI生成]
- **[2026-07-06 已证实]** reason 列修复正解（在"重装/无历史旧库"前提下）：补 `10.sqm`（`ALTER TABLE ingredient ADD COLUMN reason ...`）让迁移链重建结果与 `Schema.create` 一致（version 自动升 11），随后**删除** `DatabaseDriverFactory.android.ensureLegacyColumns` 幂等补列（消除驱动侧重复 DDL）。⚠️ 若线上已有"该列已进 Schema.create 的旧库"，普通 ALTER 迁移会对已有列的库崩（duplicate column），此时才保留幂等驱动补列；本项目因重装无此约束。[AI生成]
- **[2026-07-07 实际踩中·教训]** 上条的"删除驱动补列"决策在真机翻车：用户设备旧库是 v10-已含 reason，升级跑 `10.sqm` 的普通 ALTER → `duplicate column: reason` → 迁移失败 → "初始化数据失败"。单测走 `Schema.create` 不跑迁移，永远测不出这类**迁移专属**失败。**正解**：把 `10.sqm` 改为无操作占位（`CREATE TABLE IF NOT EXISTS _noop; DROP TABLE IF EXISTS _noop;`，勿删文件否则版本空洞），reason 由 `Schema.create`(新装) + 恢复的 `ensureLegacyColumns` 幂等补列(旧库) 共同保证。**教训：改动只影响迁移路径时，务必单独推演"设备各历史版本升级"矩阵，别被单测全绿误导；"假设都重装"是危险前提。**[AI生成]
- 迁移空迁移占位别用 `SELECT 1;`：Android `execute()` 对 SELECT 的处理有歧义，用「建了即删的临时表」这类确定性 DDL 更稳。[AI生成]
