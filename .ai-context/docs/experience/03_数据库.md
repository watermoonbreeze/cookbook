## 启动 seed 性能：内容指纹守卫 + 单事务

[2026-07-06]
- 补齐式 seed（每次启动 upsert 全部预设食材/分类/详情/调养）**无守卫 + 无事务**时，每条独立 fsync，随数据量增长（食材 87→153、规则 15→163）启动明显变慢。[AI生成]
- 方案：各 seed JSON 算"长度+hashCode"内容指纹存 `PreferenceKeys.SEED_CONTENT_FINGERPRINT`，内容未变整段跳过、零写入；需写入时整套包一个 `db.transaction`，上千次 fsync 降为一次提交。[AI生成]
- 旧库一次性清洗（NULL 修正）用 `SEED_LEGACY_SANITIZED` 标记守卫，不再每次全表 UPDATE。[AI生成]
- 坑：写 seed 元数据 key 后 `user_preferences` 非空，会让 `count==0` 守卫漏写用户默认偏好；守卫应按具体 key（如 `THEME_MODE` 是否存在）判断。[AI生成]
- 手动"更新基础数据"= 忽略指纹强制重跑幂等 upsert（`forceReseedBaseData`），**只刷新不删除**，用户数据与引用不受影响；预留后续从后台拉数据包。[AI生成]

## 数据库设计演进

### [2026-05-14] 从 MVP 简单方案到完整食材-菜品-食谱体系

MVP 原方案仅有 5 张表（dish、meal、meal_dish、favorite_combo、favorite_combo_dish），经三轮讨论细化为完整方案。

**完整方案核心表（详见 `.ai-context/docs/feature/数据库设计方案.md`）**：

#### 字典/基础表
- `cooking_method` — 烹饪方式（炒、蒸、煮...）
- `crowd_type` — 人群分类（高血压、糖尿病...），一期
- `measurement_unit` — 计量单位（克、两、个...）

#### 食材体系
- `ingredient` — 食材表（name UNIQUE），含别名用于搜索
- `food_category` — 食物分类（支持多维度 dimension + 层级 parent_id），一期
- `ingredient_category` — 食材-分类多对多关联，一期
- `nutrient` — 营养素定义，一期
- `ingredient_nutrient` — 食材营养素含量（每100g），一期
- `crowd_ingredient` — 人群-食材禁忌（recommend/limit/avoid 三级），一期

#### 菜品体系
- `dish` — 菜品表，**name 允许重复**，通过标签区分同名菜品
- `dish_tag` — 标签表（"少盐版"、"妈妈做法"等）
- `dish_tag_rel` — 菜品-标签多对多关联
- `dish_ingredient` — 配料表，菜品与食材的关联（含用量、单位、主料/辅料）
- `dish_crowd` — 菜品适应人群，一期

#### 每餐记录
- `meal_type` — 餐序类型，6 个固定（早餐/上午餐/中餐/下午餐/晚餐/宵夜）+ 用户加餐
- `meal_record` — 每餐记录（date + meal_type_id + meal_time）
- `meal_record_dish` — 每餐-菜品关联

#### 收藏组合
- `favorite_combo` + `favorite_combo_dish`

## 关键设计决策

### [2026-05-30] 菜品支持多个烹饪方式

- 原 `dish.cooking_method_id` 只能保存一个烹饪方式，无法满足“新建/编辑菜品可添加多个烹饪方式”。
- 新增 `dish_cooking_method_rel(dish_id, cooking_method_id)` 多对多关联表。
- `dish.cooking_method_id` 暂时保留，用作旧数据兼容和首个烹饪方式缓存。
- Repository 读取时优先取关联表；如果关联表为空，再回退到 `dish.cooking_method_id`。
- 保存时先按名称确保 `cooking_method` 字典存在，再全量重建关联表。

### [2026-05-30] 预设食材允许编辑但不能删除

- 修复9后，`ingredient` 的编辑不再限制 `source='user'`，预设和自建食材都可改名称/别名/图片。
- 删除仍限制 `source='user'`，且删除前先清理 `dish_ingredient` 关联。
- 权限要同时体现在 UI、ViewModel 和 SQL 层，不能只靠界面隐藏按钮。

### [2026-06-03] 菜品/食材缩略图字段

- `dish` 和 `ingredient` 均新增 `thumbnail_path TEXT NOT NULL DEFAULT ''`。[AI生成]
- `image_path` 保存原图路径，`thumbnail_path` 保存缩略图路径；多图时仍使用 `|` 分隔，并按索引对应。[AI生成]
- SQLDelight 目标版本升级到 v3，迁移文件 `2.sqm` 负责 v2 -> v3 添加字段。[AI生成]
- 列表、卡片、封面优先读取 `thumbnail_path`，详情预览再加载 `image_path`，减少滚动解码成本。[AI生成]

### [2026-06-03] Android 数据库文件外置

- Android 端数据库统一打开 `/sdcard/cookbook/db/cookbook.db`，不再 fallback 到 app 专属外部目录。[AI修改]
- `MainActivity` 必须先拿到外部存储权限，授权后创建公共 `db/img` 目录，再加载数据库和 HomeScreen。[AI生成]
- 如果旧 app 专属外部目录存在 `Android/data/<package>/files/cookbook`，授权后先复制迁移到 `/sdcard/cookbook`；目标已有文件不覆盖。[AI生成]
- 迁移时也会从旧内部数据库路径复制主库和 `-wal`、`-shm` sidecar 文件；目标库已存在时不覆盖，避免误删用户数据。[AI修改]

### [2026-06-14] 烹饪计时模板持久化边界

- 厨房小助手的倒计时只持久化“模板配置”：名称、总时长、备注、铃声 URI、铃声名称、展示顺序。[AI生成]
- 运行态、暂停态、完成告警态、剩余秒数和正在播放的 `Ringtone` 都属于页面临时状态，不写数据库，避免重进页面后恢复出半运行状态。[AI生成]
- 展示顺序使用 `sort_order, id` 稳定排序，不跟随运行/暂停/完成状态变化；计时类列表如果按状态重排，会在倒计时过程中产生列表跳动，实际体验差。[AI生成]
- 新增此类工具型配置表也要完整走 SQLDelight 流程：schema 加表、迁移文件升版本、Repository 封装、单元测试、迁移验证和数据库设计文档同步。[AI生成]

### [2026-05-14] 菜品重名 + 标签区分

- `dish.name` 允许重复，不做 UNIQUE 约束
- 通过 `dish_tag` + `dish_tag_rel` 标签体系区分同名菜品
- "菜名 + 标签组合"在**业务层**保证唯一
- 新增菜品时如有同名，弹框展示已有菜品信息供用户选择（复用/基于已有修改/全新创建）

### [2026-05-14] 餐序以时间排序

- `meal_type.default_time`（HH:mm 格式）替代数字排序
- 预设时间：早餐 07:30、上午餐 10:00、中餐 12:00、下午餐 15:00、晚餐 18:30、宵夜 21:30
- `meal_record.meal_time` 存储实际用餐时间，固定餐序取 default_time，加餐由用户选择
- 查询按 `meal_time` 排序，HH:mm 字符串字典序 = 时间序，零额外逻辑
- 用户可在设置中修改固定餐序的 default_time
- 去掉了 `UNIQUE(date, meal_type)` 约束，固定餐序唯一性在业务层控制

### [2026-05-14] source 字段统一规范

- 所有需区分来源的表加 `source` 字段：`preset`（预设）/ `user`（用户添加）
- 用户只能编辑/删除 source='user' 的数据
- APP 升级时可安全更新 preset 数据，不影响用户数据

### [2026-05-14] 分阶段建表策略

- **MVP**：全部表结构建好，但 UI 只暴露必要字段（菜名必填，配料/烹饪方式可选填）
- **一期**：激活 crowd_type、food_category、nutrient 等健康维度的表和 UI
