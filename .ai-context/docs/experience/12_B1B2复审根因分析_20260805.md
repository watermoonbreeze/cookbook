# B1/B2 复审根因分析

> 日期：2026-08-05 · 复审触发：Codex 架构复审发现 AF-01~05 共 5 项阻断问题

## 一、问题总表

| ID | 问题 | 直接原因 | 深层根因 |
|----|------|---------|---------|
| AF-01 | 流式不是真正逐帧 | streamOnce 累积全部 SSE 后发一个 Delta | 流式编程模式不熟；实现时未对照"Delta=每帧独立"的合同 |
| AF-02 | 取消与不重试未生效 | hasAnyContent 在 streamOnce 返回后才赋值 | 状态跟踪点选错位置；未考虑"读取中已收内容再失败"场景 |

| AF-05 | 同键合并不完整 | dish 整节点替换而非字段合并；ingredient 未去重 | 只处理了"新增"场景，忽略了"合并/去重"的规范要求 |

## 二、核心根因

### 2.1 验收纪律缺失（最严重）

任务规范给出了显式的分批验收矩阵（B1-B6）+ 编号测试用例（T-01~T-12），但实现完成后**凭"感觉都覆盖了"判断通过**，没有逐条拉出验收框架核对。

**GLOBAL.md 已新增「自带验收框架的任务」规则（2026-08-05），实施模型必须逐项验收并报告证据。**

### 2.2 "宽容性默认"vs"严格契约"的思维偏差

归属校验（AF-03）中，非法 slot 被当作 warning 而非 error——这是因为默认偏向"尽量让更多数据通过"。但协议明确要求精确匹配，非法值必须拒绝。**当规范说"必须匹配/拒绝"时，不要自作主张降级为 warning。**

### 2.3 新增路径走旧代码

整体 JSON fallback（AF-04）是新协议的回退路径，实现时直接调用了旧 `FlatToDayMealConverter`——因为它"刚好能工作"。但这跳过了新归属校验链和 segment_id 映射。**新增路径的所有分支必须走同一校验入口。**

### 2.4 流式编程模式不熟悉

AF-01/AF-02 的根因是对 `callbackFlow`/协程取消/`SendChannel` 生命周期不够熟悉。具体：
- `callbackFlow` 中 `withContext(IO)` 内调用 `send()` 会 flout context；应该 launch IO job 后用 channel 引用发送
- `awaitClose {}` 用来清理被取消的 IO，不能替代 `close()` 来结束流程
- `hasAnyContent` 必须在收到内容时即时标记，不能在函数返回后才赋值

## 三、如何预防

| 措施 | 具体做法 |
|------|---------|
| **验收框架驱动** | 实施前把验收矩阵拉出来；每完成一项标记状态+证据；不入下一批 |
| **协议/合同思维** | 规范中的"必须/禁止/拒绝"= 硬编码阻断，不降级为 warning |
| **新路径走新校验** | 任何新增分支必须先经过本次改造的校验入口；不要复用"刚好能工作"的旧路径 |
| **流式生命周期检查清单** | 写 `callbackFlow`/`channelFlow` 时检查：①逐帧 send ②close() 结束 ③awaitClose 清理 ④取消断开连接 |
| **状态标记即时性** | 任何"是否已收到XX"的标志必须在收到那一刻标记，不能在回调/函数返回后 |
