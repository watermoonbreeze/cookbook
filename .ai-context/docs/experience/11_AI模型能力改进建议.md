## R1 — 注释驱动验证（头注释≠实现）

**规则**：函数头注释里声称"做了 X"，必须立即 grep 确认代码里有 X 的实际调用点。

**背景**：`DayAutoGenerator.commit()` 头注释写了「eaten_ratio 回填」，但代码里从未调用 `mealRepo.setEatenRatio()`。平移代码时注释被复制，功能被漏写，且注释掩盖了缺失。

**检查方式**：
```
头注释提到 → grep 对应方法名 → 确认在本函数体内有调用
```

## R2 — 测试内存 DB 必须共享单实例

**规则**：同一测试类里，`RepositoryTestDatabase.create()` 只调一次，所有 ctx/repo/generator 基于同一个 `db`。

**背景**：原 `IngredientAutoGeneratorTest` 中 `createContext()` 建 DB-A，`createGenerator()` 建空 DB-B，T07 还建了 DB-C。`commit()` 写进 DB-B，ctx 在 DB-A 里推演，两库毫无关联。commit 断言恒绿但没测到任何真实路径，`source="auto"` / `ref="自动估算"` 等核心不变量无法被发现。

**标准写法**：
```kotlin
@BeforeTest
fun setUp() = runBlocking {
    db = RepositoryTestDatabase.create()   // ← 唯一一次
    // 在同一个 db 上种入数据
    ctx = AutoGenContext.load(db, aliasResolver)
    generator = IngredientAutoGenerator(IngredientRepository(db), NutritionRepository(db))
}
```

## R3 — 条件语义先分清再用 `||` 合并

**规则**：用 `||` 合并两个条件前，先确认两个条件表达的是同一语义类别，不能把"未归类"和"是调料"混在一起。

**背景**：`IngredientAutoGenerator.kt` 里 `isSeasoning = nameKey in ctx.seasoningNames || group == null`。`group == null` 表示 FoodGroup 无法识别的生僻食材（如"藜麦""魔芋丝"），被误判为调料，给 3g 默认克数，营养估算严重低估。

**正确判断**：
```kotlin
// 调料 = 在调味品/油脂类分类下的食材（DB 驱动）
val isSeasoning = nameKey in ctx.seasoningNames
// group == null = 生僻食材，分类未命中，默认 100g
```

## R4 — 两阶段 API：用 preview 携带派生数据，commit 之后读它

**规则**：两阶段 `preview/commit` 的核心价值之一是 **preview 作为数据携带者**——凡是 commit 完后需要用到"preview 阶段算出来的数据"（如实际解析出的各天日期），都应先 capture preview，再 commit，再从 preview 里读。

**背景**：`MultiDayRecorder.recordAll()` 直接调 `dayGen.commit()`，commit 内部每天的实际日期已经算出但没暴露；外层只能用 `today` 当所有天的日期，`MultiDayRecordResult.days` 全部 `date=today`。

**正确顺序**：
```kotlin
val autoGenPreview = dayGen.preview(semanticDays, today, ctx)   // ← 先 capture
val result = dayGen.commit(preview = autoGenPreview, ...)        // ← 再 commit
val savedDays = autoGenPreview.days                              // ← 从 preview 里读派生数据
```

## R5 — 统计计数与缓存副作用解耦

**规则**：计数逻辑不能嵌在 `getOrPut`/`?.let`/`firstOrNull` 等有副作用的路径里，命中缓存时 lambda 不执行，统计就会漏计。

**背景**：`DayAutoGenerator.commit()` 里 `dishIdCache.getOrPut(dish.inputName) { /* 建菜 + 计数 */ }` 命中缓存时 lambda 不执行，同名菜跨餐次第二次出现既不计 reused 也不计 created，统计偏低。

**解耦写法**：
```kotlin
val alreadyCached = dish.inputName in dishIdCache       // ← 先判缓存命中
val dishId = dishIdCache.getOrPut(dish.inputName) { … } // ← 再执行缓存/创建
// 独立统计（不依赖 lambda 是否执行）
if (dish.resolution == ResolveKind.REUSE || alreadyCached) reused++
else if (dishId > 0) created++
```

## 速查表（给下一个 AI 的 checklist）

在平移/新写代码后，自检以下几项：

- [ ] 头注释声称的功能 → grep 确认调用点存在
- [ ] 新建测试类 → 全部操作基于同一个 `db` 实例
- [ ] 用 `||` 合并条件 → 两个条件语义同类才合并
- [ ] 调用 `commit()` 后需要知道"commit 处理了哪些数据" → 先 capture preview 对象
- [ ] 在 `getOrPut/let/firstOrNull` 里写计数 → 把计数挪到外层独立执行
