## 二、新增：`pantry` 库存表（决策=独立表，记数量/时间）

```sql
-- [AI生成] 我家食材(库存)：从预设/自定义食材加入，作家庭食材库。独立表以支持数量/时间/临期预留。
CREATE TABLE pantry (
    id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    ingredient_id INTEGER NOT NULL REFERENCES ingredient(id) ON DELETE CASCADE,
    quantity REAL,                              -- 数量(可空=只标记在手)
    unit_id INTEGER REFERENCES measurement_unit(id),
    added_at INTEGER NOT NULL,                  -- 入库时间
    expire_at INTEGER,                          -- 保质期/临期(预留"临期提醒")
    note TEXT NOT NULL DEFAULT '',
    status INTEGER NOT NULL DEFAULT 1           -- 0=已移出/用完，1=在手
);
CREATE UNIQUE INDEX uq_pantry_ingredient ON pantry(ingredient_id);
```

- **库存 Tab** = `SELECT ingredient.* FROM pantry JOIN ingredient WHERE pantry.status=1`，平铺无子分类。
- **加入库存**：详情`[+加入库存]` / 库存 Tab 底部`[+从食材库添加]`多选 / `[+新建食材入库]`。
- **移出库存**：`pantry.status=0`（不删记录，留复购历史）。
- **详情/做法区标记（chatlog 470）**：查某菜品配料时，`ingredient_id IN (SELECT ingredient_id FROM pantry WHERE status=1)` → 标"家里有"。

## 三、DB 版本对齐（阶段 0，最优先修）

**现状矛盾（已实测）**：
- `build.gradle` `version = 8`，但迁移文件已排到 `9.sqm`；`.sqm` 注释与文件名**错位一位**（`7.sqm`→v8、`8.sqm`→v9、`9.sqm`→v10）。
- `ingredient.reason` 改了 `.sq` 却漏建迁移，旧库升级缺列，只能靠 `DatabaseDriverFactory.android.kt` 里 `ALTER TABLE ... ADD COLUMN reason` 幂等补——**临时手段，非正道**。

**修正动作**：
1. 把 `build.gradle` `version` 补正到与最后一个迁移一致的**真实版本**（现有 1–9.sqm ⇒ 目标 schema v10 → `version = 10`）。
2. 为漏掉的 `reason` 列**补一个正式迁移**（`ALTER TABLE ingredient ADD COLUMN reason ...`），随后**移除驱动侧临时 `ALTER`**。
3. 之后所有 `.sq` 表结构变更**必须同步 `.sqm`**（工程红线，已沉淀 experience `06_问题与踩坑`）。

## 四、迁移排号（本方案新增，接在 v10 之后）

| 文件 | 版本 | 内容 |
|------|------|------|
| `10.sqm` | v10→v11 | 补漏的 `ingredient.reason`（对齐现有 schema，替代驱动补列） |
| `11.sqm` | v11→v12 | `CREATE TABLE pantry` + 索引 |
| `12.sqm` | v12→v13 | 营养/季节维度节点若需结构调整时用（多数走 seed 数据，无需迁移） |

> 幂等原则：所有 `.sqm` 用 `CREATE TABLE IF NOT EXISTS` / 先查列再 `ALTER`，兼容"驱动已临时补过列"的旧库。每加一个迁移文件，`build.gradle` `version` 同步 +1，并跑 `:shared:testDebugUnitTest` 验证。

## 五、全局搜索查询（chatlog 488-492）

需求：**全库搜索**（不限当前 Tab）、按字符**包含**匹配、结果下拉、点结果**跳到其所属分类**。

- 复用现有 `SearchIngredients`（generated 已存在），确认为**全表** `WHERE (name LIKE '%'||:q||'%' OR alias LIKE '%'||:q||'%' OR pinyin LIKE '%'||:q||'%') AND status=1`，按匹配度/最近使用排序。
- 结果项点击 → 返回该食材 + 其主品类 `category_id`（查 `ingredient_category` 取 general 维度首个）→ UI 切到「常规」Tab 并展开定位。
- 搜索框样式：无边框、色块、高度 48dp（chatlog 194，与菜品/搜索页统一）。

## 六、软失效与引用不断裂（已落地，明确契约）

- 删除食材 = `UPDATE ingredient SET status=0, reason=?`；**菜品引用照旧**（`dish_ingredient` 不动），列表/详情灰显。
- 预设食材下架 = seed JSON `status:0`+`reason`，补齐式导入同步。
- 回收站 = `selectInactiveUserIngredients`（source=user AND status=0），可恢复(status=1)/彻底删除(物理 DELETE)。
- 删除提示文案：软失效语义，**不用"移除"**（chatlog 452，已改）。

## 七、维度归属与 seed（承接明细①②）

- 常规品类：食材 seed 的 `categories` 里带 general 维度 code（如 `veg_leaf`）。
- 营养/季节：同一食材 `categories` 追加 nutrition/季节维度 code（如 `gi_low`、`season_spring`），Tab 过滤 dimension 即得聚合视图。
- 调养：写 `ingredient_care_rule`（病种 category + advice_level + reason），不占 `ingredient_category`。
- 字段级规范一律遵守 `食材数据规范.md`（code 不可复用、name 不可改）。
