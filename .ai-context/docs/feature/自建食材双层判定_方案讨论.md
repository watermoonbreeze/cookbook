# 自建食材能否适用「数值+属性双层」判定 · 方案讨论

> [AI生成] 2026-07-22 用户提议讨论：数值+属性双层 + 属性标签体系是否适用于**用户自建食材**。本文=现状+缺口+方案选项+权衡+推荐，供讨论定方向（未实现）。

## 一、现状（自建食材已支持的比想象多）
用户建食材（`createUserIngredient` / IngredientEditor）**已有**：
- **营养大类必选**（FoodGroup）→ 分类/色系/均衡统计基础
- **营养数值录入**（`IngredientNutrition` 每100g·可选·折叠区）→ 数值层判定的输入
- **智能推演营养**（`NutritionGuesser`·按名三级兜底：近似同名→大类均值→不填·标来源·可撤）→ 用户不填也有保守估值
- **care 规则手动编辑**（`careRules`·调养建议区）→ 用户可手动配忌口

**→ 数值层已适用**：用户填营养 / 智能推演 → `IngredientCrowdCare.evaluate` 自动判级（食材详情红绿灯、忌口都生效，与预设食材同一条链路）。

## 二、缺口（属性层缺"智能"·全靠用户手动想）
属性层（`FoodAttribute`/`FoodAttributeCare`）目前只在 **seed 给预设食材** 打标签。自建食材要享属性层，只能**用户手动加 care 规则**——但：
- 普通用户不懂"啤酒嘌呤低但酒精升尿酸→痛风避免"这类机制，**想不到、易漏**（自酿米酒/自制含糖饮料填了营养但嘌呤低→纯数值判可食→漏判，正是双层要防的）
- 手动配 care 负担高、违反"少操作"

**核心问题 = 如何让自建食材低负担地自动获得属性层判定。**

## 三、方案选项
### L1 · 最小（现状）
自建食材只走数值层（填营养）+ 保留手动 care。简单，但属性盲区漏判（自酿酒/自制甜饮）。

### L2 · 智能推断 + 通俗确认（**推荐**·复用 NutritionGuesser 范式）
建 **`AttributeGuesser`**（照 `NutritionGuesser` 三级兜底范式）：自建食材按**名称关键词 + 营养大类**推断可能的 `FoodAttribute`：
- 名含 酒/白酒/啤酒/米酒/黄酒 → `CONTAINS_ALCOHOL`
- 名含 可乐/雪碧/汽水/奶茶/果汁 或（大类=饮料 且 高糖）→ `PROCESSED_FRUCTOSE`
- 大类=内脏 或 名含 肝/腰/脑 → `ORGAN_HIGH_CHOLESTEROL`
- 名含 植脂末/奶精/起酥/油炸/炸 → `TRANS_FAT`

推断命中 → **通俗提示 + 用户确认**（复用营养推演的"预填·可撤·标来源"UX）：
> "这看起来是**含酒精**的，会对痛风家人提示避免。保留吗？ [保留 / 去掉]"

用户确认 → 属性 → 展开 care（`source='user'`）→ 双层判定生效。
- **优点**：低负担（只在命中时提示、确认非输入）、享双层、透明可控、与营养推演体验一致
- **符合准则**：智能默认值 + 透明（T2 告知可控）+ 少操作 + 诚实不操纵

### L3 · L2 + 通俗属性勾选（增强）
在 care 编辑区加一排**通俗属性标签勾选**（"含酒精 / 含糖甜饮 / 动物内脏 / 油炸 / 腌制加工"），用户可主动补/改推断没覆盖的。属性标签体系对用户显性化。

## 四、权衡（讨论点）
| 维度 | 考量 |
|---|---|
| **准确性** | 关键词推断会漏/误判（"酒酿圆子"含酒但量小、"苹果醋"非酒）→ **用户确认兜底 + 保守**（拿不准不推，宁漏不误·避免过度忌口误导） |
| **负担 vs 价值** | 多一步确认违"少操作"，但仅命中时提示（多数食材无属性、不打扰）、且是确认非录入（低负担）；换来自建食材也防漏判 |
| **健康红线** | App 推断忌口=T2 自动行为（改判定须告知+可控）→ 通俗提示+可去掉满足透明；守"仅供参考·非医嘱" |
| **数值 vs 属性** | 两层都要：用户填的营养走数值层，属性推断补数值盲区（酒精/果糖）；一致取更严 |
| **存储** | 推断属性**直接生成 `source='user'` 的 care 规则**存 care 表（复用现有表/链路·无需给 ingredient 加 attributes 列/迁移）；食材详情/判定自动用 |
| **软删/编辑** | 自建食材编辑改名→重新推断（提示确认）；user care 随食材软删（现有机制） |

## 五、推荐
**L2（智能推断+通俗确认）为主**，复用 `NutritionGuesser` 成熟范式与 UX，低成本、低负担、守红线；**L3 通俗勾选**作为增强项按需加。
- 落地点：`AttributeGuesser`（shared·纯函数可单测）+ IngredientEditor 加"属性推断提示"（复用 onGuess 范式）+ 确认后写 user care。
- **判定口径红线照旧**：`AttributeGuesser` 的关键词→属性→care 映射也须联网核实指南口径、保守（见脚本方案三-B）。
