# 自建食材营养数值「自动获取」规划（少输入·三来源）

> [AI生成] 2026-07-22 用户提议：自建食材用户常不知道营养数值，应能少输入、自动算出来。呼应旧待办"我的·联网校验自建食材"。
> 现在已有体系（`NutritionGuesser` 本地推演 + nlc/USDA 联网抓取 + 属性标签体系）→ 整合成"营养自动获取"。本文=规划，供讨论/排期。

## 一、目标
自建食材营养数值尽量**自动填**、用户只需确认，减少"要用户查嘌呤/GI"的不合理负担；与「数值+属性双层」结合，营养(数值层)+属性(属性层)一起自动化。

## 二、三种来源（用户视角）
| 来源 | 适用 | 技术 | 现状 |
|---|---|---|---|
| **1 手动输入** | 兜底/用户想改 | 现有营养录入区 | ✅ 已有 |
| **2 扫描包装营养表（OCR）** | 加工食品（GB 28050 强制标注营养表） | 拍照→OCR→解析每100g→预填 | ⏳ 待做 |
| **3 联网按名查权威库** | 常见食材（成分表有的） | nlc（中国·已逆向 foodName 接口）/ USDA（进口·全库本地匹配） | ⏳ 待做（接口已通） |
| **0 本地按名推演** | 所有（瞬时兜底） | `NutritionGuesser`（近似同名→大类均值） | ✅ 已有 |

## 三、智能分层策略（组合·最省输入）
用户建食材填**名字**后，自动按成本从低到高尝试，每步**预填 + 可撤 + 标来源**（复用 `NutritionGuesser` 现有 UX）：
1. **本地推演**（瞬时·无网·零成本）：`NutritionGuesser` 近似同名命中→直接预填（标"按名估算·可改"）。
2. **联网精确**（用户触发·按需·省 token）：本地没精确命中时，给「🔍 联网查准确营养」按钮 → nlc 按名搜 / USDA → 命中则用权威值覆盖预填（标"来自《中国食物成分表》/USDA·可改"）。**不静默联网**（守透明+权限）。
3. **扫描营养表**（加工食品）：给「📷 扫描营养成分表」入口 → OCR 识别 → 解析每100g → 预填（标"来自包装营养表·可改"）。
4. **手动**：以上都不满意 → 用户改任意字段（`editedN` 已保证推演不覆盖用户手改）。

## 四、与「双层判定」结合（营养 + 属性一起自动）
填名后，**并行**：
- 营养 → 上述三来源（数值层）
- 属性 → `AttributeGuesser` 按名/分类推断属性标签（属性层·见 `自建食材双层判定_方案讨论.md` L2）
→ 一次填名，数值层 + 属性层双双自动预填、用户确认即可，自建食材享完整双层判定。

## 五、技术要点与红线
- **联网权限**：本地优先 App **默认无 `INTERNET`**（踩坑红线）→ 加联网查前须声明 `INTERNET`；缺则 HTTP 静默失败。
- **不静默联网**：联网获取=T2/T3 透明级（联网+取数据）→ **用户主动触发**（按钮），不后台偷偷联网；标来源、可改。
- **OCR**：端侧优先（ML Kit/离线·隐私好·无 token）；营养表格式较固定（项目+每100g/份+NRV%），正则/规则解析；注意"每份 vs 每100g"换算、NRV 干扰。
- **省 token**：联网走**脚本化接口**（nlc foodName / USDA 本地库·见 `数据获取脚本化方案.md`），非 LLM 逐条；App 端直接 HTTP 调 nlc 接口即可（已逆向）。
- **数据诚实**：自动获取的值标来源 + review（权威库=较可信、推演=粗略估算）；守健康免责"仅供参考"。查不到不编造。
- **判定口径**：属性推断映射须联网核实指南（脚本方案三-B）。

## 六、分期建议
- **P1（高性价比·接口已通）**：联网按名查营养——App 端调 nlc `foodName` 接口（+USDA 兜底），命中预填、标来源、用户触发。**先声明 INTERNET**。同时接 `AttributeGuesser` 属性推断（L2）。
- **P2**：扫描包装营养表 OCR（加工食品主力·端侧 OCR）。
- **P3**：三来源统一到食材编辑的"智能填充"入口，体验打磨（一键智能填、来源角标、冲突时用户选）。
