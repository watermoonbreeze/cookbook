## 一、背景与用户洞察
- 初诉求：AI 推荐周计划"营养素色条下方列当前计划天数的营养素曲线图" + "一周营养搭配/一周合计"文案适配不同天数。

## 二、四方会商核心共识（多方独立趋同·信号强）
1. **曲线归饮食报告**（真实摄入=趋势主场）——UX/产品/算法一致。落点=报告"营养摄入卡"内部子区（非独立新卡）。
2. **周计划不做趋势曲线**——UX+产品明确反对：①计划态是预估未吃，连成"趋势线"诱导把计划当既成事实、制造达标焦虑；②与 line30"整周结构覆盖/缺口"**功能重叠且折线形态更差**（覆盖是"够不够全"、该用点亮/缺口清单，不是趋势）。⚠️**此点与用户原始想法冲突，见第四节拍板**。
3. **反考核·避焦虑硬红线**（全体一致）：**无目标线/达标带、无纵轴刻度数字、全程无红**（高值浅琥珀不报警）；主语对准食物不对准人；禁"达标/不够/下降/偏高偏低"；语气锚「**帮你了解，不替你打分**」。
4. **热量不做曲线主轴**（算法+UX+产品一致）：热量受 `CALORIE_NUMBER_ENABLED`(默认关)、做主轴会让图空掉且踩个人概念红线；主轴用**恒显**的量（宏量克数 / 均衡度）。
5. **个人视角专属**：曲线按成员 share 折算(同今日卡口径)；家庭视角不做曲线(多人汇总趋势语义混)。
6. **断线示"没记"**：空天不连线不画点(不把没记的天脑补成 0 暴跌)。

## 五、通用数据层与接口（算法·拍板 A/B 后即可实施）
- **通用接口**(shared domain·两端中立)：`NutritionTrendPoint(label, kcal?, proteinG?, fatG?, carbG?, isEmpty, partial)`。热量不耦合开关(数据带着·UI 按开关决定显不显)；`isEmpty`=空天断点、`partial`=有摄入但缺营养数据。
- **报告聚合器最小扩展**：`NutritionTotals` 加 `operator times(f)`；`DietReport` 加 `perDayNutrition: List<NutritionTotals?>?`(个人视角非空·家庭 null·长度=periodDays·空天 null)；`aggregate()` 在现有逐日循环里**顺手收进 List**(标量 sum/均值口径一行不改·防漂移)。
- **月周期**：逐日照画(31 点折线不密)，只做 x 轴标签自适应(隔 N 标一个/标周界)；**不做周聚合**(会掩盖记录稀疏)。
- **防漂移单测**：逐日序列聚合回均值 ≈ `personal.avgKcal`(钉死两套口径一致)。
- 周计划(若拍板做)：`dailyMacro → NutritionTrendPoint` 近直接映射(补空天)·数据现成。
- **工作量**：数据/算法侧约 1.2~1.7 人日(不含曲线 Composable 绘制)。

## 六、文案（copywriter·守免责/避焦虑）
- **天数通用化**：标题「这份计划的营养搭配」/合计「整套合计」/覆盖「这几天安排了 X」/空态「还没排菜\n排上几天，就能看看这几天搭得均不均衡」。

- **图例**：蛋白/脂肪/碳水/热量(热量线受开关·关则连图例隐)。
