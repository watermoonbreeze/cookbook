## 一、首页现状与落点

### 1.1 现状信息架构（自上而下）
1. LargeTopAppBar「今天吃什么」+ 搜索/主题图标
2. **AI 推荐入口卡**（白卡 + 🤖 + "用你现有的食材，帮你搭配今天吃什么" + chevron → 跳 `AiRecommendScreen`）
3. 营养色系墙（仅开关开启时）+ 今日营养卡（仅开热量数值时）
4. **今日**区（今日卡 / 空态"随手记一餐"）
5. **计划**区（一周计划入口 + 下一个有安排的日期卡 / 空态）

关键判断：现状 AI 推荐是**一张"入口卡"——只承诺、不兑现**，用户必须点进全页才知道推荐什么。这正是 §5.2「打开即见」缺口：价值没在打开时兑现。

### 1.2 落点决策：把"入口卡"升级为"下一餐推荐卡"（就地兑现）
将现有 AI 推荐入口卡**原地升级**为展示 2–3 道具体菜的"下一餐推荐卡"，放在**今日区之上、色系墙之下**（若色系墙关则紧跟顶栏第一屏）。理由：
- **打开即见**：不点任何东西就看到"下一餐建议吃这几道菜"，一屏内兑现。
- **不新增层级**：替换而非叠加，首页 item 数量不增反聚合，守克制。
- **心智连续**：卡内"换一批 / 看更多"仍下钻到现有 `AiRecommendScreen`（同一引擎、同一心智），首页只做"轻量预览版"。

优先级：**下一餐推荐卡 > 今日卡 > 计划**。色系墙/今日营养卡是"回顾"性质，语义上应在推荐卡之后（推荐=向前看，色系=向后看）。

## 二、下一餐推荐卡：结构与密度

### 2.1 卡片结构（ASCII mockup）
```
┌───────────────────────────────────────────────┐  ← InsetGroup 白卡, 16dp 圆角
│  下一餐 · 晚餐                        换一批 ↻   │  ← 卡头 16/12dp
│  下面几道，挑顺手的记一下                          │  ← 副标题 bodySmall, onSurfaceVariant
│                                                 │
│  番茄炒蛋                              [ 记 ]   │  ← 菜行 dish row, 56dp 高
│  ⭐你常做 · 🥗补今日营养                          │  ← note 一行, bodySmall 省略号截断
│  ─────────────────────────────────────────────  │  ← Divider(非HorizontalDivider,1.1.2)
│  清炒时蔬                              [ 记 ]   │
│  🥗补今日营养 · 已避开五花肉                        │
│  ─────────────────────────────────────────────  │
│  紫菜蛋花汤                             [ 记 ]   │
│  ⭐你常做                                        │
│                                                 │
│                        看更多推荐 ›              │  ← 底部 CTA → AiRecommendScreen
└───────────────────────────────────────────────┘
```

### 2.2 展示密度
- **固定 3 道菜**（默认）：一餐"一荤一素一汤/主食"的家庭直觉；`fallback` 已按荤素+主食组合，3 道刚好体现搭配；再多首页臃肿。→ D2。
- 每道菜**只显一行 note**（省略号截断），不展开所有 buildNote 字段。
- 卡片总高约 320–360dp，第一屏可见完整卡 + 今日区标题露头。

### 2.3 点一道菜的默认动作
菜行**整行可点 = 打开菜品详情**（复用 `onOpenDish(id)`）。行尾**独立「记」按钮 = 直接记进"下一餐"餐次**（一键记一餐）。
- 点详情="确认再决定"，点「记」="信你直接记"——两类都照顾，「记」是转化目标动作必须一键可达。
- 「记」落点：日期=今天、餐次=按钟点判定的"下一餐"，预置该菜进 `AddMeal` 页（不静默写库，给确认/加菜机会），保存后回首页 Snackbar「已记入晚餐」。→ D3/D4。

### 2.4 "换一批 / 看更多"
- **卡头「换一批 ↻」**：就地刷新 3 道（`rotation++` 轮转下一批不重复），不跳页，加载转 skeleton。
- **底部「看更多推荐 ›」**：跳 `AiRecommendScreen`（携当前餐次预选），进全页看 10 道候选、切风格/餐次/去重周期、批量勾选、负反馈踩等重能力。**首页不放重控件**。

## 三、推荐依据的轻量呈现（信任但不啰嗦）

复用 `AiRecommendViewModel.buildNote()` 理由片段，首页做减法：每道菜 note **最多显 2 个理由**，优先级（家庭+慢病定位）：

| 优先级 | 片段 | 复用来源 | 首页文案（温和口径） |
|---|---|---|---|
| 1 | 忌口已避开 | 引擎 `selectable` 已剔除忌口 | 不显性写病名；仅当"避开常吃主料"才正向提"已避开五花肉" |
| 2 | ⭐你常做 | `c.frequent` | 「常做」 |
| 3 | 🥗补今日营养 | `c.complementary` | 「补今日营养」 |
| 4 | 宜吃食材 | `c.recommendHits` | 「宜吃 山药」（仅有登记健康档案时） |

**红线**：
- 首页**绝不显性标病名**，只正向表述"已避开 XX / 补今日营养 / 你常做"。病名视角留今日营养卡 concerns（个人视角带免责）。
- 忌口菜在首页推荐卡**根本不出现**（`selectable` 已剔除）——首页是"建议吃"，忌口标红教育职能留全页。
- 不出现"降压/达标/治疗"断言；卡底一行浅色免责「按你的记录与健康档案生成 · 仅供参考」。→ D5。

## 四、餐次判定："下一餐"是早/中/晚

复用 `AddMealViewModel.pickDefaultMealType`（`DateTime.currentHour()` → 最接近 `defaultTime` 的固定餐次）映射到引擎 `MealSlot`：

| 当前钟点 | 下一餐 | MealSlot |
|---|---|---|
| 04:00–09:59 | 早餐 | BREAKFAST |
| 10:00–13:59 | 中餐 | LUNCH |
| 14:00–19:59 | 晚餐 | DINNER |
| 20:00–03:59 | 明日早餐 | BREAKFAST（标"明天 · 早餐"） |

引擎已支持 `gather(mealSlot=...)` + `DishMini.mealSlots`，首页传判定出的 slot 即可。

非当前餐次：首页卡**默认只展示"下一餐"一个餐次**，不放切换控件（守克制）。想看别餐次→点「看更多推荐」进全页（已有 §9.21 餐次二级横滚栏）。→ D6（备选：餐次标题做可点 chip 循环切，倾向不做）。

## 五、零录入 aha 与降级链（§5.1 关键）

**核心**：首页推荐卡**任何状态下都不空**——价值不锁在"先干活才给看"后面。

| 场景 | 数据条件 | 引擎行为 | 首页卡呈现 |
|---|---|---|---|
| A 老用户 | 有历史+库存 | 偏好画像+营养互补+忌口，MODEL/规则 | 正常 3 道 + 理由 note |
| B 有档案无历史 | 配了健康档案、无记录 | RANDOM 全库候选+忌口过滤+营养互补 | 3 道，note 侧重"补今日营养/宜吃"，无"常做" |
| C 全新用户 | 无历史无库存无档案 | RANDOM 全库 → `fallback` 组合级荤素搭配 | 3 道**预设菜示例**，卡头标「示例 · 记录后更懂你」 |

**C（全新用户）关键交互**：
- `pantryIds` 空时 RANDOM 取全库 `selectAllIngredientIds`，`fallback` 保证荤素搭配不空——**技术上零录入即可出 3 道**，无需新数据。
- 卡头加**「示例」浅色标签**（§9.4 角标）+ 副标题「先看看今天可以吃什么，记一顿后会更懂你的口味」——诚实标注（守 §5.1）。
- 卡底 CTA 换「记第一餐 · 试试看」，把 aha 引向第一次价值动作。→ D7（推荐**要**：§5.1 明确要求且零成本）。

## 六、"历史菜单 vs 营养规划"两依据的融合

现引擎**已把两者融合进单一打分**，无需用户在首页取舍：
- **历史/习惯**：`preferenceScores`（记录 8 次饱和+收藏）、`tasteProfile`（近 90 天菜系/做法/主料偏好）、`mainRepeatCounts`（近期主料去重）。
- **营养规划**：`nutritionBalanceScores`（补今日缺口宏量）、`recommendHits/limitHits`（档案宜吃/限量）、`conditions`+`giByName`（慢病软约束）。
- **权重**由 `RecommendationStyle`（综合/偏熟悉/偏新鲜/偏营养）调节。

**结论：产品层够用，首页不需新增"按习惯/按营养"开关**（两依据已在一个分数里平衡，多开关增负担违背克制）。想偏向某侧→全页"推荐风格"选择，首页继承其粘性选择。→ D8（唯一可加：一句"综合你常做的菜和今天营养搭配"说明依据，不加控件）。

## 七、刷新与打扰边界（守 §5.4 红名单）

| 时机 | 是否刷新 | 说明 |
|---|---|---|
| 进入首页（首次） | 是 | 打开即见，一次 `gather`+推荐 |
| 返回首页/切后台回前台 | **否** | 对齐全页"移除 refreshOnResume"（用户 2026-07-18），避免每次回来菜就变 |
| 点「换一批」 | 是 | 用户主动 `rotation++` |
| 记完一餐回首页 | **仅刷新餐次判定** | 刚记完晚餐、钟点已过→下一餐自动变"明日早餐"重取；否则不动 |
| 跨餐次时段 | 下次进页面按新钟点重判 | 不做后台定时刷新 |

**绝不做**：推荐卡红点、"3 道菜等你记"角标、每日推送催记录、"今天还没采纳推荐"提示。推荐卡是**安静的建议**，不理它毫无负担。

## 十一、v2 收敛：轻量单菜引流卡（2026-07-19 用户反馈 → 会商 → 拍板）

> v1（3 道菜 + 逐行「记」+ 换一批 + 看更多）落地后用户实用反馈：①逐行「记」只能记一道、不实用（想"勾选把生成的都记成一餐"）②卡"感觉重了"③标题"下一餐·明天·早餐"与已有周期计划**歧义**。用户重定位：**这卡=引流入口**（让用户知道有自动推荐 + 首屏尝甜头 + 真帮到用户，**不做重功能**）。

### 11.1 会商（apple_operations_designer + apple_ux_designer 双视角）
- **一致**：定位=橱窗样品/引流入口；标题弃"下一餐·明天·早餐"排班硬承诺改**疑问/邀请式**；守免责/忌口红线/示例态诚实/不催不打扰；下钻 CTA 升级为利益驱动。
- **分歧**：①密度=单菜 vs 3 道减重 ②首页要不要记=纯引流(进全页记) vs 勾选批量记在首页。两视角各自呼应用户矛盾的两句原话。

### 11.2 用户拍板（2026-07-19）：**轻量单菜·纯引流**（运营方案）
- 只推 **1 道**菜 + **一句人话理由**（非标签罗列）。
- 首页**不做记/详情**（记一餐的批量能力全留 AI 推荐全页），**整卡点击 = 进 AI 推荐全页**（全页按钟点自判餐次 + 已有勾选批量记范式）。
- 保留一个本地 **「换一道」**（轮播已算好的候选·零成本）。
- 标题**疑问式**："X吃点什么"（X=早餐/中餐/晚餐/明早）；示例态="今天可以吃什么"。去掉"下一餐/明天"——一句话天然兼容"已有计划/没计划"两种人，不检测计划状态（省复杂度·更克制）。

### 11.3 落地实现（已编码·BUILD SUCCESSFUL）
