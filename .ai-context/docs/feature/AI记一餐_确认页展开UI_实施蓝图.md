## §5 移交 `apple_ux_designer` 的功能性需求与约束清单

> **这是本蓝图当前唯一完整交付的设计产出**，不是待补的空缺。UX 设计师应基于此产出具体的交互/视觉规范，规范产出后由架构模型回填进本蓝图 §6/§7/§8。

### 5.1 功能性需求

在确认页每道 CREATE 菜的条目上，新增一个"明细展开区"，用于展示该菜即将写入库的完整信息（食材清单、烹饪方式、菜系、标签、做法步骤），让用户在确认前看清楚"这道菜到底会带什么信息进库"。

### 5.2 硬约束清单（9 条，交互设计不得违反）

1. **展开区位置**：放在 `DishNutritionLine`（营养行）之后，作为该菜条目的最后一块——营养行是慢病 App 的第一优先信息，必须紧贴菜名，展开/收起动作不得改变营养行的垂直位置。
2. **默认状态**：收起。确认页的首要任务是"快速核对菜名/份量/新建数量"，一屏内看完是核心体验；多道菜默认全展开会把主 CTA（"确认记下"）推出首屏。
3. **展开粒度**：逐道菜独立展开/收起，不是整卡片级或整页级。
4. **入口显示条件**：仅 `dishPreview.resolution == ResolveKind.CREATE` 且以下至少一项非空时才显示展开入口——`ingredients`/`cookingMethods`/`steps`/`tags`（`cuisine` 单独非空不足以触发入口，因为一个"菜系"标签单独展示价值有限，需配合其他内容）；内容全空时不显示入口（不能让用户点开看到空白）。
5. **REUSE 菜不展示任何展开入口**（对应 INV-C-02）——REUSE 菜的确认语义是"沿用库里已有的这道菜，不改它一个字"，若展开显示 AI 本次解析出的食材/做法，会让用户误以为这些内容会被写入，而 REUSE 路径下这些内容全部会被丢弃，展示哪一份都是错的。若产品未来希望支持"查看已有菜资料"，正确做法是提供跳转菜品详情页的链接，而非在确认页内展开——这个"要不要加跳转"由 UX 设计师自行判断是否纳入本批，不强制。
6. **估算值诚实标记**：食材克数/营养值来自估算（`DishAutoGenerator` 的 `anyGuessed` 逻辑已标记营养为估算），展示这些内容时需要有"估算"标记，沿用确认页已有的"营养为自动估算，仅供参考"文案口径，不新造一套说法。
7. **PARTIAL_READY 期间稳定性**：确认页在流式生成期间会持续增量重建列表，新菜/新餐次可能插入到已渲染列表的中间位置（非仅追加到末尾）。展开态必须绑定稳定业务 key（候选：`"${day.date}|${meal.mealTypeCode}|${dishPreview.inputName}"`，见 §2 D4），不能用"渲染位置/下标"隐式记忆——否则用户展开了 A 菜，列表重排后展开态会跳到 B 菜上。内容本身也可能增量变化（steps 从 0 条变 3 条），展开区高度变化不得引起页面滚动位置跳变。
8. **纵向空间预算**：确认页底部有"确认记下"主按钮，展开后不得把它推出首屏之外（或需要 UX 设计 sticky/其他方案兜底）。
9. **多天/多菜场景的信息密度上限**：周期记一次最多可能出现 7 天 × 3 餐 × 3~5 菜 ≈ 100 个菜条目，展开区的信息密度设计必须考虑这个数量级上界（不能是"每条都很占地方"的设计，否则长列表体验会劣化）。

### 5.3 待 UX 设计师补充判断的开放问题（非约束，供参考）

- 是否需要"全部展开/全部收起"的批量操作入口（多天场景下逐条点展开可能繁琐）？
- `cuisine` 单独展示的视觉形式（小标签/文字前缀/图标）？
- 展开动效是否需要（考虑到 PARTIAL_READY 期间已有内容持续刷新，过多动效可能造成视觉噪音）？
