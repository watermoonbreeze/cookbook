## 三、其余深挖点（排优先级·多为待方案/待拍板）

### 🟡 中优先（可做，部分需口径确认）
1. **多病种叠加只 `minOf` 取最严、无优先级**：两病种都命中时不分轻重。可定义病种权重/优先级，但"哪个更重"需营养口径确认——**待拍板**，别自行定医学优先级。
2. **GI/纤维覆盖 63-65%**：季节/地方菜缺 gi → 糖尿病维度对这些菜不触发。同饱脂法可补（GI 有 FAO/WHO 口径）。
3. **嘌呤单字泛词风险**（"肝"/"胰"）：新增含此字的非高嘌呤食材会误判。加 seed 引用完整性校验时顺带扫"含肝/胰但非内脏"的反例，或改 `NAME_OVERRIDE` 白名单。

### 🟠 需先出方案（大改/涉 schema/涉产品）
4. **患者实测指标（血糖/血脂/血压/尿酸）**：现按"登记病种"通用阈值，无个性化。可预留 `family_member.lab_values`（偏好 JSON 免迁移）承载可选指标→个性化阈值。**属新能力·先方案**。
5. **member_care 无 enabled 软禁用**：现删即禁用、重开需重选。加 `enabled` 列（涉 `.sqm` 迁移）支持"暂停某病种档案"。**涉 schema·先确认**。
6. **库存×病种断层**：推荐考虑 avoid 但库存食材未按病种强提示"含你需避免的"。属推荐/库存交叉产品设计。
7. **慢病软约束权重是否上调**：现高GI/高嘌呤罚分 0.42（远小于 avoid=5），"含高GI但非直接忌口"的菜仍靠前——是否让其对糖尿病/痛风成员更难推出，**产品取舍待拍板**（家庭 app 定位：列出告知 vs 替用户过滤）。

### 🟢 架构健康（择机）
8. **病种名 3 处分散**（`crowd_type.name` 旧/`food_category.name`/`HealthCondition.fromCareName` 枚举）：新增/改名需同步 3 处。可收敛单一真值源（food_category 为准）。
