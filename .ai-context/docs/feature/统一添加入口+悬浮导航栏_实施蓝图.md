## 4. 已验证的现有代码事实

### 4.1 AI Body（单天AI + 周期AI）本来就是一个 ViewModel

`AiMealInputViewModel`（`androidApp/.../ui/ai/AiMealInputViewModel.kt`）的 `AiMealInputUiState`（约102-159行）已经把"快速记草稿"和"周期记草稿"存成**两个独立字段**，同属一个 State：

```kotlin
data class AiMealInputUiState(
    val inputMode: InputMode = InputMode.QUICK,   // 只是"当前显示哪个"的选择器
    val phase: AiMealPhase = AiMealPhase.INPUT,    // 全局阶段机，不分 quick/period
    val quickDraftText: String = "",               // 单天AI草稿，切 inputMode 不清空
    val periodInputs: Map<Int, String> = emptyMap(), // 周期AI草稿(0..6=周一..周日)，切 inputMode 不清空
    ...
)
```

`setInputMode(mode)` 只是切换 `inputMode` 显示哪块 UI，两个草稿字段互不影响（代码注释原文："B4: 快速记草稿（切换模式保留）"）。

**结论**：统一入口的 `SINGLE_DAY+AI` 和 `PERIOD+AI` 两格，**必须复用同一个 `AiMealInputViewModel` 实例**，Range 在 AI 方式下的切换 = 调用 `vm.setInputMode(InputMode.QUICK / InputMode.PERIOD)`，**不是**创建两个 VM 实例、不是原文档说的 "singleAiState / periodAiState 两份独立 Draft"。这个 VM 已经天然满足"草稿互不清空"的要求，不用额外开发状态隔离逻辑。

### 4.2 AI Body 的 `phase` 是全局的，不区分 quick/period

`AiMealInputSheet` 顶层按 `state.phase` 分发（`AiMealInputSheet.kt:174-192`）：`INPUT → GENERATING/PARTIAL_READY → PREVIEW_READY → SAVING → DONE`，`ERROR` 单独分支。**Range/Method 切换控件（当前的"快速记/周期记" SegmentedControl）只在 `InputPhase` 里渲染**（`AiMealInputSheet.kt:198` 起的 `InputPhase` 函数内部）——一旦进入 `GENERATING`，没有回到"选择模式"的 UI 路径。

现有代码已经处理了"生成中/预览中想关闭 Sheet"的场景：`AiMealInputSheet.kt:141-161`，`showDismissConfirm` 弹窗 + `vm.cancelGeneration()`，触发条件是 `state.phase in [PARTIAL_READY, PREVIEW_READY]`（`onDismissRequest` 里，`SAVING` 时忽略关闭）。

**结论**：见第 6 节，统一页面的 Range/Method 切换器需要复用这一套"生成中/预览中切换=需要确认放弃"的既有逻辑，不能像原文档假设的那样"任何时候切换都无条件保留、不弹确认"。

### 4.3 单天手动（`AddMealViewModel`）已有现成的 Dirty 概念

`AddDayFoodScreen.kt:157` 用 `koinViewModel()` 拿 `AddMealViewModel`；`AddDayFoodScreen.kt:191-192`：

```kotlin
val requestBack = com.sxdbsm.cookbook.android.ui.component.rememberUnsavedGuard(

```

**结论**：`SINGLE_DAY+MANUAL` 格的 Dirty 判断直接复用 `vm.isDirty()`，现成的，不用新写。

### 4.4 `rememberUnsavedGuard` 内部自带 `BackHandler`，只能在页面里调用一次

`UnsavedGuard.kt:27-34`：

```kotlin

    isDirty: () -> Boolean,
    onConfirmLeave: () -> Unit,
    dialogText: String = "你的改动还没保存，返回将丢失。",
```

**结论**：每个原 Screen（`AddDayFoodScreen`/`WeekPlanScreen`）目前各自调用一次。**抽取出的 Body Content 组件（`SingleManualContent` 等）必须去掉这个调用**，改由 `UnifiedAddMealScreen` 顶层统一调用一次（否则多个 `BackHandler` 同时注册，物理返回键行为不可预测）。原有的 `AddDayFoodScreen`（保留给"编辑某天"等直达入口用）继续保留自己的调用不受影响——这是两个不同的组合位置，互不冲突。

### 4.5 `PERIOD+MANUAL`（`WeekPlanScreen`/`WeekPlanViewModel`）没有"草稿"概念

`WeekPlanScreen.kt` 通读下来（全文159行）：删除走软删+撤销 Snackbar（`vm.deleteDayUndoable`），复制/编辑都是**跳转到别的页面**（`onEditMealDate`/`onCopyMeal`），本页自身**不持有任何未保存的表单状态**——它是一个"整周已保存数据的实时视图"，没有 `isDirty()` 这回事。

**结论**：原文档"四个 Body 各自有 Dirty"的说法里，`periodManualDirty` 在当前架构下**恒为 `false`**，不需要也没有对应的状态字段。Unified 页面的总 Dirty 判断实际上是三路，不是四路：

```kotlin
val hasUnsavedChanges =
    (aiVm.state.value.let { it.phase != AiMealPhase.INPUT || it.quickDraftText.isNotBlank() || it.periodInputs.values.any(String::isNotBlank) }) ||
    singleManualVm.isDirty()
    // periodManual（WeekPlanScreen）无 Dirty 概念，不参与判断
```

## 5. 修正后的产品/状态模型

用真实持有点替换原文档 §10-11 的"四个独立 Draft"假设：

```text
UnifiedAddMeal 页面持有：
├── aiVm: AiMealInputViewModel          （复用现有类，一个实例，服务 SINGLE_DAY+AI 与 PERIOD+AI 两格）
├── singleManualVm: AddMealViewModel    （复用现有类，服务 SINGLE_DAY+MANUAL）
└── periodManual: 直接复用 WeekPlanScreen 现有 Composable 树/ViewModel（服务 PERIOD+MANUAL，无独立草稿）

UI State（页面壳，新写）：
data class UnifiedAddMealUiState(
    val range: MealRange = MealRange.SINGLE_DAY,
    val method: MealInputMethod = MealInputMethod.AI,
)
```

Range/Method 切换事件的真实映射：

| 事件 | 目标格 | 真实动作 |
|---|---|---|
| `range=SINGLE_DAY, method=AI` | 单天AI | `aiVm.setInputMode(InputMode.QUICK)` |
| `range=PERIOD, method=AI` | 周期AI | `aiVm.setInputMode(InputMode.PERIOD)` |
| `range=SINGLE_DAY, method=MANUAL` | 单天手动 | 渲染 `SingleManualContent(singleManualVm)`，不动 `aiVm` |
| `range=PERIOD, method=MANUAL` | 周期手动 | 渲染 `PeriodManualContent`（即 WeekPlanScreen 内容），不动 `aiVm`/`singleManualVm` |

`method=MANUAL` 时 `aiVm` 只是"不显示"，不需要销毁或暂停，它的 `state` 该是什么就是什么，天然保留。反过来同理。这就是"切换不丢草稿"的正确实现方式——**靠"不销毁 VM 实例"天然做到，不需要原文档说的额外 Draft 快照/恢复机制**。

## 6. Range/Method 切换的真实约束（原文档没考虑到，本节新增）

原文档 §7/§8/§21/§22 假设"任何时候切换 Range/Method 都无条件保留状态、不弹确认"。这对 `MANUAL` 方向成立（`AddMealViewModel`/`WeekPlanScreen` 没有"生成中"这种异步阶段），但对 `AI` 方向不完全成立：

- **`aiVm.state.phase == INPUT` 时**：可以自由切换 Range（`QUICK⇄PERIOD`）和 Method（切到 MANUAL），无需确认，草稿保留——这条和原文档一致。
- **`aiVm.state.phase != INPUT`**（即 `GENERATING`/`PARTIAL_READY`/`PREVIEW_READY`/`SAVING`）**时**：这是一个正在进行的异步解析/保存流程，不能假装"切走了它还在后台安静等着"。处理方式：
  - `SAVING` 阶段：禁止切换（复用现有 `onDismissRequest` 里 "SAVING 中忽略关闭" 的既有逻辑，Range/Method 选择器在此阶段置灰不可点）。
  - `GENERATING`/`PARTIAL_READY`/`PREVIEW_READY` 阶段：允许切换，但要弹与现有 `showDismissConfirm`（`AiMealInputSheet.kt:141-160`）语义一致的确认框（"AI 已解析的餐食预览将不会被保存"），确认后调用 `vm.cancelGeneration()` 再执行切换；取消则停留原状态。
  - 这不是"新增一套确认语义"（违反原文档禁止事项"不新增另一套确认语义"的精神），是**复用 Sheet 迁到全屏页之后，`showDismissConfirm` 原本挂在"关闭 Sheet"上的那套逻辑，现在同时挂到"切走 Range/Method"这个新触发点上**——同一套对话框、同一个 `cancelGeneration()` 调用，只是触发条件从"关 Sheet"扩展到"关 Sheet 或切模式"。

`method=MANUAL` 方向和 `range` 在 `MANUAL` 下的切换，维持原文档"无条件不确认"结论不变（`AddMealViewModel`/`WeekPlanScreen` 没有异步生成态）。
