# 推荐/关联查询 性能复杂度与热点地图

> [AI生成] 2026-07-18 夜 无人值守·`algorithm_engineer`(基础算法镜头)会诊产出。**预防式性能**：到阈值再优化，本文件是地图+埋点+优化清单。与 `性能优化DB索引.md`(索引层·已完成)、`工程优化待办.md`(写路径)正交，此处专攻**推荐读路径的全表/全窗口聚合缓存化**。

## 一、结论
推荐单次 `gather` ≈18–22 条 SQL，**全批量、无逐项 N+1**（历史两处 N+1：候选逐菜 getDishById≈500 查、buildDishMini 逐菜——均已消除，代码注释可查）。evaluate/MMR 纯内存 O(候选×配料)、候选≤100 非瓶颈。**结构健康**，痛点集中在少数"全表/全窗口聚合"随数据量线性放大——**加索引解决不了(v24 反查索引已齐)，只能靠缓存/物化**。

## 二、痛点排序（按数据量增长）
- 🔴**#1 口味画像 3 查**(`selectCookedCuisineFreqSince/MethodFreqSince/MainFreqSince`)：风格开 tasteProfile>0(综合/偏熟悉等常用风格默认开)即触发，扫近 90 天全部餐食×配料 GROUP BY。**随餐食记录量 M 线性增长、每次推荐必跑**——最普遍最先痛。
- 🔴**#2 `giByName`**(`selectAllIngredientNutrition`)：糖尿病成员触发，O(I) 全食材营养全表，随食材库扩充变慢。**结果与候选无关、跨请求近乎不变，却每次重查+重建 map**——典型可缓存却没缓存。
- 🟡**#3 `findDishesByIngredients`(候选预筛)**：`DISH_PREFILTER_LIMIT=100` 封顶输出但不封顶计算(JOIN dish_ingredient GROUP BY HAVING)，随菜品量 D 增长。**⚠️并含正确性隐患**：RANDOM 模式 `IN :ingredientIds` 展开全食材库(数千)→逼近 **SQLite 999 变量上限→可能报错崩溃**(见下 🔴)。
- 🟡**#5 `selectSeasoningIngredientIds`**：O(I) 全类目扫、结果近乎静态(调料分类极少变)，被 gather+gatherForPlan+freePairing+annotatePlan **4 处**每次重查——可缓存一次多处受益。
- 🟡#4 `dishNutrition(candidateIds)`：C=100 封顶、O(C·k) 稳定，随每菜配料数增长；当前不痛。
- 周期规划 `gatherForPlan`：全库菜 O(D·k) 一次性 + 内存组装(已从 2500+ 查降到 ~8 条)，D 到数千道时月计划(低频)变慢。

痛点收敛：**记录量 M↑→#1 先痛；食材库 I↑→#2/#5；菜品量 D↑→#3**。#1 最普遍。

## 三、🔴 正确性隐患（建议不等阈值·尽早修）
**RANDOM 模式 `IN` 变量上限**：`gather(RANDOM)` 用 `selectAllIngredientIds()` 取全食材 id → `findDishesByIngredients(全部id)` 的 `IN ?` 展开为数千个绑定变量，**旧版 Android SQLite `SQLITE_MAX_VARIABLE_NUMBER=999`→超限报错**(食材库过千时 RANDOM 推荐可能直接崩)。修法：RANDOM 模式改走**无 IN 过滤的候选查询**(如按热度/最近取 top-C，语义="都可做")或分块。**这是正确性风险不只性能**，优先级高于缓存。
