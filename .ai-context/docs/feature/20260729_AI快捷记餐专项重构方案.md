## 一、产品定位与范围

### 1.1 核心思路转变

**旧（K1）**：AI 快捷记 = "AI 解析一段文本 → 入库"

**新（K2+）**：AI 快捷记 = **全局统一的食材/菜品/餐次/餐食数据流水线**

即：食材创建界面、菜品创建界面、记餐界面、周期计划都是"数据收集载体"，最终都组成统一 JSON 入库。没有界面时，数据由 AI 或规则自动生成。

### 1.2 用户故事

| 优先级 | 编号 | 用户故事 |
|--------|------|---------|
| **P0** | US1 | 语音一句话记餐：长按→说话→松手→文字填入→发送→预览→确认入库 |
| **P0** | US2 | 粘贴菜单快速记：复制微信里的菜单→打开 App→点粘贴→发送→预览→入库 |
| **P0** | US3 | 打字记餐：手动输入吃了什么→发送→预览→入库 |
| **P0** | US4 | 查看操作说明：点 (i) 图标了解支持什么格式 |
| **P1** | US5 | 粘贴整周菜单：贴上7天菜单→AI 自动解析每一天每一餐→预览可逐天微调→一键入库到周计划 |
| **P1** | US6 | 对话式 AI 生成餐食 JSON→导入入口→预览→入库（本期不实现，只做架构预留） |
| **P2** | US7 | 统一数据入库管道：食材创建/菜品创建/记餐/周计划都走同一套 JSON→Domain→DB |

### 1.3 MVP（本次交付）vs 后续迭代

**MVP（K2）**：
- 界面改造（去掉 Tab、新布局、语音长按、粘贴按钮、(i) 说明）
- 语音输入修复（SpeechRecognizer + 长按 + 波形动画 + 权限）✅ **已实现**
- 规则引擎增强（多餐次分段、星期/餐次全量正则）
- AI Prompt 重写（完整 JSON 示例 + 多场景覆盖）
- DishNameIngredientGuesser 抽通用方法 `IngredientNameExtractor`
- 四级 JSON Schema 定义（shared 纯数据类）
- 预览确认页增强（可调日期/餐次/菜品、支持撤销）

**下个迭代（K3）**：
- 多天解析（粘贴整周菜单→按天分拆→逐天预览→批量入库）
- `MultiDayRecorder` 多天入库编排
- 周计划入口接入

**远期**：
- 对话式 AI 生成餐食 → JSON → 一键入库
- 统一入库管道覆盖食材编辑器（AI 补全营养）、菜品编辑器（AI 补全食材/做法）

## 三、四级 JSON Schema 设计

> 文件位置：`shared/.../ai/meallog/UnifiedMealSchema.kt`（纯 @Serializable 数据类，shared commonMain，零平台依赖）

### L1: FoodJson（食材创建）

```kotlin
@Serializable
data class FoodJson(
    val name: String,                             // 必填：食材名
    val alias: String = "",
    val emoji: String = "🥗",
    val default_unit: String = "g",
    val category_names: List<String> = emptyList(), // 分类名列表
    val food_group: String? = null,                // 营养大类
    val nutrition: FoodNutritionJson? = null,      // 营养数值（可选）
    val detail: FoodDetailJson? = null,            // 详情扩展
    val image_hint: String = "",
    val source: String = "ai",                     // preset/user/ai/imported
)
```

### L2: DishJson（菜品创建）— 内嵌 FoodJson 用于食材

```kotlin
@Serializable
data class DishJson(
    val name: String,
    val cooking_methods: List<String> = emptyList(),
    val tags: List<String> = emptyList(),
    val cuisine: String = "家常菜",
    val special_note: String = "",
    val description: String = "",
    val steps: List<String> = emptyList(),
    val meal_slots: List<String> = emptyList(),
    val image_hint: String = "",
    val ingredients: List<DishIngredientJson> = emptyList(), // 内嵌 food 或 name 引用
    val source: String = "ai",
)

@Serializable
data class DishIngredientJson(
    val food: FoodJson? = null,      // 新建食材时提供完整信息
    val name: String = "",           // 引用已有食材时按 name 匹配
    val quantity: Double = 100.0,
    val unit: String = "g",
    val is_main: Boolean = true,
)
```

### L3: MealJson（餐次入库）— 内嵌 DishJson

```kotlin
@Serializable
data class MealJson(
    val meal_type: String? = null,            // breakfast/lunch/dinner/snack
    val meal_time: String? = null,            // HH:MM
    val note: String = "",
    val dishes: List<MealDishRefJson> = emptyList(),
)

@Serializable
data class MealDishRefJson(
    val dish: DishJson? = null,    // 新建菜品时提供完整信息
    val name: String = "",         // 引用已有菜品时按 name 匹配
    val quantity: Double = 1.0,
    val quantity_unit: String = "份",
    val eaten_ratio: Double? = null,
    val note: String = "",
)
```

### L4: DayMealJson（一天餐食）— 内嵌 MealJson

```kotlin
@Serializable
data class DayMealJson(
    val date: String? = null,          // YYYY-MM-DD 绝对日期（优先）
    val date_offset: Int = 0,          // 相对今天偏移
    val weekday: String? = null,
    val meals: List<MealJson> = emptyList(),
    val raw_input: String = "",        // 原始用户输入（可溯源）
    val parse_method: String = "",     // "ai"/"rule"/"hybrid"
)
```

### 多天汇总（周计划用）

```kotlin
@Serializable
data class MultiDayJson(
    val days: List<DayMealJson> = emptyList(),
    val meta: MultiDayMetaJson? = null,
)
```

### 关键设计决策

| 决策 | 理由 |
|------|------|
| **层层内嵌复用**（L1→L2→L3→L4） | AI 可一次输出完整嵌套 JSON，也可只引用已有实体 |
| **`name` 即引用键** | 对 AI 友好（不暴露内部 ID），入库时按 name 查已有→复用 |
| **所有非必填有默认值** | 容错 AI 输出不完整；`ignoreUnknownKeys=true` 兼容多余字段 |
| **`parse_method` 溯源** | 标记 AI/规则产出，方便诊断 |
| **`FoodJson/DishJson` 既可用于新建也可用于引用** | `food=null` 时按 `name` 匹配已有；`food!=null` 时走新建入库 |

## 四、解析引擎设计

### 4.1 两路并行 + 合并策略

```
用户输入
  │
  ├─ [A路] 规则引擎（永远跑，离线可用）
  │   TextNormalizer → TextSegmenter → RuleMealParser → DayMealJson
  │
  └─ [B路] AI 解析（有Key且有网时跑，增强准确率）
      Prompt(A路结果作hint) → LLM → JSON → DayMealJson
  │
  └─ 合并策略：B路优先，A路填充B路未识别段
     → DayMealJson(parse_method="hybrid")
```

**兜底链**：AI 解析（优先）→ AI 失败→规则匹配→ 规则也失败→最简拆分（硬按分隔符拆，每段当一道菜）→ 还不行→ErrorPhase

### 4.2 规则引擎（RuleMealParser）

```
输入文本
  → TextNormalizer（全半角归一、标点统一、合并空行）
  → TextSegmenter（按星期/日期/空行切 N 个日期块）
  → 逐块 parseDayBlock:
      ① resolveDate（weekdayHint + dateHint + today → date_offset）
      ② splitByMealKeywords（按 早饭/午餐/晚饭/加餐/宵夜 分段）
      ③ 逐段 parseMealBlock → MealJson
         · extractMealType → "breakfast"/"lunch"/...
         · extractMealNote → "少盐；少油"（提取后**从文本删除**←避坑！）
         · splitDishes（硬分隔 `、，,+\n` + 软分隔 `和/跟/还有`）
         · 逐菜 parseDish → 份量+单位+食用比例+烹饪方式
         · IngredientNameExtractor.extract(dishName, libNames) → 食材列表
```

### 4.3 星期/餐次全量正则

**星期**：`周一/星期二/礼拜三/周三/星期日/星期天/周末/Mon/Tue/...`
**相对**：`前天(-2)/昨天(-1)/今天(0)/明天(1)/后天(2)`
**餐次**：`早饭/早餐/早上/早点/早晨/晨间/过早→breakfast | 午饭/午餐/中饭/中午/中餐/午间/晌午→lunch | 晚饭/晚餐/晚上/夜间/傍晚/夜饭→dinner | 加餐/宵夜/夜宵/零食/下午茶/早茶/点心→snack`

### 4.4 IngredientNameExtractor（通用食材提取器）

将 `DishNameIngredientGuesser.guessDetailed()` 核心算法抽取为独立工具：

```kotlin
object IngredientNameExtractor {
    fun extract(
        dishName: String,
        libraryNames: List<String>,
        extraStopWords: List<String> = emptyList(),
    ): List<ExtractedIngredient>  // {name, inLibrary}
}
```

- ①库内食材长名优先占位子串匹配 → ②停用词剔除 → ③剩余连续中文段(≥2字)作库外候选
- `DishNameIngredientGuesser` 保留旧 API 委托给新工具
- 规则引擎和 AI 解析共享此工具

## 五、AI Prompt 设计

### 5.1 设计要点

作为 AI，设计 Prompt 时遵循原则：
1. **先给完整 JSON 示例**（而非文字描述字段）—— 比描述直观 10 倍
2. **分场景规则**—— 单餐/多餐/跨天各一组规则
3. **食材估量参考范围**—— 肉 100-200g/蔬菜 100-150g/蛋 50-60g/调料 3-15g，避免 AI 都填 100g
4. **规则预解析作为 hint**—— AI 在规则基础上纠正补全，比从零解析更稳
5. **只输出 JSON 铁律**—— 强烈约束 + extractJson 兜底 + 重试一次

### 5.2 System Prompt（核心结构）

```
你是家庭饮食记录助手。从用户自然语言提取结构化用餐信息，输出 JSON。

=== 输出格式 ===
{ "days": [{ "date_offset": 0, "meals": [...] }] }
  ...完整 JSON 示例（展示四级嵌套结构）...

=== 分场景规则 ===
【单餐】"中午吃了红烧肉和米饭"→1个meal, 2道dish
【多餐】"早饭鸡蛋牛奶，中午牛肉面，晚上不吃"→3个meal
【跨天】"昨天早上面包，今天早上面条"→2个day
【份量】"三个鸡蛋"=1菜 quantity=3 unit="个"
【食用比例】"吃了一半"→eaten_ratio=0.5
【食材反推】"番茄炒蛋"→番茄+鸡蛋（估正常份量克数）

=== 铁律 ===
- 只输出 JSON，不要解释、markdown标记、前后缀
- 字段能填就填，填不出用默认值，别臆造
- 每餐至少1道菜
```

### 5.3 结构化输出策略

| 层级 | 策略 |
|------|------|
| L0 | temperature=0.2 + Prompt强约束仅JSON |
| L1 | extractJson（去```json```+首{到尾}截取） |
| L2 | 解析失败→重试一次（temperature+0.05） |
| L3 | 重试仍失败→回退规则引擎结果 |

### 5.4 食材/菜品名引用策略

**结论：当前不把完整食材库名列表传给 AI**

理由：
- Token 成本高（200-500 食材 × 3 字 ≈ 600 token/次）
- AI 需要的是"从菜名反推食材"而非"从库中选"，入库层会自动按名匹配已有
- `AiMealRecorder.resolveDish()` 先查 `dishIdByName()`
- `createUserIngredient()` 自动去重（UNIQUE 约束）

## 六、数据入库流水线

### 6.1 完整链路

```
用户输入
  → RuleMealParser + AI → MultiDayJson
  → SchemaValidator（必填完整性/日期范围/至少一菜）
  → MultiDayRecorder.recordAll()
      逐天、逐餐、逐菜：
      Phase 0: 日期解析（date/date_offset + today → LocalDate）
      Phase 1: 食材解析（food.name → 查已有/新建 createUserIngredient）
      Phase 2: 菜品解析（dish.name → 查已有 dishIdByName / saveDish）
      Phase 3: 组装 Drafts + mergeWithExisting（同餐次追加）
      Phase 4: eaten_ratio 回填
  → 入库完成 → RecordResult（含新建食材/菜品清单）
```

### 6.2 周计划接入

粘贴整周菜单 → `MultiDayJson`（7条 DayMealJson）→ `MultiDayRecorder.recordAll(days, today)` → 逐天 `saveDayMeals`

**约束**：某天已有餐食走 `mergeWithExisting` 同餐次追加（与现有 D4 行为一致）

### 11.1 方案优化建议（我们自己的反思）

经过三人会商 + 用户审阅后，以下是可以进一步优化的点：

| # | 优化建议 | 说明 | 建议 |
|----|---------|------|------|
| **A** | **Schema 层次过深** | 当前 L1→L2→L3→L4 四层嵌套，LLM 生成深层嵌套 JSON 容易出错（漏括号、字段层级错位）。业界实践：**对 LLM 输出尽量扁平化** | 增加一个 **扁平中间格式 `FlatMealJson`**：AI 输出扁平行列表（每行=一道菜的完整信息含菜名/餐次/日期/食材），后端再按日期+餐次聚合为嵌套 `DayMealJson`。AI 准确率更高，后端聚合纯函数零风险 |
| **B** | **Prompt 中给用户食材库「高频食材 Top 50」** | 原方案说"不传完整库"，但传少量高频食材名（~150 token）能让 AI 拆分菜名时更有针对性（如知道库里有"上海青"而非笼统"青菜"） | 每次调 AI 时附带**用户最近使用 Top 50 食材名 + 预设高频 Top 50**（~100个名~300 token，可控），入库层仍做 name→查已有兜底 |
| **C** | **规则引擎加"模糊纠错"层** | 用户输入可能有错别字（"西蓝花"/"西兰花"、"番茄"/"蕃茄"、"鸡蛋"/"鸡旦"）→规则匹配失败 | 食材名匹配前做**常见错别字归一化映射表**（`西蓝花→西兰花`、`番茄→番茄`…），不改变库内名称，只在匹配时做输入侧纠正 |
| **D** | **AI 响应流式化** | 当前等完整响应再解析，用户等待时间长（最坏 45s） | 后期可用 SSE 流式，边出字边显示"AI 正在理解…已识别 3 道菜"，本期先做超时降级提示 |
| **E** | **DishJson 区分"食谱模板"与"餐次实例"** | "红烧肉"作为一道菜的食谱（食材/做法/菜系）vs "今天午餐吃了红烧肉 ×1份（吃了一半）"作为实例，两者字段交集大但有独立语义 | 当前 Schema 已内嵌（`MealDishRefJson.dish: DishJson?` = 模板，外层字段=实例），方向正确。后期可独立 `DishTemplateJson` 与 `DishInstanceJson` 两张表 |

**关于建议 A（扁平化）的详细分析**：

当前嵌套式（AI 直接输出）：
```json
{"days":[{"meals":[{"dishes":[{"dish":{"ingredients":[...]}}]}]}]}
```
问题：5 层嵌套，LLM 容易在中间层漏 `}` 或 `]`。

建议增加扁平中间格式（AI 输出这个，后端再聚合）：
```json
{
  "items": [
    {"date":"周日","meal":"早餐","dish":"白煮蛋","qty":1,"unit":"个",
     "ingredients":[{"name":"鸡蛋","qty":50,"is_main":true}]},
    {"date":"周日","meal":"早餐","dish":"鲜牛奶","qty":1,"unit":"杯",
     "ingredients":[{"name":"牛奶","qty":200,"is_main":true}]},
    ...
  ]
}
```
优点：每行自包含、AI 无需管理嵌套括号、后端按 date+meal 聚合零风险。

**决策**：两套 Schema 并存——AI 输出扁平 `FlatMealJson` → `FlatToDayMealConverter` 聚合为 `DayMealJson`；规则引擎直接产出 `DayMealJson`（程序化生成无嵌套风险）。

### 11.3 JSON Schema 优雅性评估

#### 标准做法参考

| 标准 | 说明 | 适用性 |
|------|------|--------|
| **JSON Schema (json-schema.org)** | 声明式校验规范，描述字段类型/必填/枚举/嵌套 | 可用于**后端校验** AI 输出，生成 `UnifiedMealSchema.schema.json` |
| **OpenAPI/Swagger** | API 文档规范，定义请求/响应模型 | 适合对外 API，内部用偏重 |
| **JSON-LD** | 关联数据，用 `@context` 描述语义 | 过度设计，营养/食材领域无标准词汇表 |
| **Protocol Buffers / FlatBuffers** | 二进制序列化，强类型 | 不适用（需要人类可读 JSON 给 AI 输出） |
| **HAL / JSON:API** | RESTful 资源表达规范 | 过度设计 |

#### 当前方案评价

**优点**：
- `@Serializable` + `ignoreUnknownKeys` + 全字段默认值 → 对 AI 输出容错强
- 层层内嵌复用，层级清晰

**可改进**：
1. **AI 输出用扁平格式**（见 11.1-A），降低嵌套深度从 5 层→2 层
2. **加 `$schema` 版本字段**到顶层 `MultiDayJson`，如 `"schema_version": "1.0"`——后期 Schema 演进时老版本 JSON 可自动迁移
3. **食材/菜品引用统一为 `ref` 字段**（仿 JSON Reference 草案），清晰区分"新建"和"引用"：

```kotlin
// 更优雅的引用语义
@Serializable
data class DishIngredientJson(
    // 二选一：引用已有 → 用 ref；新建 → 用 food
    val ref: String? = null,        // "牛肉" → 入库时按 name 查已有
    val food: FoodJson? = null,     // 新建食材的完整信息
    val quantity: Double = 100.0,
    val unit: String = "g",
    val is_main: Boolean = true,
)
```

**结论**：当前方案已足够好，建议采纳以下改进：
- ✅ 加扁平中间格式 `FlatMealJson`（AI 输出用，后端再聚合）
- ✅ 加 `schema_version` 字段
- ✅ 引用字段统一为 `ref: String?`（语义更清晰）

### 11.5 AI 生成菜品不受食材库限制

**已在本方案覆盖，补充强调**：

```
AI 输出食材名（如"樟树椒"）
  → IngredientNameExtractor.extract() → inLibrary=false（库外候选）
  → MultiDayRecorder.resolveDish():
      ① dishRepo.dishIdByName(name) → 已有 → 复用 ID
      ② 无 → ingredientRepo.createUserIngredient(name, source="ai")
         → 自动建库 + UNIQUE 约束防重复
      ③ saveDish(source="ai") → 自动建菜
```

- AI 可自由创建任意食材名，不受库限制
- 入库时自动去重（按名查已有→复用；无→新建）
- 新建的食材标 `source="ai"`，在详情页可看到"AI 创建"标签
- 用户可后续编辑/删除（AI 创建的 source="ai" 不限制删除，不像预设 preset 不可删）

### 11.6 多餐食日期默认 + 冲突处理

#### 日期默认规则

```
用户输入未提任何日期
  → 所有解析出的 DayMealJson.date_offset = 0（当天）
  → 如有星期几（如"周一吃X，周二吃Y"），按 today 推算未来最近的对应星期

用户输入提到具体日期
  → 优先用绝对日期；相对日期（昨天/前天/明天）→ date_offset
  → "下周X" → today + (7 + 目标星期偏移)
  → "从明天开始连续3天" → date_offset = 1,2,3 分别对应三天
```

#### 已有餐食冲突处理

当解析出的某天某餐次**已有餐食记录**时：

```
预览确认页：

┌─────────────────────────────────────────────┐
│  📅 周三 7/30 · 午餐                        │
│                                              │
│  ⚠️ 这一天午餐已经有记录了                   │
│                                              │
│  【已有记录】                    【新解析】   │
│  ┌──────────────────┐  ┌──────────────────┐ │
│  │ 沙县小吃  ×1份    │  │ 宫保鸡丁  ×1份   │ │
│  │                   │  │ 米饭      ×1碗   │ │
│  └──────────────────┘  └──────────────────┘ │
│                                              │
│  如何处理？                                   │
│  ○ 保留已有，不添加新的                       │
│  ● 追加到同餐次（两边都保留）                  │
│  ○ 用新的替换已有                             │
└─────────────────────────────────────────────┘
```

**默认行为**：追加到同餐次（`MergeMode.APPEND`），用户可切换为替换或跳过。

**多天预览**：逐天卡片，有冲突的日期卡片顶部标橙色"⚠️ 已有 N 餐"，展开后并排对比。

### 11.7 周计划界面入口 + 自动跳转

#### 入口

```
一周计划页（WeekPlanScreen）右上角：
  [✨ AI快捷记] 按钮（IconButton 或 CapsuleButton）

一周计划中的"某天空态 + 添加餐食"入口进去的 AI 快捷记：
  行为同上，但 Sheet 标题改为"AI 快捷记 · 周计划"
```

#### 自动跳转逻辑

```
用户从「记一餐」入口进入 AI 快捷记
  → 输入文本 → 解析
  → 判断结果：
      ├─ 只有 1 天（date_offset 相同） → 正常预览确认 → 入库到当天
      └─ 解析出 2+ 天（不同日期）
           → 弹提示对话框：
              "你输入的内容包含 N 天的餐食，已自动切换到周计划视图"
              [取消]  [去周计划查看]
           → 点「去周计划查看」→ dismiss AI Sheet
             → navigate 到 WeekPlanScreen（带 MultiDayJson 数据）
             → WeekPlan 预览模式（同 §2.5 多天预览）
```

同样的逻辑反过来也适用：
```
用户从「周计划」入口进入
  → 解析出 1 天 → 正常预览 → 入库到对应日期（周计划中该日自动刷新）
  → 解析出 2+ 天 → 多天预览 → 逐天确认 → 批量入库
```
