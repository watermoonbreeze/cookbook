# 食用比例「进度条 + 成员维度」摄入方案（讨论稿）

> [AI生成] 2026-07-23 用户反馈 J2。升级现有「四档吃完度」为「0-100 进度条 + 每成员各自吃了多少」。**本文是讨论稿**：先厘清一个核心建模歧义、给两个建模选项 + 我的倾向，供会商拍板后再出实现方案。前身：`食用比例吃完度_摄入会商方案.md`（已落地的四档版）。

## 一、用户诉求（原话要点）
1. **进度条替四档按钮**：吃了多少是一根 **0~100 进度条**（没吃0→少量→一半→大部分→吃完100），每个区间给口语名；用户可拖到任意位置（体现"一半多一点"），点击直接落到对应区间。
2. **餐次 = 菜品进度的平均值**，双向联动：改菜品→餐次滑块按均值落位（不会像现在四档那样"整餐没对上就不高亮/滑块消失"）；改餐次→菜品按均值平分。
3. **实际吃了多少要跟着成员走**（当前的 bug：成员1调了比例，成员2进去还是这个值）。默认按**在场成员的餐食系数平分 100**；某成员调整后，其他成员按各自系数重分。
4. **新增"没吃"档** = 亮点：兼容"给小孩单独做的菜，其他成员不计入"、"某人中午外食，该餐设没吃 / 或把外食也记进来各算各的"→ 更准地统计每个人的摄入。**要在功能介绍重点体现**。
5. **餐食系数固定为下拉** 10/20/…/100 十档（现在能随便填，要规范）。
6. 计算按百分比：每个菜品 / 每顿餐次在总体中参与计算时**乘上这个百分比系数**。
7. **同步更新**「我的·营养怎么算·吃了多少怎么算」的说明。
8. 问：现在"今日营养·吃完=把自己那份全吃完"是不是太笼统？按新规划是否更合理？（是，见下）

## 二、现状（已落地·四档版）
- `meal_record_dish.eaten_ratio`（**菜级·不分成员**，默认1.0，四档 1.0/0.75/0.5/0.25）。
- `IntakeCalculator`：个人摄入 = Σ菜[ 整份 × `eaten_ratio` × 成员`share`(餐食系数归一) ]。**eatenRatio(这道菜被吃掉多少) 与 share(吃掉部分成员各占多少) 是两个正交维度。**
- 入口 `EatenAdjustSheet`（今日卡·四档整餐+分菜折叠）。
- 问题：①四档离散→整餐混合态滑块不高亮（J2.2 要解决）②eatenRatio 不分成员→"给小孩单做的菜"其他人也被算、"某人外食"没法单独排除（J2.3/2.4 要解决）。

## 三、🔴 核心建模歧义（会商必须先厘清）
用户把两件事说在了一起，需要拍板它们是**合并**还是**保持正交**：
- **A「这道菜被吃掉多少」**（菜的整体消耗·进度条）
- **B「吃掉的部分，每个成员各占多少 / 每个成员各自吃了多少」**（成员维度）

用户原话"默认按系数平分100、用户1调到50吃一半、其他人分剩下50"——这句里 **A 和 B 纠缠了**：50 到底是"这道菜整体吃了一半(A)"还是"用户1一个人吃了整份的50%(B)"？两种解读导致完全不同的数据模型。

## 四、两个建模选项 + 我的倾向
**选项① 保持两维正交，但都可 per-member 覆盖**（改动较小）
- 菜级进度条 = A（这道菜被吃掉多少·0-100）；成员 share = B（餐食系数归一·可调）。
- "没吃" = 某成员对某菜 share=0（给小孩单做→其他人 share=0；某人外食→该餐所有菜 share=0）。
- 摄入 = 整份 × A(菜进度) × B(该成员share)。**沿用现有公式**，只把 share 从"全局系数"升级为"可 per-dish 覆盖 + 支持0"。
- 优点：改动小、公式不变、概念清晰。缺点：不完全等于用户说的"每个成员各自吃了多少"（成员差异体现在 share 不在"吃了多少"）。

**选项② 统一为「每成员每菜的摄入比例」矩阵**（改动大·更贴用户心智·我倾向）
- 一道菜整份=100%，**每个成员对每道菜一个百分比**（0-100·占整份多少）；默认按在场成员餐食系数分配（三人各≈33）；某成员拖动改自己的，其他人按系数重分「剩余额度」。
- 这个百分比**直接**就是该成员从这道菜的摄入比例（A×B 合并成一个数）。
- "没吃"=该成员该菜=0（天然兼容外食/给小孩单做）；这道菜"整体被吃掉多少"=Σ成员百分比（进度条给整菜看的落位=这个和 或 均值）。
- 餐次某成员进度 = 该成员当餐所有菜百分比的均值；改餐次→按均值平分回各菜。
- 优点：**完全等于用户心智"每人吃了这道菜多少"**、成员差异一等公民、亮点(没吃/外食/单做)自然。缺点：**数据模型大改**——`meal_record_dish.eaten_ratio` 单值 → 新表 `meal_record_dish_member(mrd_id, member_id, ratio)`；迁移；`IntakeCalculator` 重写；UI 变"进度条矩阵"。

**我的倾向 = 选项②**（更贴用户描述、把 J2.3/2.4 的成员差异做成一等公民、"没吃"亮点最自然），但它是 **L 级改造**，必须会商确认存储粒度与迁移成本后再动。若想先快速见效，可先做**选项①的 share 支持0+per-dish**（解决"给小孩单做/外食"亮点）+ 进度条替四档（解决滑块消失），把"每成员各自吃了多少"的完整矩阵留二期。

> **🟢 2026-07-23 用户拍板 = 选项②**：语义明确为"**针对单个菜品，我（某成员）吃了多少 → 算我的摄入**"，即 **per-member-per-dish 百分比矩阵**（每格=该成员吃了这道菜整份的百分之几）。**下一步 = 五方会商细化选②**：①存储（新表 `meal_record_dish_member(mrd_id, member_id, ratio)` + 迁移）②`IntakeCalculator` 重写为读矩阵（个人摄入=Σ菜[整份×该成员该菜ratio]，不再×全局share）③默认分配（在场成员按餐食系数分整份·一人调其余按系数重分「剩余额度」的确切算法）④UI（进度条矩阵·菜级/餐级/成员级联动落位）⑤迁移旧数据（现有 `eaten_ratio` 单值 → 按当时在场成员系数拆成矩阵）。会商后再动 schema。

## 五、进度条交互（两个选项通用）
- 0-100 连续条，**内部按百分比存**；叠加区间标签：没吃(0) / 少量(约1-30) / 一半(约31-60) / 大部分(约61-90) / 吃完(91-100)——**区间阈值数据驱动、可调**。
- 点击标签→落到该区间中点；拖动→任意值（体现"一半多一点"）。区间口语文案随位置显示。
- 解决"滑块消失"：进度条恒有位置（餐次=菜品均值算出落点），不再有四档"整餐没对上→不高亮"。

## 六、餐食系数固定下拉（J2.5·独立小项·可先做）
- 档案里餐食系数从自由输入 → **下拉 10/20/…/100**。归一化逻辑不变（∑在场成员系数做分母）。这条**独立、低风险**，可先落地。

## 七、亮点（J2.4·功能介绍重点体现）
"**每个人各自吃了多少、没吃也能记**"——给小孩单独做的菜其他人不计、某人外食那餐可标没吃或各算各的 → 家庭多成员摄入统计更准。这是区别于普通记账 App 的差异点，运营/功能介绍(J7)重点讲。

## 八、影响面
- **DB**：选①=share 存储支持 per-dish+0（可能偏好JSON或轻改）；选②=新表 `meal_record_dish_member`+迁移。
- **算法**：`IntakeCalculator` 单一真相源改造（守"抽共享防漂移"）；今日营养卡/报告/EatenAdjustSheet 全接新口径。
- **UI**：进度条组件（替四档）；成员维度矩阵（选②）；防"改B表不刷A表"令牌（沿用 `observeEatenRatioChanges` 教训）。
- **红线**：计划餐不自动算吃；eatenRatio 只缩摄入量不缩"高钠/高嘌呤定性"；热量默认开可关。
