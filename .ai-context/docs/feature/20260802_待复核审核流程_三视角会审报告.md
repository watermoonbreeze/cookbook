# 待复核食材审核流程 — 三视角会审报告

## 会审结论

方案方向正确，三处设计调整 + 两处数据层阻断修复。详细如下。

## 一、Apple UX 设计评审

### 阻断级

1. **入口放顶栏图标** → 改为 Tab 栏动态追加
   - 顶栏已有搜索+添加两个图标，加第三个拥挤且条件显隐导致布局跳动
   - Tab 栏语义上就是内容过滤器，"待复核"天然属于筛选维度

2. **覆盖层叠放模式** → 改为 Tab 切换
   - 搜索覆盖层是瞬态输入，"待复核"是任务型浏览，语义不同
   - 顶栏从 LargeTopAppBar 秒变 AppTopBar→视觉跳动剧烈

3. **编辑器内双按钮（标记+保存）** → 改为详情弹层标记 + 编辑保存自动标记
   - 编辑器一个页面一个主任务，"复核"和"编辑保存"是两个任务
   - 编辑保存即自动标记已复核（用户编辑了=确实看过了，少一步）

### 建议级

| 议题 | 决议 |
|------|------|
| Badge 颜色 | 红色=危险语义 → 用 primary 色（赤陶橘）小圆点贴 Tab 标签角 |
| 操作步数 | 原方案 6 步 → 方案 A 缩短为 3-4 步 |
| 组件复用 | `PrimaryTabRow` + `IngredientCard` + `IngredientDetailSheet` + `NutritionGuessBanner` 风格 |
| 空态 | 全部复核完→Tab 消失+Snackbar；首次无待复核→教育性空态 |

## 二、Google 工程质量评审

### 阻断级（🔴 必修）

| # | 问题 | 文件 | 修复 |
|---|------|------|------|
| 1 | SQL 12 列 vs mapper 10 参数 → 编译失败 | `Cookbook.sq` + `IngredientRepository.kt` | 删 `i.status`/`i.reason` 冗余列 |
| 2 | `upsertNutrition` 硬编码 `review=0L` 会冲掉已复核标记 | `NutritionRepository.kt` | 先查当前 review，若已=1 则保留 |

### 建议级（🟡）

| # | 问题 | 修复 |
|---|------|------|
| 1 | `ref LIKE '%待核%'` 与 `review=0` 双重判定冗余且脆弱 | 纯用 `review=0` 判定 |
| 2 | 两条查询 WHERE 条件重复 | 加注释同步提醒 |
| 3 | `listPendingReview()` 返回无营养数据 → 潜在 N+1 | 详情弹层走现有独立查询，不新增 N+1 |
| 4 | `markReviewed` 无返回值 | 返回 Boolean |
| 5 | Badge 入口仅 LargeTopAppBar（Tab 页），selectionMode 缺 | 方案已改为 Tab 动态追加，双模式均覆盖 |
| 6 | `showPendingReviewOnly` 与 `filterForTabSource` 交互 | 待复核 Tab 走独立数据源，不经过 source 过滤管道 |

## 三、Apple 软件行为评审

### 透明分级

| # | 行为 | Tier | 告知方案 |
|---|------|------|----------|
| 21 | autogen 自动建食材（营养估算+care 留待） | T1+ | 首次→Snackbar 引导；后续→简化版；Badge 常驻 |
| 22 | 待复核列表+Badge | T1 | 持续性被动线索，与 #21 Snackbar 互补 |
| 23 | 标记已复核 | T1 | 二次确认（不改数值时）+ Snackbar 可撤销 |
| 24 | 营养修改后自动复核 | T0/T1 | 保存即自动 review=1+ref 标注 |

### 关键决议

| 议题 | 决议 |
|------|------|
| ref 语义拆分 | `ref="自动估算"`（溯源·不变）+ `review`（状态·可变）→ 消除"已复核但仍标待核"矛盾 |
| 标记确认 | 不改数值直接标记→二次确认弹框（防止随手点掉）；编辑保存→自动标记（无确认） |
| 批量操作 | **禁止**批量一键标记（反暗黑模式） |
| 健康免责 | 待复核列表顶部+详情琥珀条均含「仅供参考·非医嘱」 |
| 操作审计 | 仅 `updated_at` 时间戳，不另建审计表（单用户本地 App） |
