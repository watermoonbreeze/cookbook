# 预设食材数据生产线方案（Ingredient Data Pipeline）

> [AI生成] 2026-07-23 与用户讨论确立骨架。目标：把预设食材的**采集→校验→发布**做成**脚本驱动、脱离 AI、可复现、可持续**的数据生产线，替代当前"临时联网核准 + 手工改 JSON"的零散模式。
> 定位：本方案只管**预设食材**（方向①数据扩充 + ②营养素/忌口补充）；方向③自建食材联网补充暂不在此，但架构上可复用同一套采集/校验能力。

## 一、拍板结论（2026-07-23 用户定）
1. **目标量级 = 1–2 千常见食材**（家庭日常 + 慢病高频覆盖）。→ 不上重型分布式爬虫，"半自动采集 + 人工把关"即可。
2. **营养数值主干 = USDA FoodData Central API + 中文补**（USDA 合法可批量；中文特色食材人工/半自动补）。
3. **发布模式 = 预制 db（进 assets·全新装用）+ 增量 seed（老用户版本化更新）并存**——不丢增量更新能力、不毁用户自建数据。

## 二、核心红线（贯穿全线·不可破）
- **忌口/健康规则 = 规则不是数据**：忌口/生命阶段限制的判定口径必须来自**权威指南原文**，人工核 level。爬虫只收候选，**不自动定忌口**（否则会像 Q1 植物高嘌呤那样过度误判）。
- **营养数值权威分级**：USDA / 《中国食物成分表》为一手；薄荷/美食天下等二手站**只作交叉参考、标低置信度、不单独采信**（生蚝钙131、玫瑰花gi=0 都是二手错值教训）。
- **未过校验门不发布**：不搞"攒够条数自动转预设"；发布前必过质量门 + 人工抽检。
- **健康免责**：所有数值/分级带口径来源 + "仅供参考·非医嘱"；无国标的（嘌呤三级）标"惯例·非国标"。
- **每个值可溯源**：staging 里每个字段都带 `source + 置信度 + 采集时间`。

## 三、可行性难点与应对（写在前面·决定打法）
**难点：USDA 是英文库，中式食材/加工食材/调料映射困难。**
- 基础食材（肉蛋奶、常见果蔬、谷物）USDA 覆盖好、映射清晰 → **USDA 主干成立**。
- 中式特色（油麦菜、腐竹、皮蛋、老抽、豆瓣酱、腊肠…）USDA **常无对应或差异大** → 这部分**必须靠《中国食物成分表》值**（人工/半自动录，标来源），USDA 补不上。
- **应对策略（分而治之）**：
  - A 类·国际通用食材 → USDA API 自动拉（英文名映射表维护）
  - B 类·中式特色/加工/调料 → 中文成分表值为准（半自动录入 + 人工核）
  - 两类都在 staging 标 `source`，校验层对 A 类可 USDA↔中文交叉，对 B 类靠中文源 + 合理性检查（离群/单位）。
- 结论：**"USDA 主干"落到实处 = USDA 覆盖的用 USDA、覆盖不了的中式食材老实用中文成分表**，不硬套 USDA。

## 四、总体架构：三层管线
```
采集层(三采集器 → staging DB)  →  校验层(质量门)  →  发布层(生成预设)
        ↑ 脚本驱动·脱离AI                ↑ 自动+人工抽检        ↑ 预制db + 增量seed
```
- **staging DB**：独立的数据仓库（单一事实源），**不必与生产 SQLDelight schema 同构**（避免双份 schema/迁移维护）。用自由结构的 SQLite 即可，字段带溯源。
- 生产数据从 staging **导出/发布**，staging 本身不直接当生产库 → 解耦、可审计、可回滚。

## 五、staging DB 表设计（草案）
```
ingredient_meta        食材元数据: id, name, aliases, category, priority_tier(1健康/2家庭/3其他),
                                   source, collected_at, status(候选/已录)
ingredient_nutrient    营养素: ingredient_id, 各营养字段(每100g), per_field_source(USDA/CN成分表/二手),
                               confidence(高/中/低), collected_at
health_care_rule       健康/生命阶段忌口: condition(病种/生命阶段), ingredient_id, level(avoid/limit/recommend),
                                        guideline_source(指南名+年), guideline_quote(原文摘录),
                                        reviewed_by(人工核标记), status(候选/已核)
review_flag            校验标记: ingredient_id, field, issue(离群/单位/缺一手/USDA中文差异), resolved
```

## 六、三个采集器（对应你的三爬虫·修正版）
### 采集器1 · 元数据（分档优先级）
- 按 `priority_tier` 分三档采集：① 健康状态/生命阶段覆盖到的食材 → ② 家庭常见 → ③ 其他。
- **加类别就自动采**（你的核心诉求）：维护一份"类别→食材清单"配置，脚本按配置扩充 `ingredient_meta`。
- 只拿元数据（名/别名/分类/优先级），营养和忌口由后续采集器补。

### 采集器2 · 营养素（USDA 主干 + 中文补·分批回填）
- 从 staging 分批取"缺营养"的食材 → A 类走 USDA API、B 类中式食材走中文成分表值。
- 每字段写 `source + confidence`；查不到的**留空不编造**（沿用现有红线）。
- 可**定时/增量跑**（脱离 AI）——这就是你要的"脚本自动化执行者"。

### 采集器3 · 健康/生命阶段忌口（半自动·指南驱动·守红线）
- **不是纯爬**：以**权威指南结构化录入**为主（各病种/生命阶段食养指南的"应避免/限制/推荐"清单 → 结构化成 `health_care_rule`，带 `guideline_quote`）。
- 爬虫/检索只做**候选收集**（帮你找"某病种可能相关的食材"），**level 由人读指南原文定**、`reviewed_by` 打标。
- **增量**：加了心脏病/老年人 → 补录这两者的指南清单即可（你的诉求，✓），但走"录指南"而非"自动爬忌口"。

## 七、校验层（质量门·发布前必过）
- **交叉校验**：A 类 USDA↔中文成分表差异 > 阈值 → 标 `review_flag`。
- **离群检测**：同类食材某营养值离群（钙131 那种）→ 标记。
- **单位/引用完整性**：单位一致、food category code 有效、care 的 ingredient 名在食材表存在（沿用现有 seed 校验）。
- **一手性**：营养值 confidence=低（仅二手站）的 → 标"待核"、不升 verified。
- 输出：`verified` / `待核` 标记；**人工抽检**通过才进发布。

## 八、发布层（预制 db + 增量 seed 并存）
- **发布产物1 · 预制 db → assets**：staging 中 `verified` 数据导出成预制 SQLite，进 `assets`，**全新安装**直接加载做基础数据（快、免首启大量 seed）。
- **发布产物2 · 增量 seed / patch**：**老用户**仍走现有机制——导出成 seed（JSON 或版本化 patch），改数据 → 指纹重跑 → `upsert` 增量更新，**不动用户自建菜/食材/餐食记录**。
- 现有 `ingredient_nutrition.json` / `ingredient_care_rules.json` / `crowd_rules.json` 作为**首批导入 staging 的基线**（不重头爬，把已核数据先纳入生产线管理）。

## 九、分期实施（先小步验证管线·再扩量）
- **P0 搭台**：建 staging schema + 把现有 JSON 全量导入 staging（作基线·验证发布链路能重建出等价的现有 seed）。
- **P1 营养管线跑通**：USDA API 拉一批 A 类基础食材、与现有中文值交叉校验、补现有食材缺失营养素（先验证管线，不扩新食材）。
- **P2 元数据扩充**：按优先级配置扩充到 1–2 千食材清单。
- **P3 忌口指南结构化**：把各病种/生命阶段指南清单结构化进 `health_care_rule`（方向②）。
- **P4 发布链路**：预制 db 导出 + 增量 seed patch 生成，双轨落地。
- 每期可独立验证（脚本产物 + `:shared` 单测校验），符合"先做一版看效果"。
