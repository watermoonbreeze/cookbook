# AI-CAPABILITY-01：AI 能力扩展研究与决策蓝图

> 状态：**DECIDED**。SOL 裁决见 `SOL-DECISIONS-20260829.md` §七；本文件仍不授予任何代码改动权限。
>
> 前置：R2（AI 记餐可靠性）、R3（食材数据与来源）必须分别完成对应子批次的 ARCH 验收；R4、R6 的健康和餐食语义决定不得被本批绕过。

## 1. 已核实事实

- `F-AI-MEAL` 的 K1g（NDJSON）、K1i（渐进显示）和 L1（云端 AI 同意）已有历史实现与验收记录；本批不重复实现，只保留到 R10 的设备回归。
- K1f 是“静态别名归一”的已批准方向，但尚无可执行实现批；K15 的规则回退仍必须与 R2-E 的用户确认决策一致。
- 条码、营养标签 OCR、AI 估算、AI 对话计划、端侧模型和 L3 全自动建库均不是同一风险等级，禁止合并成“AI 食材导入”大批次。

## 2. 唯一执行顺序

`R8-A 合同基线` → `R8-B 静态别名` → `R8-C 条码确定性映射` → `R8-D OCR 提取预览` → `R8-E AI 估算预览` → `R8-F 多轮计划研究` → `R8-G 端侧模型评估`。

R8-H（全自动建库 ADR）仅在 R8-B～E 全部有真实使用与风险证据后重开；它不在当前代码队列。每一子批均需重新建立独立 L7 蓝图和 `BLUEPRINT_STATE` 握手，不能复用本研究文件。

## 4. 跨子批不变量

1. 本地、确定性、可审阅的映射优先于云端或概率性推断。
2. 任意 OCR/AI 产物均经历“预览 → 用户确认 → 来源与版本留痕”；取消、退出和失败均不得写库。
3. 云端能力默认关闭，只有明确同意和用户触发时才发送；诊断不得暴露原始敏感内容。
4. 健康提示、营养数值和推荐排序只能消费 R3/R4/R5 已定义的真相源；AI 估算不得伪装成权威来源。
5. 每个子批的 L7 必须含 `INV`、逐文件 allowlist、`T` 自动化案例与 `DEV` 真机项；R10 才能关闭设备证据。
