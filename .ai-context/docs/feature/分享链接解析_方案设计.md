## 一、产品定位

**一句话**：把别人家的菜谱，变成你自己的健康菜单。

用户在"下厨房"等 App 看到菜谱 → 分享链接到本 App → 后台 WebView 加载 + 解析引擎提取结构化信息（菜名/食材/剂量/步骤/图片/烹饪方式）→ BottomSheet 展示结果 → 用户确认 → 跳转编辑页预填 → 保存入库。**导入后立刻给出慢性病评估（忌口/宜口/营养）**——这是本功能的差异化价值。

[v1.1] 与 v1.0 的定位差异：食材入库质量对齐 AUTOGEN-UNIFY 后的"一条链路"标准——链接导入的新食材与 AI 记一餐/快速自建走**同一条统一管线**（归一→dedup→分类→营养预估→food_group 一次做齐），不再是"有分类无营养"的裸入库。

MVP 范围：仅下厨房一个来源 + 预设正则解析 + 基础链接列表 + 存为菜品。AI 解析、多来源、批量操作放 Phase 2。

#### 解析流程伪代码（v1.1.1·行配对算法）

```kotlin
// RecipeParser.kt (shared) —— 输入为 WebView 层一次 JS 提取的 ExtractedPage（§3.3）
fun parse(page: ExtractedPage, config: ParseConfig): ParsedRecipe {
    // 1. 菜名：优先 DOM h1 值（ExtractedPage.title）；空则 innerText 兜底（过滤噪音行）
    val title = page.title.ifBlank { fallbackTitle(page.innerText, config.title) }

    // 2. 食材清单：用料区（sectionStart~sectionEnd 之间）行序列扫描，行配对
    //    名行+下一行匹配 quantityPattern → 配对成功（名, 数量, 单位）
    //    名行+下一行不匹配 → 无量食材（如"盐⏎适量"里"适量"也是 quantity 行；
    //    真正无量的食材罕见，Phase1 按"名行后无数量行则数量=0/单位=适量"兜底）
    val ingredientLines = sectionBetween(page.innerText, config.ingredients)
    val ingredients = mutableListOf<ParsedIngredient>()
    var i = 0
    while (i < ingredientLines.size) {
        val name = cleanIngredientName(ingredientLines[i]) // 去括号说明："猪肉馅（…）"→"猪肉馅"
        val qty = ingredientLines.getOrNull(i + 1)?.takeIf { it.matches(quantityPattern) }
        ingredients.add(ParsedIngredient(name, parseQuantity(qty), parseUnit(qty)))
        i += if (qty != null) 2 else 1
    }

    // 3. 步骤：的做法步骤~菜谱创建时间 之间，以"^步骤 N$"标记行分块
    //    每块=标记行之后到下一标记行/区尾的所有非空文本行（图片不进 innerText·天然干净）
    //    Phase1 不做内容级过滤（成品感言行保留原文，用户可删——宁全勿缺）
    //    [v1.1.3] 步骤图：ExtractedPage.stepImages（WebView 层 DOM 查询·按步骤序对位）
    //    与文本按 index 配对成 ParsedStep(text, imageUrl)；某步无图 imageUrl=""
    val stepTexts = splitByMarkers(sectionBetween(page.innerText, config.steps), config.steps.itemStart)
    val steps = stepTexts.mapIndexed { i, t -> ParsedStep(t, page.stepImages.getOrNull(i).orEmpty()) }

    // 4. [v1.1] 烹饪方式推断：菜名+步骤全文合并跑共享字表（§3.4）
    val cookingMethods = CookingMethodInferrer
        .inferFromName(title + steps.joinToString(""))

    // 5. 封面图：ExtractedPage.imageUrl（WebView 层 DOM 查询 og:image）
    // 6. 作者碎碎念 → note（可选预填 description）
    return ParsedRecipe(title, ingredients, steps, cookingMethods, page.imageUrl, note)
}
```

### 3.3 页面提取策略（v1.1.1：结构化字段走 DOM 查询 + 块文本走 innerText）

WebView 加载完成后**一次 JS 注入**同时取结构化字段与块文本，返回一个 JSON（避免多次 `evaluateJavascript` 往返与 innerText 噪音依赖）：

```kotlin
// WebViewTextExtractor.kt (androidApp·薄层)
val js = """
    JSON.stringify({
        title: document.querySelector('h1')?.textContent?.trim() || '',
        author: document.querySelector('meta[name="author"]')?.content || '',
        imageUrl: document.querySelector('meta[property="og:image"]')?.content || '',
        // [v1.1.3] 步骤图（真实 DOM：#steps > #step-cover-0~N > img·用户提供 2026-09-03）：
        // 按块 id 数字序排列（与 innerText 步骤文本序对齐）；兼容懒加载 data-src
        stepImages: [...document.querySelectorAll("[id^='step-cover-']")]
            .sort((a, b) => (parseInt(a.id.replace(/\D/g, '')) || 0) - (parseInt(b.id.replace(/\D/g, '')) || 0))
            .map(el => el.querySelector('img')?.currentSrc || el.querySelector('img')?.src
                        || el.querySelector('img')?.getAttribute('data-src') || ''),
        innerText: document.body.innerText
    })
"""
webView.evaluateJavascript(js) { json ->
    val page = ExtractedPage.fromJson(json)  // title/author/imageUrl/innerText 四字段
    repo.updateClearText(linkId, page.innerText)  // 落库 clear_text（复验/重解析用）
    parseRecipe(page, config)  // 触发解析（§3.2 伪代码）
}
```

- 菜名走 `h1` DOM 查询（innerText 首行是「用APP打开」等噪音——v1.0 取第一行的假设不成立）
- 作者/封面走 DOM/meta；**作者值在「作者：」的下一行**（innerText 正则跨行兜底，meta author 若有则优先）
- 用料/步骤两大块走 innerText 正则（行配对/标记分块，见 §3.2）
- 图片 URL 不走 innerText；**步骤图 alt 是懒加载占位错误文案**（每步 alt 均为「纯奶手撕吐司的做法 步骤1」），Phase1 不做步骤图

### 3.4 [v1.1] 烹饪方式推断（复用共享组件·不自创）

**复用 `CookingMethodInferrer.inferFromName(dishName: String): List<String>`**（`shared/.../domain/CookingMethodInferrer.kt`·AUTOGEN-UNIFY STEP-AU-6 交付）：

- 字表 18 字（炒/煮/蒸/炸/煎/烤/炖/拌/烧/焖/卤/熘/焗/烩/涮/煲/炝/熬·冻结值），菜名含任一字即命中
- **输入 = 菜名 + 步骤全文拼接**：菜名常无方式字（汤/羹/煲仔类），步骤文本是更可靠的方式来源（"大火煮10分钟"→煮、"转小火炖"→炖）
- **输出与烹饪方式字典交集过滤**：18 字中仅 炒/煮/蒸/炸/煎/烤/炖/焖/卤 在预设字典（字典名"凉拌"非"拌"），交集为空则 cookingMethods 为空——与 `NewDishViewModel.updateCookingMethodPreselect` 的过滤口径**完全同源**（GC-12：UI 判据与业务同源）
- 交集为空时的兜底：预填菜名后 `applyPrefill` 内既有的菜名推断预选自动跑（v1.1 零成本兜底链，见 §4.4）

### 3.5 基准样本与模板迭代兼容（v1.1.3·用户确立）

**基准样本**：`m.xiachufang.com/recipe/106889995/`（巨鲜美的冬瓜丸子汤·2026-09-03 实抓）——下厨房解析模板（配置 version 3）的**定稿锚点**。

## 附一：关键踩坑红线

1. **SQLDelight 迁移文件名 = 目录最大号+1**：现有最大 32.sqm（2026-09-03 复核·AUTOGEN-UNIFY 零迁移）→ 新建 33.sqm

6. **WebView 必须在后台运行、不可见**：用户界面只看到 BottomSheet
7. **表 `.sq` 不加列无需 .sqm**：纯新查询不改表结构
8. **CRLF 文件正则注意**：`perl` 用 `$` 锚行尾在 CRLF 匹配不到
9. **[v1.1] `ensureCreated` 新增调用方须过架构审**（其 KDoc 明示）——Phase1 蓝图须引用本方案 §六 作为过审依据
10. **[v1.1] save() source 参数化时默认值必须保持 `"user"`**——搜索新建/食材组成菜品等既有调用点行为零回归（AUTOGEN-UNIFY AF-AU-01 三处门控不回退）
11. **[v1.1] 预填多值做法走 `addCookingMethod(markUserTouched=false)`（置 `cookingMethodImported`）**——禁绕过直接改 `cookingMethodNames`（会被菜名推演覆盖·AUTOGEN-UNIFY INV-AU-12 同族约束）；菜名推演跳过条件=`touched || imported`（Apple-UX C.3 精化：导入值不被覆盖 + 提示行诚实区分来源）
