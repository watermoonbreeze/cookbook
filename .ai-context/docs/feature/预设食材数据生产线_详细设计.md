## 一、现有 seed 数据现状（映射基础·先摸清）
预设食材数据当前分散在多个 seed 文件，按 `code`/`name` 关联：

| 文件 | 主键/关联键 | 字段 | 归属管线数据类 |
|---|---|---|---|
| `ingredients.json` | `code`(唯一) | code, name, alias?, unit, emoji, categories[](分类code+特征标签如 gi_high/fiber_high) | **元数据** |
| `ingredient_nutrition.json` | `ingredient`(=name) | kcal, protein, fat, carb, fiber, sodium, potassium, calcium, gi, purine, saturatedFat?, cholesterol?, pieceGram?, ref, review | **营养素** |
| `ingredient_care_rules.json` | `ingredient`(name)+`category` | ingredient, category(care_diabetes/care_pregnancy/…), level(avoid/limit/recommend), reason, ref? | **健康忌口** |
| `crowd_rules.json` | `crowd`+`ingredient`(name) | crowd(高尿酸/高血压…), ingredient, level, reason | **健康忌口** |
| `ingredient_attributes.json` | `name` | {name: [属性标签]}(CONTAINS_ALCOHOL/PROCESSED_FRUCTOSE…) | **属性(忌口中间层)** |
| `ingredient_details.json` | `ingredient`(name) | commonMethods, prepTips… | 元数据(技法·可后期) |

**关键观察**：
- 元数据主键是 `code`(英文)，营养/care/属性却按 `name`(中文) 关联 → staging 要维护 `code↔name` 映射，name 作为跨文件关联键需去空格归一（沿用现有 `name_key` 思路）。
- `categories[]` 混装了两类：真·分类(staple/staple_grain_rice) + 特征标签(gi_high/fiber_high/whole_grain) → staging 分开存（category vs feature_tag），避免混淆。
- **本期聚焦食材三类数据**（元数据/营养/忌口+属性）；菜品(`dishes.json`)、字典(单位/food_category)、药食同源(`yaoshi_tongyuan.json`) **不在本管线**，另议。

## 二、staging DB 完整 schema（sqlite·带溯源）
> 独立于生产 SQLDelight schema（不同构）。每张业务表都带 `source / confidence / collected_at / status`。

```sql
-- 食材主表(元数据)
CREATE TABLE ingredient (
  id INTEGER PRIMARY KEY,
  code TEXT UNIQUE,               -- 英文唯一码(对齐 ingredients.json.code)
  name TEXT NOT NULL,             -- 中文名
  name_key TEXT NOT NULL,        -- 去空格/归一化名(跨文件关联键)
  alias TEXT,
  unit TEXT DEFAULT 'g',
  emoji TEXT,
  piece_gram REAL,               -- 计件默认克重(从 nutrition.pieceGram 归并到元数据更合理)
  priority_tier INTEGER,          -- 1健康覆盖 / 2家庭常见 / 3其他
  source TEXT,                    -- 数据来源(现有seed/USDA/CN成分表/人工)
  status TEXT DEFAULT 'candidate',-- candidate候选 / imported已录 / published已发布
  collected_at TEXT
);

-- 食材↔分类(真·分类)
CREATE TABLE ingredient_category (ingredient_id INT, category_code TEXT);
-- 食材↔特征标签(gi_high/fiber_high/whole_grain…)
CREATE TABLE ingredient_feature (ingredient_id INT, feature_tag TEXT);
-- 食材↔属性标签(CONTAINS_ALCOHOL/PROCESSED_FRUCTOSE…·忌口中间层)
CREATE TABLE ingredient_attribute (ingredient_id INT, attribute TEXT);

-- 营养素(每字段独立溯源·因不同字段可能来自不同源)
CREATE TABLE nutrient (
  id INTEGER PRIMARY KEY,
  ingredient_id INT,
  field TEXT,                     -- kcal/protein/fat/carb/fiber/sodium/potassium/calcium/gi/purine/saturatedFat/cholesterol
  value REAL,
  unit TEXT,                      -- 值单位(kcal, g/100g, mg/100g, 指数)
  source TEXT,                    -- USDA-FDC#id / 中国食物成分表6版 / 悉尼GI库 / 二手站名
  confidence TEXT,                -- high(一手) / mid(交叉/权威近似) / low(二手)
  review TEXT,                    -- verified / pending
  collected_at TEXT
);
-- 说明: 用"长表(每字段一行)"而非宽表, 便于逐字段溯源/交叉校验/增量补; 导出时再 pivot 回宽表 seed。

-- 健康/生命阶段忌口规则(指南驱动·人工核)
CREATE TABLE care_rule (
  id INTEGER PRIMARY KEY,
  ingredient_id INT,
  condition TEXT,                 -- care_diabetes/care_pregnancy/… 或 crowd(高尿酸…) 统一口径
  scope TEXT,                     -- 'care'(生命阶段/慢病category体系) / 'crowd'(人群体系)
  level TEXT,                     -- avoid/limit/recommend
  reason TEXT,
  guideline_source TEXT,          -- 指南名+机构+年
  guideline_quote TEXT,           -- 指南原文摘录(守"规则非数据")
  reviewed INTEGER DEFAULT 0,     -- 人工核过=1
  status TEXT DEFAULT 'candidate',
  collected_at TEXT
);

-- 校验标记(质量门产出)
CREATE TABLE review_flag (
  id INTEGER PRIMARY KEY,
  ingredient_id INT, field TEXT,
  issue TEXT,                     -- 离群/单位/缺一手/USDA-CN差异/引用完整性
  detail TEXT, resolved INTEGER DEFAULT 0
);

-- 中↔英食材名映射(USDA采集用·人工种子表逐步扩)
CREATE TABLE cn_en_map (
  name_key TEXT PRIMARY KEY, en_query TEXT, fdc_id INT,
  match_note TEXT, confirmed INTEGER DEFAULT 0
);
```

## 三、导入映射规范（现有 seed → staging）
逐文件映射规则（P0 导入器 `import_seed.py` 按此实现）：

1. **`ingredients.json` → `ingredient` + `ingredient_category` + `ingredient_feature`**
   - code/name/alias/unit/emoji → `ingredient` 同名字段；`name_key` = 归一化(name)；`source='seed'`, `status='imported'`。
   - `categories[]` 拆分：命中"特征标签白名单"(gi_high/gi_mid/gi_low/fiber_high/whole_grain/nutrition_*…) → `ingredient_feature`；其余 → `ingredient_category`。
2. **`ingredient_nutrition.json` → `nutrient`(长表) + 回填 `ingredient.piece_gram`**
   - 按 `ingredient`(name) → name_key 关联到 ingredient.id。
   - 每个营养字段拆成一行 `nutrient(field,value,unit,...)`；`unit` 按字段固定(kcal/‘g/100g’/‘mg/100g’/指数)。
   - `source` 从原 `ref` 解析(尽量识别"中国食物成分表/USDA/悉尼GI/二手站")；`confidence`：ref 含"成分表/USDA/nlc"→high，"悉尼GI/综述"→mid，二手站→low；`review` 沿用原 `review`(verified/pending)。
   - `pieceGram` → 回填 `ingredient.piece_gram`(元数据)。
3. **`ingredient_care_rules.json` → `care_rule`(scope='care')**
   - ingredient(name)→id；condition=category；level/reason 直填；`guideline_source` 从 ref 提取(可空→待补)；`reviewed=1`(现有已人工整理)；status='imported'。
4. **`crowd_rules.json` → `care_rule`(scope='crowd')**
   - crowd→condition；ingredient(name)→id；level/reason 直填。
5. **`ingredient_attributes.json` → `ingredient_attribute`**
   - {name:[tags]} 展开成行。

**关联失败处理**：name_key 在 ingredient 表找不到的 nutrition/care/attribute 行 → 记 `review_flag(issue='引用完整性')`，不静默丢（正好首校揪出"营养/care 引用了不存在食材"的问题）。

## 四、导出规范（staging → 等价 seed）
`export_seed.py` 把 staging 反向导出成与现有格式**逐字段等价**的 seed JSON：
- `ingredient` + category/feature → 重建 `ingredients.json`(categories[] 合并回分类+特征)。
- `nutrient` 长表 pivot 回宽表 → 重建 `ingredient_nutrition.json`(字段顺序/精度对齐原文)。
- `care_rule`(scope='care') → `ingredient_care_rules.json`；(scope='crowd') → `crowd_rules.json`。
- `ingredient_attribute` → `ingredient_attributes.json`。
- **只导出 `status='published'`(或首校期 imported)** 的数据。

## 五、首校 / roundtrip 验证（P0 核心价值）
`verify_roundtrip.py`：**现有 seed → 导入 staging → 导出 seed' → diff(seed, seed')**，期望**语义等价**(允许 key 排序/浮点格式差异，用规范化后 diff)。
- diff 为空 → 管线无损、链路可信。
- diff 非空 → **正是首校要揪的问题**：字段精度丢失、ref 解析不全、categories 拆分规则漏项、name_key 关联歧义(同名多义)、营养/care 引用了不存在食材。逐条记 `review_flag` 供人工看。
- **产出首校报告**：`review_flag` 汇总(引用完整性 N 条、低置信度营养 N 条、缺 guideline 的 care N 条…) → 这就是现有数据的"体检单"。

## 七、P1 · USDA 采集详细（拿到 key 后）
- **⚠️ 前提·连通性（2026-07-23 实测）**：采集机须能访问 `api.nal.usda.gov`——**中国大陆直连该 API 常失败（超时/ECONNREFUSED/HTTP 000）·需代理或 VPN**。跑脚本前先浏览器打开 search URL 验证 key + 连通（返回含 `foods` 的 JSON=OK）。**若长期无代理→P1 需备选**：手动/半自动导出 USDA 数据、或换可连通的营养 API、或该批直接走中文成分表源。此前提不通则"USDA 主干"无法自动化，务必先解决。
- **API**：`GET https://api.nal.usda.gov/fdc/v1/foods/search?api_key=KEY&query=<en>&dataType=SR%20Legacy,Foundation`；取命中食物的 `foodNutrients[]`。
- **字段映射**(USDA nutrientId/name → staging field)：Energy(kcal)→kcal、Protein→protein、Total lipid(fat)→fat、Carbohydrate→carb、Fiber→fiber、Sodium(Na)→sodium、Potassium(K)→potassium、Calcium(Ca)→calcium、Fatty acids total saturated→saturatedFat、Cholesterol→cholesterol。(USDA 无 GI/嘌呤 → 仍靠既有中文/文献源)。
- **A/B 分类**：先查 `cn_en_map` 有无该食材英文映射；有→USDA 拉(A类)，无→标记为 B 类(中式/加工/调料·走中文成分表·人工补)。
- **中英映射表**：`cn_en_map` 人工种子起步(大米→rice/白菜→chinese cabbage…)，逐步扩；`confirmed=1` 才用于自动拉。
- **写入**：USDA 值写 `nutrient`(source='USDA-FDC#fdcId', confidence='high', review 视交叉结果)；**不覆盖已有 high 置信度中文一手值**，而是并存+交叉校验(第八节)。

## 八、校验门规则清单（校验层）
1. **交叉校验**：同字段 USDA vs 中文源 相对差 >阈值(如营养素 >25%) → `review_flag(USDA-CN差异)`。
2. **离群检测**：同 category 内某字段偏离中位数 >N倍MAD → 标记(捕获"生蚝钙131"类)。
3. **单位/量纲**：钠/钾/钙/胆固醇 mg、蛋白/脂/碳/纤维/饱脂 g、gi 0-100、purine mg → 越界标记。
4. **合理性**：fiber≤carb、saturatedFat≤fat、各宏量非负、kcal 与宏量估算不背离过大。
5. **引用完整性**：care/attribute/nutrient 的食材必须存在于 ingredient 表。
6. **一手性**：confidence=low(仅二手) → review 强制 pending，不发布为 verified。
7. **忌口红线**：care_rule 无 `guideline_source/quote` 或 `reviewed=0` → 不发布(守"规则非数据·人工核")。

## 九、发布层详细（预制 db + 增量 seed 并存）
- **发布器 `publish.py`**(P4)：只取 `status='published' + 过校验门` 的数据。
- **产物1 预制 db**：把 staging 映射成**生产 SQLDelight 表结构**(需一个 staging→生产 schema 映射器)，导出 `preset.db` → 放 `androidApp assets`；全新装直接 attach/copy 作基础库。
- **产物2 增量 seed**：导出成现有格式 seed JSON(第四节) → 覆盖 `shared/.../seed/`；沿用**指纹重跑 + upsert** 机制，老用户增量更新、不动自建数据。
- **版本**：发布打 `data_version`；seed 侧继续用内容指纹；预制 db 带同一 data_version 供首装比对。
- **与现有衔接**：首次发布 = 用 staging 重新生成一份和现在等价的 seed(首校已保证等价) → 平滑切换，后续所有预设数据改动都从 staging 走。

## 十、P0 交付清单与验收标准
**交付**：`data-pipeline/` 目录 + 六脚本 + schema + 特征标签白名单 + 首校报告。
**验收**：
1. `build_staging.py` 建库成功、schema 与本文一致。
2. `import_seed.py` 导入现有全部食材/营养/care/crowd/attribute，关联失败项进 review_flag。
3. `verify_roundtrip.py` 跑出 diff=空(语义等价) **或** 输出可解释的首校报告(每条 diff 有归因)。
4. 首校报告 `首校体检报告.md` 作为**现有数据体检单**交付(引用完整性/低置信度/缺 guideline 统计·**每条附详细修复方法**·本期只诊断不改 seed)。
**验收即证明**：整条"采集→存储→发布"链路对现有数据无损，可放心在此之上扩量(P1+)。

## 十一、拍板定论（2026-07-23 用户定·方案冻结）
1. **`staging.db` 纳入 git**：留数据快照可追溯（不 gitignore）。
2. **首校揪出的问题 = 只出「体检单 + 每条详细修复方法」，本期不修数据**：`verify_roundtrip.py` 产出结构化报告(问题分类/条数/每条归因 + 建议修复方式)，写成 `data-pipeline/首校体检报告.md`；**不改任何 seed**（修复留后续按体检单单独走"改seed→指纹重跑"）。
3. **忌口指南清单按现有病种/生命阶段来**（糖尿病/高尿酸/高血压/高血脂 + 孕/婴/哺乳/学龄前/学龄）。用户提的心脏病/老年人 = **验证"加任意 condition 分类→跑管线→快速产出"的可扩展性**(核心设计目标)，不是本期内容。
   - → **设计含义**：采集器3 与 care_rule 表须做到 **condition 配置驱动**——新增一个 condition(病种/生命阶段) 只需补该 condition 的指南清单配置，管线自动产出其 care_rule，**不改脚本代码**。这是本管线的关键复用能力，P3 设计须满足。
