# 跨平台架构策略（数据驱动 UI 准则评估 + 多平台路线）

> [2026-07-21] 用户质疑"数据驱动 UI"准则是否最优、要求评估含 iOS/Android/鸿蒙/macOS/Windows 的跨平台架构。由 `google_architecture_engineer`(规模/规范) + `apple_architect`(平台契合/反过度设计) 会诊，两方跨工程文化**高度收敛**。本文是结论沉淀；准则条款见 CLAUDE.md「架构与代码质量准则」。

## 一、核心结论：数据驱动 UI 准则「合理·正确·无更优替代」，但需正名

**用户把两个正交层级合并了**（会诊一致最重要结论）：

| 轴 | 问题 | UDF 是否属于此 |
|---|---|---|
| **A · UI 层范式** | 单个界面内状态怎么流动（单一真相源·State 下行·Event 上行） | ✅ UDF 在这里 |
| **B · 跨平台共享边界** | 哪些代码写一次多端复用、哪些各端各写 | ❌ 与 UDF 无关 |

- **UDF 是轴 A 的 UI 层原则**，对 Compose/SwiftUI/ArkUI/Compose Desktop **每种声明式 UI 都成立且最优**（声明式 UI 天然要求 UDF）。命令式 MVP / 双向绑定 MVVM 反而制造状态撕裂——正是踩坑红线里"草稿 vs DB 回灌打架""重建 UiState 丢字段"这类竞态的温床。**无更优替代**；全量上 MVI/Redux-like 是过度设计（本项目无此规模痛点，仅极复杂状态机页面才值得 reducer）。
- **落地 = MVVM**：VM 暴露 `StateFlow<UiState>`（Android）；**状态载体各端原生**（iOS `@Observable`/`@State`·别把 `StateFlow` 强加给 Swift）。

## 二、跨平台共享边界：共享逻辑、不共享像素（两方一致）

- **共享甜点区 = Domain + Data**：业务规则（纯 Kotlin 无平台依赖 + 单测）+ Repository（暴露 `Flow`/`suspend` 平台中立接口）。**现状已达标**（`HealthRuleEngine`/`MealCompositionScorer`/`NutritionInterpreter`/`IngredientCrowdCare`/推荐算法 全在 `shared`）。这是 KMP 最大价值，也是共享**天花板**。
- **薄表现层 + 原生 UI**：VM 只做状态编排+生命周期、业务调 shared UseCase（**薄 VM = 未来上移最优低成本预留**）；UI 各平台原生（不追求像素级共享·保体验契合=本 App 核心竞争力"顺手"）。
- **判据**："能脱离任何 UI 框架、无平台 UI/导航/生命周期概念"的才进 `shared`，沾了 UI/导航/生命周期就留该端。

## 三、平台路线表

| 平台 | UI 层 | 逻辑共享 | 现在做? | 备注 |
|---|---|---|---|---|
| **Android** | Compose 原生（现状） | shared KMP | ✅ 唯一交付 | 标准答案·不动 |
| **iOS** | 原生 SwiftUI + `@Observable` | shared KMP（SKIE 桥 Flow→async） | 立项再定 | **非 CMP**·非 TCA |
| **macOS** | 原生 SwiftUI（与 iOS 共享视图·Swift 世界内部） | shared KMP | 更远 | 非 CMP Desktop |
| **鸿蒙** | ArkUI 原生 | **Kotlin 不通**·ArkTS 重写/桥接 | **不投入** | 预留即负债 |
| **Windows** | Compose Desktop 可接受 | shared KMP | YAGNI | 桌面容忍度高·唯一 CMP 松口处 |

**鸿蒙现实**：HarmonyOS NEXT（ArkTS/ArkUI）已去 AOSP、自成生态，KMP 无 target、Kotlin/Native 无鸿蒙后端——**"Kotlin 共享到鸿蒙"目前不成立**。真要上：ArkUI 原生 UI + ArkTS 重实现业务规则（维护双份·高技术债）或消费共享后端（需先云端化）。**核心规则保持纯 Kotlin+单测**，是将来万一人肉翻译成 ArkTS 唯一的降本项——已在做。触发再评估的两信号：①鸿蒙用户量对本 App 有商业意义 ②出现成熟 Kotlin→鸿蒙互操作。

**CMP-iOS 为何默认否决**（Apple 视角·逐条硬伤）：非原生控件（Skia 自绘·滚动惯性/橡皮筋/文本选择/Dynamic Type 失真）、手势（滑动返回肌肉记忆难复刻）、**无障碍 VoiceOver 缩水**（中老年/慢病用户=实打实流失）、系统集成（分享/Widget/Live Activity/Siri）。本 App 命门=顺手，恰是 CMP 最难保证处，与 CLAUDE.md"家庭高频操作尤其要顺手"直接冲突。

## 四、唯一分歧（记录·iOS 立项时定）

**iOS 表现层要不要上移 `commonMain` 共享？**
- **Apple 立场**：永远原生。Swift 消费 Kotlin `StateFlow` 别扭（需 SKIE/手写桥·丢 `@Observable` 细粒度依赖追踪）；presentation 恰是各端差异最大层（导航/生命周期/手势/无障碍）。**各写一份 ViewModel=看似重复实为契合**。
- **Google 立场**：iOS 立项时升 Kotlin 2.0+，可用**官方 KMP ViewModel**（androidx.lifecycle 主线·迁移面最小）把薄 VM 下移 commonMain、SwiftUI 订阅同一 VM，换多端行为一致 + `commonTest` 可测。
- **收敛**：**两方都同意现在不做**（iOS 空壳·Kotlin 1.9.20 不够·无反馈闭环=过度设计）。**默认取 Apple 的"原生 presentation"**（本 App 体验敏感）；但因两方都要"薄 VM"，无论将来走哪条路成本都低——**保持薄 VM 即把这个决策廉价地推迟到 iOS 真立项**。

## 五、唯一"现在就该做"的跨平台动作

**保持 VM 薄 + 持续把业务逻辑下沉 `commonMain` + 单测。** 这一件事同时服务 iOS/桌面/甚至鸿蒙移植，零投机风险，是所有未来平台的**公约数**。其余（VM 上移、CMP、Decompose/MVIKotlin/moko、导航共享）都等对应平台真立项再决策——**不为不存在的消费者提前抽象**。

**关联技术债**：`navigation-compose` 是 Android 专属；未来若共享表现层，导航是第二个要上移项（届时评估 Decompose）。现无需动，登记备查。Kotlin 1.9.20 是跨平台前提（KMP ViewModel/CMP 稳定/Swift 互操作改善都在 2.0+），iOS 立项先升级。
