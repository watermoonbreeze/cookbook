> 上位方案见 `端侧AI能力接入方案.md`（架构/安全边界/场景分级），本文只聚焦这一个场景的可编码设计。

## 一、场景定义

**用户故事**：我打开 App，想知道"用我现有的食材，今天下一餐吃什么"。App 结合我**在手食材 + 健康忌口 + 最近吃过的**，给 3 个**可做、不犯忌、不重复**的组合，每个附一句人话理由和用到的在手食材；我可以「换一换」或选一个直接落到记一餐/菜品选择。

**边界**：
- 只在**本地已有菜品/食材**范围内推荐，模型**不凭空生成**不可选的菜。
- 忌口/过敏/慢病硬约束**由代码强校验**，模型输出只是候选，过不了规则的一律剔除。
- 失败可**回退**到现有手动"添加餐食"，不阻塞核心链路。
- 不做医疗处方定性，文案定位"饮食建议辅助"。

## 二、云端 vs 端侧 对比分析（本方案关键决策）

### 2.1 逐维对比

| 维度 | 云端 LLM API | 端侧小模型(LiteRT-LM/Gemini Nano) |
|---|---|---|
| **输出质量/JSON 稳定性** | 高（大模型，中文与结构化输出稳） | 中低（0.5B~2B，JSON 可解析率需 POC 验证，易跑偏） |
| **隐私（敏感健康数据）** | 数据出设备——需最小化传输+用户授权 | **最佳**，数据不出设备 |
| **工程量/周期** | 小（HTTP + JSON，天级） | **大**（runtime 抽象+模型分发+适配+碎片化，数周级） |
| **成本** | 按调用付费（低频推荐场景很便宜） | 一次性集成成本高，运行零费用 |
| **离线可用** | 否（需联网） | **是** |
| **设备门槛** | 无（任何设备） | 高（内存/算力，低端机跑不动或很慢） |
| **首包体积** | 无（不打模型） | 模型 100MB~1GB，需下载/导入引导 |
| **迭代速度** | **快**（换 prompt/换模型即时生效） | 慢（换模型要重新分发） |
| **合规** | 选国内合规厂商 API（数据境内） | 无外传，天然合规 |

### 2.2 关键判断

- 本场景**调用频率低**（一天几次），云端 API 成本可忽略；而它的**质量和迭代速度优势明显**——这正是"先验证用户到底吃不吃这套 AI"最需要的。
- 隐私风险**可控而非无解**：推荐只需要传**在手食材名 + 忌口大类标签 + 最近菜名**，**不传**完整体检/病史/身份。把"约束"抽象成粗标签（如"忌高嘌呤、低钠"）即可，敏感度大幅下降。
- 端侧的价值在**离线 + 极致隐私**，是很好的**后续差异化卖点**，但作为**首轮**投入产出比差（数周工程 + 质量没保证，可能验证不出产品价值就先耗死在工程上）。

### 2.3 推荐：**云端优先验证价值 + 端侧作为 P2 隐私增强（同一抽象层，可切换）**

- 用 `AiRuntime` 抽象把"模型怎么来"隔离掉，**业务层不关心云/端**。首轮实现云端适配器，端侧适配器后补，**切换不动业务代码**。
- 云端**优先免费厂商**：首选 **智谱 GLM-4-Flash**（当前**免费**、中文强、JSON 稳定、数据境内合规）；备选免费档 **讯飞星火 Lite / 百度 ERNIE-Lite**。抽象层统一，哪个免费/额度够用就用哪个，`AiRuntime` 换实现即可，不动业务。
- 传输**最小化**：只发食材名 + 粗约束标签 + 最近菜名；本地日志不记完整档案（沿用上位方案安全边界）。
- 端侧路线**并不废弃**：`AiRuntime` 留好口子，后续按 `端侧AI能力接入方案.md` 第 1 步接 LiteRT-LM。

> 一句话：**架构对云/端中立，首轮走云端把价值和交互跑通，端侧作为隐私版后续接入。**

## 三、推荐算法：规则先筛 + 模型组合解释（安全核心）

不把"要不要犯忌"交给模型判断，而是**代码先筛出安全可做的候选，模型只在安全集里做组合、排序、讲人话**。

```
① 取数据      在手食材 / 健康忌口 / 最近N餐 / 菜品库(含 dish_ingredient)
      ↓
② 规则先筛     HealthRuleEngine：
   (纯代码)    - 可做性：**主料(is_main=1)全部在手即算可做**（辅料缺不影响可做，只影响做法）
              - 犯忌过滤：菜品含 avoid 等级食材/命中忌口大类 → 剔除
              - 去重：最近N餐出现过 → 降权/剔除
              → 得到「安全候选菜品集」+ 每个的(在手主料、在手辅料、缺失辅料、命中规则)
      ↓
③ 模型组合     只把安全候选集 + 约束摘要喂给模型：
   (LLM)      「从这些候选里搭 3 个下一餐组合(每餐 2~3 菜)，各写一句理由；
              **根据在手辅料的多少给出对应做法建议**(如有葱姜→红烧，只有主料→清蒸)」
              输出严格 JSON（dish id 必须来自候选集）
      ↓
④ 校验+兜底    JSON schema 校验；dish id 不在候选集→丢弃；
              不足3个→用规则打分 top 补齐；模型全挂→纯规则兜底出结果
      ↓
⑤ 落地         3 张候选卡(理由/在手食材/缺什么) → 换一换 / 选一个 → 记一餐 or DishPicker
```

**要点**：即使模型完全失效，② + ④ 也能纯规则出一版推荐——AI 是"锦上添花的组合与解释"，不是"正确性的保证方"。

## 四、分层与代码落点

沿用 `shared`(平台无关) / `androidApp`(运行时+UI) 划分：

### shared（commonMain，可单测）
| 单元 | 职责 |
|---|---|
| `ai/model/` DTO | `PantrySnapshot`、`HealthConstraints`、`RecentMeals`、`DishCandidate`、`MealSuggestion`、`RecommendationDraft` |
| `ai/AiRuntime`(interface) | `suspend fun complete(request: LlmRequest): Result<String>`（云/端各自 actual/实现） |
| `ai/RecommendationOrchestrator` | 取数→构造 prompt→调用 runtime→schema 校验→映射草案→交给规则层复筛 |
| `ai/HealthRuleEngine` | **纯函数**：可做性/犯忌/去重过滤 + 打分；复用 `crowd_ingredient`、健康档案忌口大类、`dish_ingredient` |
| `ai/PromptBuilder` + schema | 构造中文 prompt、定义并校验输出 JSON schema |

### androidApp
| 单元 | 职责 |
|---|---|
| `ai/CloudAiRuntime` | 实现 `AiRuntime`：HTTP 调国内 LLM API（key 管理、超时、重试、错误归一） |
| （后续）`ai/OnDeviceAiRuntime` | LiteRT-LM 适配器，P2 |
| `ui/.../AiRecommendScreen`/入口 | 触发、loading、3 候选卡、换一换、落地到记餐/DishPicker |
| ViewModel | 调 Orchestrator、状态管理、失败回退 |

- 模型输出必须先过 schema 再转业务对象；写操作（真正记一餐）**用户确认后**才落库。
- 依赖注入沿用 Koin：`AiRuntime` 在 `androidModule` 绑定云端实现。

## 五、数据契约（草案）

```kotlin
// —— 输入上下文（发给模型的都最小化、脱敏）——
data class RecommendationContext(
    val pantry: List<String>,          // 在手食材名
    val constraints: List<String>,     // 粗约束标签，如 "忌高嘌呤","低钠","少油"
    val recentDishNames: List<String>, // 最近N餐菜名(去重用)
    val candidates: List<DishCandidate>,
)
data class DishCandidate(
    val id: Long, val name: String,
    val mainOnHand: List<String>,      // 在手主料(可做性=主料齐)
    val secondaryOnHand: List<String>, // 在手辅料(决定做法)
    val secondaryMissing: List<String>,// 缺的辅料(可提示/换做法)
)

// —— 模型输出（严格 JSON，dishIds 必须来自 candidates）——
data class RecommendationDraft(val suggestions: List<MealSuggestion>)
data class MealSuggestion(
    val dishIds: List<Long>,           // 这一餐的菜(2~3 个搭配)
    val reason: String,                // 一句人话理由
    val cookingHint: String? = null,   // 按在手辅料给的做法建议(可空)
)
```
输出 JSON schema（示意）：`{ suggestions: [ { dishIds: number[], reason: string, cookingHint?: string } ] }`，Orchestrator 校验：可解析、dishIds ⊆ candidates、每餐 2~3 菜、组合数截到 3。

## 六、交互设计

- **入口（都要）**：① 首页"下一餐"区卡片 + ② 添加餐食页顶部「🤖 AI 推荐」按钮（无网/AI 关闭时置灰或隐藏）。
- **加载**：云端调用 1~3 秒，显示"正在为你搭配…"骨架。
- **结果**：3 张候选卡，每张显示【菜名组合】+【一句理由】+【用到的在手食材(高亮)】+【缺 X 食材(如有)】。
- **操作**：每卡「选它」→ 带入记一餐/DishPicker 选择态；底部「换一换」重新推荐；「都不满意」→ 转手动。
- **失败**：toast「AI 暂不可用，已切换手动」+ 直接进手动添加，不卡流程。
- **合规文案**：卡片底部小字"仅为饮食建议参考，禁忌以你的医嘱为准"。

## 八、风险与回退

- **模型乱推荐犯忌菜**：规则层在模型前后各筛一次（②预筛、④校验 dishId 合法性 + 复筛），模型无权绕过。
- **JSON 不稳定**：schema 校验 + 不足补齐 + 全失败纯规则兜底。
- **无网/低端机**：回退纯规则推荐或手动。
- **隐私**：只传脱敏摘要；日志不记完整档案；云端选境内合规厂商；后续端侧版彻底不外传。
- **候选太少**（库存少/菜品库小）：放宽可做性阈值 or 提示"补充库存/菜品"。

## 九、已定决策（2026-07-08 评审）

1. **云端厂商**：优先免费——首选 **智谱 GLM-4-Flash**（免费/中文/JSON/境内），备选讯飞星火 Lite、百度 ERNIE-Lite；抽象层可换。
2. **可做性**：**主料(is_main=1)齐即可做**；辅料多少 → 模型给不同做法建议（cookingHint）。用现有 `dish_ingredient.is_main`，无需改表。
3. **入口**：**都要**——首页"下一餐"区 + 添加餐食页 AI 推荐按钮。
4. **一餐规模**：**2~3 菜搭配**一餐。
