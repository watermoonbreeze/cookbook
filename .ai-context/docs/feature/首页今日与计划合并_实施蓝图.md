## 3. 审核结论摘要

`apple_ux_designer` 产出的交互规范（`苹果风格UI设计方案.md` §9.43）已用实读代码核验：`DayMealCardView.kt` 当前今天/未来角标确实共用同一套配色（`Badge(text, primary, primaryContainer)`，仅文案不同），合并后不做区分会导致今天被淹没——设计给出的"降未来的调"方案技术上可行，直接采纳。`MealRecordRepository.observeTodayPlusFuture` 当前 `.take(2)` 确认是"排序后取前2个日期组"，今天无记录时会被未来第2、第3天顶替，与"今天永远占一格"的设计要求冲突，必须改成"今天(0~1)+未来.take(2)"分别取（§6）。

**一处简化决策（ARCH 拍板，非设计缺陷）**：设计规范 §3.4 给了"新增 `hasAnyMealRecord` 判定"与"始终显示、退路兜底"两个选项并推荐前者。本蓝图选择**退路方案**——不新增 VM/Repository 字段，"查看全部食历"入口行始终渲染，新用户零记录时点进去看到 `FoodTimelineScreen` 自带的空态（该页已有"记一餐"CTA，非死胡同）。理由：新增一个专门的计数查询只为覆盖"全新用户"这一个边界情况，改动面（新 Flow + VM state + 又一次 DB 查询）与收益不成比例，且不影响任何已有数据用户的体验。若真机验证发现新用户点入空食历页体验差，再补 `hasAnyMealRecord`（转 `Q-HM-01` 登记，不在本批处理）。

### 4.3 `observeTodayPlusFuture` 现状（`MealRecordRepository.kt:77-97`）

```kotlin
/** 主页用：只展示今天及未来真实存在的两条餐食记录。[AI修改] */
fun observeTodayPlusFuture(today: LocalDate): Flow<List<DayMealCardData>> {
    val todayStr = DateTime.formatDate(today)
    return q.selectUpcomingMealRecords(todayStr, UPCOMING_ROW_LIMIT)
        .asFlow().mapToList(ioDispatcher)
        .map { records ->
            records.groupBy { it.date }.entries.sortedBy { it.key }
                .take(2) // 当天 + 下一个有餐食的日期
                .map { (dateStr, rows) -> val date = DateTime.parseDate(dateStr); buildDayMealCard(date, rows, plan = date > today) }
        }.flowOn(ioDispatcher)
}
```

`selectUpcomingMealRecords(todayStr, ...)` 这条 SQL 查询本身就是"从 `todayStr` 开始"的，如果今天没有记录，`groupBy{it.date}` 得到的 map 里根本没有 `todayStr` 这个 key，`sortedBy{it.key}.take(2)` 取到的是"未来第1、第2个有记录的日期"——**今天的位置被完全顶掉**，UI 层 `ui.plans.firstOrNull{it.isToday}` 永远拿不到今天（因为压根没查出来），这正是"今天永远占一格"这条设计要求现在做不到的根因。`UPCOMING_ROW_LIMIT = 60L`（`:550`）足够覆盖"今天+未来2天"全部餐次，不用改。

## 5. 修正后的渲染模型

```kotlin
// MealRecordRepository.kt observeTodayPlusFuture 修正后语义（非逐字代码，示意）
val grouped = records.groupBy { it.date }
val todayEntry = grouped[todayStr]  // 可能为 null（今天没记录）
val futureEntries = grouped.entries
    .filter { it.key > todayStr }
    .sortedBy { it.key }
    .take(2)
val allEntries = listOfNotNull(todayEntry?.let { todayStr to it }) + futureEntries.map { it.key to it.value }
// allEntries.size 现在是 0~3（今天0或1 + 未来0~2），而不是恒定"排序后前2组"
```

UI 层 `ui.plans.firstOrNull{it.isToday}`/`filter{!it.isToday}` 拆分逻辑（`HomeScreen.kt:204-205`）不变，因为 `buildDayMealCard(date, rows, plan = date > today)` 产出的 `DayMealCardData.isToday` 判定不受本次改动影响（该字段的真相源是 `date == today` 比较，不是"是否排在第一位"，本来就正确，只是上游因为"今天没被查出来"而拿不到罢了）。
