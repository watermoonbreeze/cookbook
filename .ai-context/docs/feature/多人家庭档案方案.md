# 多人家庭健康档案方案

> **P1 已落地（2026-07-15）**：`family_member`+`member_care` 表 + 20.sqm 迁移 + FamilyRepository(默认成员「我」迁移旧数据/CRUD/关注/忌口并集/关注成员身体数据与份额流) + 成员管理页(FamilyScreen) + 功能设置「健康膳食」分组入口 + 忌口取全家并集 + 达标/摄入/色系墙按主要关注成员(个人摄入=全家餐×饭量系数份额)。单测覆盖默认成员迁移/CRUD/关注/忌口并集。P2/P3(记菜关联成员/分餐精确/成员口味画像)待后续。


> [AI生成] 2026-07-14。app 定位「家庭记菜」，现有健康档案/身体数据是**单人全局**的；
> 家庭多人吃饭场景需支持多成员各自的病种/身体数据/口味。**本文档是方案草案，待用户确认后实施。**

## 一、现状
- 健康档案 `user_health_profile`：单套病种(care 分类)，全局。
- 身体数据 `BodyMetrics`：单套(存偏好 JSON)，全局 → 每日热量目标只有一个。
- 忌口/推荐(HealthRuleEngine)：按这一套病种。

## 二、目标场景
- 一家几口，慢病不同(如爸高血压、妈痛风、孩子无)、身高体重年龄性别不同。
- 记一餐可能"全家一起吃"或"给某人做"。
- 统计/推荐要能：按成员算各自达标；忌口取"在座成员的并集"或按"给谁做"。

## 三、数据模型（新增表，纯增量迁移）
```
family_member(id, name, emoji/avatar, gender, height_cm, weight_kg, age, activity, is_self, sort, status, created_at)
member_care(member_id, care_category_id, enabled)   -- 每成员的病种档案(替代/兼容 user_health_profile)
```
- 身体数据从"偏好 JSON 单套"迁到 `family_member` 行(每成员一份)。
- 迁移：老库单套 → 建默认成员「我」(is_self=1)承接现有身体数据 + user_health_profile 的病种。

## 四、交互（我的 → 家庭成员）
- **成员管理页**：列出成员(头像+名+病种标签)，可增/删/编辑；每成员设 身高/体重/年龄/性别/活动量(算各自每日目标) + 病种(高血压/糖尿病/痛风/高血脂…)。
- **记菜**：默认"全家"；可选"这餐给谁"(多选成员) → 影响该餐的忌口口径与"算进谁的当日摄入"。
- **统计**：
  - 家庭视图：每成员一行(今日热量/达标)；或聚合。
  - 成员视图：切到某成员看其达标/趋势/慢病指标。
- **推荐**：默认避开"所有启用成员"的忌口并集(现有引擎的 avoid 取并集)；进阶"给谁做"→只按该成员病种。

## 五、忌口/目标口径
- **忌口(推荐/餐食提示)**：在座成员并集(任一成员忌口即标红/降权)——家庭 app 稳妥(不给某人做他忌口的)。
- **每日目标热量**：按成员各自 BMR；家庭统计按成员分别显示(不简单相加，因每人目标不同)。
- **营养级别/色系墙**：可按"当前查看成员"或"全家平均"；默认全家(现行为)。

## 六、分期
- **P1**：成员表 + 成员管理页(增删/身体数据/病种)；老数据迁到默认成员「我」；每日目标/达标按当前选中成员。
- **P2**：记菜关联成员("这餐给谁")；统计按成员/家庭切换。
- **P3**：推荐"给谁做"模式；成员口味偏好(增长型推荐按成员画像)。

## 七、待用户确认点
1. 记菜粒度：是否需要"每餐指定给谁吃"？还是先只做"多成员各自档案 + 统计切换"，记菜仍全家？
2. 忌口口径：并集(稳妥) vs 按"给谁做"(灵活)？默认哪种？
3. 是否需要成员头像/昵称，还是简单名字即可？
4. 迁移：现有单套身体数据/病种 → 默认成员「我」，可接受？

## 八、方案 v2（2026-07-15，用户反馈后收敛）——**推荐**

> 用户核心反馈：**记菜粒度肯定是全家餐食、非个人**，所以"纯按成员统计"不合理；但"纯按家庭整体"又不准（每人病种/饭量不同）。以下为破解该矛盾的方案。

### 8.1 破题：健康评估按"维度粒度"拆，而非按"记菜粒度"拆
餐食仍是**全家一份流水**（记菜零改动）。健康评估拆两类维度，各归其位——正好对应已定的「定性分类维度 / 定量营养维度」两分：

| 维度类 | 粒度 | 依据 |
|--------|------|------|
| **忌口 / 病种适宜**（定性） | **全家并集 + 标注对象** | 做一道菜本就要避开**所有**成员的忌口（爷爷痛风 + 爸高血脂 → 同时看两人）。并集是"做菜决策"层面天然口径；关键是标"对谁忌口"（"五花肉·爸爸忌口"）。符合慢病家庭现实："照顾病最重的人来做饭"。 |
| **热量 / 宏量达标**（定量） | **个人视角切换** | 每人 TDEE/饭量不同，"家庭总热量达标"无意义。选中某成员，用其目标看"若他吃了这些菜常规份额"是否达标——**参考**而非精确到克。 |

一句话：**忌口做减法用并集，热量做评估用个人切换**。

### 8.2 落地形态（v2 定稿建议）
1. **记菜流程零改动**：仍记全家、不加"分给谁吃"（分餐到人违背"少操作"，仅作 P3 高级可选，不做默认）。
2. 每成员独立档案（身体数据 + 病种 + 忌口）；现有单套数据迁移为成员「我」(is_self=1)。
3. **忌口提示 = 全家并集 + 标注对象**：餐食/推荐里某菜对任一成员忌口即标红，副文本写"对谁"。
4. **热量 / 达标 / 色系墙 = 顶部成员切换器**：默认可设一个「主要关注成员」(病最重那位)，切换即用其目标重算当日达标；不做"全家相加"。
5. **口径默认**：忌口=并集；成员先**昵称即可**、头像后置。

### 8.3 与 v1 差异
- v1 的"记菜关联成员/这餐给谁"降级为 P3 可选（用户明确不要按个人记菜）。
- v1 的"家庭统计每成员一行相加"改为"**成员切换器**"（因相加无意义）。
- 明确"忌口=并集(决策层)、热量=个人(评估层)"的二分原则，作为实现主轴。
