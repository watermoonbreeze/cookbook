# 食材维度体系设计（明细②）

> [AI生成] 2026-07-06。总纲见 `食材层总方案.md`。
> 本文档：营养/调养/季节/功效等**维度**如何承载。定稿=**轻方案**：全部走现有 `food_category.dimension` + 关联表，不引入属性三表（三表方案见文末「未来预留」附录）。
> 依据 chatlog 486/499：「营养和调养只是常规食材分类的聚合，数据源永远同一个」——维度即分类，天然贴合。

## 一、核心：一切皆「分类」，用 dimension 区分维度

同一个 `ingredient` 可同时归属多个维度的分类，Tab 只是按 `dimension` 过滤出的聚合视图：

| 维度 dimension | 语义 | 载体 | Tab |
|---------------|------|------|-----|
| `general` | 品类：食材是什么 | `food_category` + `ingredient_category` | 常规 |
| `nutrition`/`gi`/`purine`/`sodium`/`fat`/`sugar` | 营养档位 | `food_category` + `ingredient_category` | 营养 |
| （季节，新增）`season` | 应季 | `food_category` + `ingredient_category` | 营养 Tab 内分节 / 筛选 |
| `crowd` | 调养病种 | `food_category` + `ingredient_care_rule`(带剂量) | 调养 |

> 已具备（`food_category.dimension` 现有枚举）：general/nutrition/gi/purine/sodium/fat/sugar/crowd。**新增只加数据节点，不改表。**

## 二、营养维度（低GI/低嘌呤/高蛋白…）

- 每个营养档位 = 一个 `food_category(dimension=nutrition/gi/…)` 节点（如 `gi_low`「低GI」、`purine_low`「低嘌呤」）。
- 食材关联 = `ingredient_category(ingredient_id, category_id)`。
- **营养 Tab**：左侧列 `dimension∈营养族` 的分类（按 dimension 分节），点某档 → 右侧网格 = 关联该 category 的食材。
- **详情营养区**：查该食材在营养维度上关联的所有分类，聚合展示（如「营养：低GI·高纤维·低脂」）。

## 三、调养维度（病种×剂量，红黄绿）

- 病种 = `food_category(dimension=crowd)` 节点（如 `care_gout`「痛风」）；**只到病种/人群层**，不建"绿灯/黄灯/红灯"子节点（v10 已统一）。
- 食材↔病种建议 = `ingredient_care_rule(ingredient_id, category_id=病种, advice_level, reason, daily_limit?)`；剂量由 `advice_level`（RECOMMEND🟢/LIMIT🟡/AVOID🔴）表达。
- **调养 Tab**：左侧列病种，右侧食材按 advice_level 分 🟢🟡🔴 三组（chatlog 419-420 的诉求：调养分类只显病种，剂量在下方推荐/限量/避免里选，二者解耦）。
- **详情忌口区**：默认只显需注意的（限量/忌口）；设了健康档案则该人群置顶高亮 + 完整原因。

## 四、季节（新增维度，chatlog 469）

- 蔬菜「应季时蔬」= 4 个 `food_category(dimension=season)` 节点（春/夏/秋/冬，或含"四季"）。
- 食材关联 `ingredient_category` 即可标应季；按季节顺序 seed。
- 展示：营养 Tab 内分节 / 筛选面板一项 / 详情属性区「应季：春·秋」。

## 五、筛选面板（跨维度叠加，chatlog 365）

- 以分类、营养素、慢病、季节、用户自定义分类为条件，可叠加。
- 实现 = 对选中的多个 `category_id` 求交集/并集查 `ingredient_category`（营养/季节/常规）+ `ingredient_care_rule`（调养），无需新表。

## 六、编辑器里的维度（chatlog 366/405/420）

- 自定义食材编辑：品类**多归属**（不固定属于某一类），分类选择用弹出分类选择器；分类归属只显具体分类（逗号隔开），不全展开。
- 调养建议编辑：先选**病种大类**，再单独选剂量（推荐/限量/避免），二者分开选，不出现"黄灯限量：推荐"这种歧义组合。
- 预设食材：维度关联只读，仅可改二级名+图片。

## 七、为什么不用属性三表（决策记录）

- chatlog 明确「营养/调养=常规分类的聚合，数据源同一个」——分类模型天然表达，`food_category.dimension` **现成已支持**，零新表零迁移。
- 引入 `attribute_def/option/ingredient_attribute` 三表虽扩展性更强（加属性零改代码、支持数值型），但当前需求（档位型营养/病种/季节）分类模型完全够用，三表反增维护面与迁移成本。
- **本期走轻方案落地。**

## 附录 · 未来预留：属性系统三表（暂不实现）

当出现**分类模型难以承载**的需求时再升级，届时把营养等维度迁入：

- 触发条件：需要**数值型精确营养**（每 100g 嘌呤 mg / GI 数值 / 钠 mg）、或**大量非分类型属性**（产地/口感/功效自由标签），且要求「加属性零改 UI 代码」。
- 三表草案：
  - `attribute_def(key, name, group_key, value_type[single/multi/number/text], unit, show_in_detail, filterable, editable)`
  - `attribute_option(attribute_key, value, label, emoji)`
  - `ingredient_attribute(ingredient_id, attribute_key, option_id?, value_num?, value_text?)`
- 渲染配置驱动：详情区/营养Tab/筛选/编辑器遍历 `attribute_def` 自动生成。
- 迁移路径：`food_category(dimension∈营养族)` 节点 → `attribute_def+option`；`ingredient_category` 对应行 → `ingredient_attribute`；完成后从 food_category 删营养维度节点。
