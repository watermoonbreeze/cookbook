# 食材层总方案（总纲）

> [AI生成] 2026-07-06。食材层（Ingredient Layer）整体设计的**唯一总纲**，四份明细的入口。
> 需求来源：`temp/claude/chatlog.md` 末尾「**食材**」段落 + 现有代码/DB 实测。
> 定稿决策：营养/调养走**现有分类维度**（轻方案，不建属性三表）；库存走**独立 pantry 表**；食材文档整理为「1 总纲 + 4 明细」。

## 一、定位：三层架构中的「数据层·基础数据」

App 分三层，本方案聚焦**打好食材数据层的框架与规范**，界面层复用同一份数据，AI 层未来接入：

| 层 | 职责 | 食材层的落点 |
|---|---|---|
| 界面层 | 用户方便易用 | 6 Tab 浏览 + 全局搜索 + 详情/编辑（见明细③） |
| 数据层 | ①基础数据可维护扩展 ②用户数据可保存/后期同步 | 品类/维度/属性框架 + 预设 seed 契约 + 用户数据(自定义/库存/引用) |
| AI 层 | 结合基础数据+用户数据给膳食建议 | 详情做法/组合、按在手食材推荐（预留，不在本期） |

**核心思想（chatlog 428/442）**：现在只搭**框架与规范**，食材内容后续用人工/爬虫/AI 持续补进来，靠版本号/内容 hash 增量写入，**加内容不动架构**。

## 二、数据源模型（唯一真相，chatlog 495-504）

食材只有两种来源，**数据源永远唯一**，Tab 只是同一份数据的不同视图：

- **预设食材**（`source=preset`）：全部归属「常规」品类树，是所有食材的**总集**。
- **自定义食材**（`source=user`）：用户自建，固定只在「自定义」Tab 展示，可自定义分类与食材。

> 「营养」「调养」不是独立数据，而是**对常规食材的分类聚合**——同一个食材关联了营养/调养维度分类时，在对应 Tab **同时出现**，底层仍是同一条 `ingredient` 记录。

## 三、6 个固定 Tab（顶部固定，chatlog 473）

| Tab | 含义 | 左侧树 | 数据来源 |
|-----|------|------|---------|
| 最近 | 最近用过 | 无·平铺 | `ingredient.last_referenced_at` |
| 库存 | 我家现有食材 | 无·平铺 | `pantry` 表 JOIN |
| 常规 | 品类树（13 大类→中→小，封顶 3 层） | 品类 | `food_category(dimension=general)` + `ingredient_category` |
| 营养 | 营养维度（低GI/低嘌呤/高蛋白…） | 营养标签 | `food_category(dimension=nutrition/gi/…)` + `ingredient_category` |
| 调养 | 慢病维度（痛风/糖尿病…），右侧🟢🟡🔴分组 | 病种 | `food_category(dimension=crowd)` + `ingredient_care_rule` |
| 自定义 | 用户自建食材/分类 | 用户分类 | `source=user` |

## 六、关键约束（沉淀自 chatlog + 现有工程）

- 已发布食材/分类**不得改名**（改名=新增），别名走 `alias`。
- 预设食材编辑只允许改**二级名(alias)+图片**；自定义可改全部。
- 删除食材=**软失效**（`status=0`+`reason`），菜品引用不断裂、灰显；不是物理移除。
- 图片多张 `|` 分隔，首张为默认展示；无图用 emoji 兜底。
- seed 增量写入靠版本/内容 hash 守卫，事务化，避免每次启动全量重写（已落地）。
