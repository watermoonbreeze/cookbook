## 一、议题一句话

记一餐现按「整份 × 成员 share」计入营养摄入（**默认假设整份全吃完**，且这个假设当前对用户隐性、未告知）。用户想引入「这道菜吃了多少 / 是否吃完」维度让摄入更准。它与 share（成员分食比例）是**两个正交维度**。

## 四、收敛：共识 + 唯一分歧

### ✅ 五方共识（无论何时做都成立）

1. **默认吃完（eatenRatio=1.0）·永不强制填**——记账主动线零新增。
2. **四档离散** `吃完 1.0 / 大部分 0.75 / 一半 0.5 / 少量 0.25`（可选 `没吃 0.0`）；后两档惯例经验·非权威·代码注释标可改；**禁百分比/克数输入**（伪精度）。
3. **入口只在「个人视角今日卡 + `CALORIE_NUMBER_ENABLED` 开」暴露**，其余场景整体不渲染（对不看热量用户 100% 无感）。
4. **无弹框**（控件即告知·T0）；**吃完=静默无标记**（去记账焦虑）。
5. **摄入纯实时派生**（整份×eatenRatio×share），不缓存快照 → 天然幂等；折算**抽单一共享纯函数** `IntakeCalculator`（今日卡/趋势/报告/达标全复用·防调参漂移）。
6. 🔴 **计划餐**：已摄入只聚合 `date≤today` 的餐；App **禁自动**把"计划到点"当"吃了"，计入须用户显式"记为已吃"。（"计划没执行却因 date≤today 自动当吃完"是现状语义漏洞，属餐状态机改造，**另立待办、本次不做**。）
7. 🔴 **慢病定性提示红线**：eatenRatio **只缩"个人摄入总量"**，**不缩"这道菜是否高钠/高嘌呤"的定性提示**（少吃仍是高钠菜）。
8. 🔴 **反焦虑/免责**：摄入只中性陈述（"按记录估算约X"），禁"够不够/超没超"评判、禁诱导低填、禁"你实际摄入"确定性措辞；守"仅供参考·非医嘱"。

### ⚠️ 唯一分歧 —— 存储粒度

| | 产品经理 | 算法 + DB + UX |
|---|---|---|
| 存哪 | **整餐级** `meal_record.eaten_ratio` | **每菜级** `meal_record_dish.eaten_ratio` |
| 理由 | 防镀金·操作成本最低·够用 | 迁移成本同为1列；支持 UX 的"分菜折叠"；精度归因（慢病来源点名）；不堵死扩展 |

**收敛主线程建议**：**采纳 per-dish 存储**。因为——(a) DB 确认 per-dish 与整餐级**迁移成本相同（都1列）**；(b) 产品担心的"复杂度"主要在**交互层**，而交互层已用"**默认整餐一键调·分菜折叠兜底**"化解（存储粒度≠交互粒度）；(c) per-dish 保留了 UX 的分菜细调与算法的精度归因，整餐级会砍掉这两者。→ **存 per-dish、交互整餐一键**是同时满足四方的最优解，产品经理反对的实质（操作成本）已被交互层消化。

## 五、若拍板要做 · 落地方案（融合版）

**数据层**：`meal_record_dish` 加 `eaten_ratio REAL NOT NULL DEFAULT 1.0`；迁移 `31.sqm` + CREATE TABLE 同步 + 2 处显式列 SELECT 追加 + insert 传参（防 `INSERT OR REPLACE` 打回）+ `MealRecord`/餐次关系模型加带比例的包装类型（不污染 `DishMini`）。老库无损、seed 不动、`SEED_LOGIC_VERSION` 不变。

**算法层**：新增共享纯函数 `IntakeCalculator.personalIntake(dishTotals, eatenRatio, share)`（`eatenRatio.coerceIn(0,1)`）；`DietReport.aggregate` 折算点改为 `dishTotals × eatenRatio × share`；补单测（守恒断言 + clamp + 默认1.0零回归）。🔴 **核实并并入今日卡 mrd 变化 Flow**（否则改比例不刷新）。

**交互层**（Apple-UX 门禁硬约束）：入口=今日卡「按实际吃了多少调整」折叠文字按钮（仅热量开+个人视角）→ ModalBottomSheet：整餐一档 `PrimaryTabRow` 四档为主 + "分菜调整"折叠兜底；实时预览、无 Snackbar、无守卫；吃完静默无标记。

**行为/文案层**：控件旁一句"没调就按整份算"（T0 可查）；慢病提示注"按你记录的食用比例估算"；守反焦虑禁止清单。
