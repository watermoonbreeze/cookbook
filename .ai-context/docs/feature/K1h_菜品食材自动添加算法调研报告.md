## 一、结论先行

**本项目现有架构在三个方向上都已经走在业界主流路线上，没有发现"明显落后、应该替换"的成熟方案**。三个方向逐一说明理由；调研中发现的可借鉴点已整理进 §五"可选 fast-follow 清单"，均为增量优化，非架构级替换，且都不建议现在就做。

| 方向 | 本项目现状 | 业界主流做法 | 结论 |
|---|---|---|---|
| 菜品→食材/调料/做法自动补全 | AI（LLM prompt，`AiMealPrompt`/`DishAutoGenerator`）直接生成，规则兜底（菜名关键词推断） | 学界/工业界 2024-2026 的主流也是 LLM prompt 直出（RecipeGPT/KERL 等均是"给菜名→模型出食材"的 NAME→INGR 任务范式），早期 CRF/规则方案（2015 年代 NYTimes 式）已被 LLM 取代 | **本项目做法与业界当前主流一致**，无需替换 |
| 食材实体归一（别名/同义词） | 轻量别名表（`ingredient_aliases.json`，50-100 条高频词，K1f 已批准方案B，明确不做全量模糊匹配） | 学界主流是食物本体（FoodOn）+ LLM 实体链接（FoodSEM/FoodOntoRAG，2025-2026 最新论文），但这些本体以英文为主，中文覆盖有限 | 本项目"轻量表+不做重匹配"的既有决策**在中文场景下反而更务实**，重本体方案投入产出比对本项目不划算 |
| 营养估算 | 优先用真实食材库营养值（`NutritionCalculator`），缺数据时按食材大类均值兜底（`NutritionGuesser`），数据源为中国食物成分表/USDA（权威来源，非 AI 编造） | 学界（FoodLMM 等多模态模型）与工业界（Spoonacular、天聚数行等第三方 API）都是"匹配真实成分数据库"这条路线，与 AI 直接猜测营养值的做法均不被推荐 | **本项目做法与业界最佳实践一致**（"不采信 AI 编造的营养数据、只信权威成分表"本就是本项目已确立的红线），无需替换 |

## 二、菜品→食材/调料/做法自动补全

### 2.1 本项目现状

- `DishAutoGenerator.preview()`（CREATE 分支）+ `AiMealPrompt`：AI 记一餐/AI 快捷记场景下，直接把菜名（及用户原文）交给云端 LLM，由模型给出食材、调料、做法、份量的完整结构化输出（NDJSON/扁平 JSON 两种协议，见 K1a/K1b/K1i 相关蓝图）。
- AI 缺失/低置信时，本地规则补全候选（菜名关键词推断，如"番茄炒蛋→番茄+鸡蛋"），标来源、不静默伪装成 AI 结果（`2026-08-04_AI记一餐V2_双阶段解析与健康建议方案.md` 已定的红线）。

### 2.2 业界调研发现

- **NAME→INGR 任务**：给定菜名，生成食材列表，是学界推荐生成研究里的标准子任务。近两年的代表工作（RecipeNLG 微调 GPT-2、RecipeGPT 用 T5、KERL 用 LLM+知识增强）**统一路线是"直接 prompt 大模型生成"**，且研究明确指出"模型若带有该菜品类型的先验知识，生成的食材列表更准确"——这与本项目让 LLM 直接出结果（而非先分类再查表拼接）的做法完全一致。
- **早期 CRF 方案**（如 NYTimes `ingredient-phrase-tagger`，2015 年代产物，用条件随机场从"配料文本短语"里抽取数量/单位/名称）**已经是被 LLM 取代的旧范式**，且该类工具只有英文训练数据，没有中文可用模型，移植成本远高于收益。
- **多模态方向**（FoodLMM，复旦 2024 年工作）额外支持"看图识菜出食材+营养"，是本项目目前没有的输入模态（本项目走文字/语音输入），可作为未来"拍照记一餐"功能的参考方向，但**不属于本次 K1h 调研的三个方向**，仅作旁证记录。

### 2.3 结论

本项目现有做法（LLM 直出 + 规则兜底 + 标来源不伪装）已经是业界当前公认的最佳路线，无需引入额外的开源库或替换现有架构。

## 三、食材实体归一（别名/同义词消歧）

### 3.1 本项目现状

`IngredientAliasResolver`（K1f，已完成）：维护一份高频别名映射表（`ingredient_aliases.json`，50-100 条，如"蕃茄/西红柿"→统一实体），AI/用户新建食材前先查表，命中则复用已有 id；**明确决策不做全量模糊匹配**（误匹配风险高于收益，2026-07-25 前后的会商已定）。

### 3.2 业界调研发现

- **FoodOn**：一个成熟的食物本体（ontology），把"食材"组织成带层级关系的语义网络，供跨系统统一指代同一食材。
- **FoodSEM**（2025）、**FoodOntoRAG**（2025-2026 最新论文）：均是"用 LLM 做食物实体链接（Named Entity Linking）"的最新研究，把文本里提到的食材词链接到 FoodOn 等本体上的标准节点，解决同义词/别名消歧问题。FoodOntoRAG 特别指出：微调 LLM 的做法会"绑定在某个本体快照上、本体一更新就退化"，改用**检索增强（RAG，词法+语义混合检索）而非微调**更稳健。
- **局限**：这些本体和研究**以英文食材命名体系为主**，中文食材（尤其中式家常菜的地方性别名，如"洋柿子/西红柿/番茄"、"地瓜/红薯/番薯"）在这些本体里的覆盖程度调研中未见明确数据支撑，直接套用需要额外做中英映射或补建中文本体节点，工程量不小。

### 3.3 结论

本项目现有的"轻量高频别名表 + 不做全量模糊匹配"决策，本质上是"实体归一"这个问题在**中文、单一家常菜场景、小语料库**约束下的务实简化版——业界的本体+LLM链接方案是为"任意语言、任意食物库、开放世界"设计的重型方案，对本项目当前规模（食材库千级、别名高频词百级）投入产出比不划算。**不建议替换**，现有决策维持有效。

**唯一值得记录的借鉴点**（非替换，是方法论参考）：FoodOntoRAG"检索增强优于微调"这个思路，如果本项目未来别名表规模显著增长（比如要支持数千条长尾别名），与其死记硬背扩表，不如做"高频表精确匹配 + 兜底轻量语义检索（如按拼音/编辑距离近似匹配后人工确认）"的两层结构——但**当前 50-100 条规模完全用不上**，记录仅供规模变化时参考。

## 四、营养估算

### 4.1 本项目现状

`NutritionCalculator`/`NutritionRepository`：菜品营养 = 各食材真实营养值（来自项目自建的食材营养库，数据源中国食物成分表/USDA，人工核准，见项目"数据来源"页）按用量折算求和；食材缺营养数据时按所属营养大类均值兜底（`NutritionGuesser`），并显式标"（估算）"，绝不由 AI 直接编造营养数值（项目红线：AI 估算营养不能成为权威事实）。

### 4.2 业界调研发现

- **FoodLMM**（复旦，多模态食物大模型）：能"基于图像/文字生成食谱并估算营养"，但学术论文的评测场景通常是"给出一个大致营养区间"，**不等同于逐食材精确核算**——工业落地场景（尤其涉及慢病人群饮食管理，本项目定位）通常仍需要落到真实成分数据库做逐项核算，而非依赖模型直接吐营养数字。
- **第三方营养 API**：Spoonacular（国际，英文食材/菜谱库为主）、天聚数行等国内服务商（近 2000 种常见食物的营养成分查询）——这类 API 提供的是"查表"能力，与本项目自建食材营养库的定位相同，只是数据来源换成第三方托管。

### 4.3 结论

本项目"真实成分数据库逐食材核算 + 缺数据大类均值兜底 + 绝不用 AI 编造"的路线，与学界（FoodLMM 等工作本身也承认精确核算优于模型直接猜测）和工业界（第三方 API 本质也是查表，非模型生成）的最佳实践方向一致，**是当前营养估算问题的正确解法，无需替换**。

**唯一值得记录的可选项**（非替换，是数据源补充参考）：若本项目自建食材营养库未来遇到"食材库扩充阶段2（USDA→5000+）"（已在 🟡 中优先级待办里）过程中某类食材长期缺数据，第三方营养 API（如天聚数行，覆盖国内常见食物）可以作为**人工核准前的候选数据来源之一**去联网核实（仍需遵守项目"联网核准数据必须标注来源+免责，不能只填营养、要评估食材属性风险"的既有红线，见项目踩坑红线关于食材扩充的条目），不建议作为自动化调用的营养数据来源（避免绕过人工核准环节，且与项目"权威方法论优先"准则一致——要用就要能溯源标注，不能静默接一个黑盒 API）。

## 五、可选 fast-follow 清单（均为增量优化，非阻断，非本次任务范围）

| 项 | 内容 | 价值 | 优先级判断 |
|---|---|---|---|
| 常见家常菜"参考食材表"缓存 | 用美食杰/下厨房类中文菜谱数据（或 HuggingFace 上的中文菜谱数据集）离线整理一份"高频家常菜→典型食材+份量"参考表，AI 生成前先查表命中则跳过 AI 调用、直接用参考值（同 K1f 别名表的思路，但对象是"菜"而非"食材"） | 对高频常见菜（占比预估较高）可以降低 AI 调用成本+减少幻觉风险，类似本项目已有的"别名表优先于模糊匹配"这套哲学的自然延伸 | 低优先级：需要先做数据整理和人工核准工作量评估，且当前 AI 直出的准确率没有被证明是明显痛点（未见相关 bug 反馈），暂不必立项 |
| FoodOntoRAG 式"检索增强别名匹配" | 别名表规模显著增长（数千条）时，把当前的精确匹配升级为"精确匹配优先 + 兜底轻量语义/编辑距离检索" | 只有在别名表规模远超当前百级时才有意义 | 低优先级，规模触发型，非当前需要 |
| 第三方营养 API 作为人工核准的候选数据源 | 食材库扩充阶段2 遇到缺数据食材时，把天聚数行等服务加入"联网核准candidate 数据源"清单 | 增加数据源选择，不改变现有人工核准流程 | 低优先级，随"食材库扩充阶段2"任务一起考虑即可，不必单独立项 |

## 六、调研方法说明

本次调研为纯 WebSearch 联网检索（英文+中文关键词各若干轮），覆盖学术论文（arXiv 检索到的 2024-2026 年相关工作）、开源项目（GitHub/PyPI/npm）、产品/API 服务（Spoonacular、天聚数行等）、中文菜谱数据资源（美食杰/下厨房/HuggingFace 数据集）四类信息源。未对任何具体开源库做代码级验证/试跑，仅做方向性调研评估，结论基于检索结果与本项目现有实现的对比分析，供未来立项参考，不构成实施依据。
