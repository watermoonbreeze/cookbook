# 联网数据获取·脚本化方案（省 token·规则 + 分层方案）

> [AI生成] 2026-07-21 用户提议：营养/GI/嘌呤等联网核验之前用 LLM agent 逐条联网太烧 token
> （第一批 195 条 pending 核准烧 ~53 万 token / 5 agent）。改为"脚本优先、LLM 兜底"。本文=规则 + 方案 + 当前第二批状态。

## 一、核心判断：哪些能脚本化、哪些必须 LLM

| 环节 | 能否脚本 | 说明 |
|---|---|---|
| **抓取结构化数据源** | ✅ 能 | 有公开 API/XHR 接口/开源数据集的，纯 python 零 token |
| **食材名精确匹配** | 🟡 半能 | 同名直配脚本能做；中文别名/干鲜口径/多来源歧义需 LLM 判断 |
| **数值合理性判断** | 🟡 半能 | zscore 离群检测脚本能做；跨源冲突取舍需 LLM |
| **权威来源可信度判断** | ❌ 需 LLM | 但可预先把"可信源白名单"固化进脚本 |

结论：**80% 抓取+匹配可脚本化零 token，20% 疑难判断留 LLM**——从"195 条全 agent"降到"~10-20 条疑难 agent + 抽样校验"。

## 二、分层方案（脚本优先·LLM 兜底）

### L1 · 纯脚本 · 公开 API（零 token·主力）
- **USDA FoodData Central API**：`api.nal.usda.gov/fdc/v1/foods/search`，免费 key、返回 JSON、含 kcal/宏量/**saturatedFat**/胆固醇/矿物质/糖。python `requests` 批量查。
  - 局限：美国食材库 → 需 **中文名→fdcId 映射表**（一次性建、增量复用）；**无 GI**。
- 适合补：saturatedFat（本批缺 82）、胆固醇、矿物质等 USDA 全的字段。

### L2 · 本地权威数据集（零 token）
- **GI**：开源 Atkinson 2008 / 悉尼大学 GI 数据集（GitHub 有整理版 CSV）→ 本地按名匹配。补 gi（本批缺 46·多为主食薯类果）。
- **嘌呤**：WS/T 560-2017 附录 + 公开嘌呤含量表 → 整理成 CSV → 匹配。补 purine（本批缺 56·肉/水产/豆/菌）。

### L3 · nlc 中国食物成分表（✅ 已侦察验证·2026-07-21）
- **纠正之前误判**：nlc.chinanutri.cn **不是** JS 动态渲染，而是**服务端渲染**——python `requests` 直接拿到含营养数值的完整 HTML（之前 agent 说"WebFetch 拿不到"是 UA 被拦/超时误判）。**零 token 可全脚本抓取**。
- **详情页**：`http://nlc.chinanutri.cn/fq/foodinfo/{id}.html`，营养表 `<td>字段</td><td>值 单位</td>` 结构，正则即可解析（442=细香葱实测：能量192/蛋白3.3/脂肪0.4/碳水5.4/纤维2.5/钠6.9/钾207/钙72/铁镁磷锌硒铜锰+维生素A/B1/B2/C/E/烟酸）。
- **列表页**：`http://nlc.chinanutri.cn/fq/foodlist_0_{大类}_{子类}_0_0_{页}.htm` 分类分页，遍历可建「中文名→id」全量映射（名称与链接分离，正则待微调）。
- **⚠️ 关键局限**：nlc 营养表**不含 gi / saturatedFat / purine**（这三个正是第二批缺的字段）→ **nlc 对第二批帮助有限**；其价值在**核心四项+矿物质+维生素**的权威中文值 = **第一批那类"核准"任务的零 token 替代**（未来核准中文食材再不用烧 ~50 万 token）。
- **侦察脚本**：`temp/claude/probe_nlc*.py`。

### L4 · LLM 兜底（极少 token）
- 仅对脚本匹配不确定的少数条目（中文名歧义 / 干鲜口径 / 多源>10%冲突 / USDA 无中国对应值）才 spawn agent 判断。
- 每次只喂"脚本已抓到的候选值 + 疑点"，让 LLM 裁决，**不再让 LLM 自己联网逐条搜**。

### 校验机制（定期·抽样·非逐条）
- 脚本产出后：① 引用完整性 + `validateNutritionSeedForTest` + `:shared:testDebugUnitTest` ② python **zscore 离群检测**（同类食材数值异常自动标红）③ LLM **抽样校验**（随机 N 条 + 全部离群项）——不逐条核。
- 权威来源仍入「我的·数据来源」页（红线不变）。

## 三、规则（拟写进 CLAUDE.md / 通用规则）

> **联网获取结构化数据（营养/GI/嘌呤/价格等），尤其 >50 条 / 需多轮联网的长任务：**
> 1. **先评估数据源**：有公开 API→脚本；有 XHR 接口→抓接口脚本；有开源数据集→本地导入匹配；仅需语义判断的少数→才 LLM。
> 2. **默认脚本优先**：LLM 只做「脚本兜底裁决 + 抽样校验」，**不逐条联网抓取**。
> 3. **禁止**把长任务（>50条/多轮联网）"全量丢 agent 逐条联网"（烧 token）。
> 4. 脚本产出必过：引用完整性 + 单测 + LLM 抽样校验 + 来源入数据来源页。
> 5. 复用资产：USDA 映射表 / GI·嘌呤 CSV 建好后，后续新食材几乎零成本；增量只查缺字段（`_miss` 分片思路）。

## 四、更优建议（供决策）

- **A. 一次性资产化**：建好 USDA 中文映射 + GI/嘌呤 CSV 后，变成项目**可复用数据资产**（放 `temp/claude/dataset/` 或纳入仓库），后续新增食材/新字段几乎零 token。
- **B. cron 定时增量**：cron 定期跑脚本对新食材增量补值，LLM 月度抽检（贴合"定期检验"诉求）。
- **C. 混合最优路径**：satFat/胆固醇/矿物质走 USDA API(L1)；GI/嘌呤走本地 CSV(L2)；核心四项权威中文值走 nlc XHR(L3)；只有冲突/歧义~10条走 LLM(L4)。预计第二批 155 条 token 从"~50万"降到"~3-5万"。

## ★ 实战验证成果（2026-07-22·用户拍板"脚本优先不烧token"·PoC 全通过）

三个数据源脚本方案**均已实战验证可行**（关键风险点 USDA 中文映射、nlc 接口侦察都通过）：

| 数据源 | 方案 | 验证结果 | 脚本 |
|---|---|---|---|
| **USDA satFat/矿物质** | 下载 SR Legacy **全库**(13MB)本地匹配(非API·免限速免key) | ✅ 中文→英文映射(~180条)命中 satFat **122 条** | `fill_satfat.py`+`usda_full_idx.py` |
| **nlc 核心四项(中国口径)** | 逆向出 `foodName` 搜索接口**按名全量交叉** | ✅ 列表页原JS动态渲染→找到 `FoodInfoQueryAction!queryFoodInfoList.do`(categoryOne=0+foodName·返回含营养JSON·无需建库/抓详情) | `nlc_cross.py` |
| **能量自洽(本地零依赖)** | Atwater `kcal≈P×4+F×9+C×4` 离群检测 | ✅ **最有效本地揪错**·全量502条揪出唯一真录入错(速冻虾仁kcal199→89) | `energy_cross.py` |

**nlc 接口关键参数**（复用备忘）：`POST FoodInfoQueryAction!queryFoodInfoList.do`，data=`categoryOne=0&categoryTwo=0&foodName={名}&pageNum=1&field=0&flag=0`，返回 `{list:[[id,img,名,...,食部%,水分,能量kJ,蛋白,脂肪,?,纤维,碳水,...]]}`（列：[0]id [2]名 [5]食部 [7]能量kJ [8]蛋白 [9]脂肪 [11]纤维 [12]碳水；kcal=kJ÷4.184）。UA 需伪装浏览器。

**交叉核对方法论结论**：
- **能量 Atwater 自洽**=本地零成本、最灵敏揪"kcal 与宏量不自洽"的录入错，应纳入常规校验。
- **跨口径源(USDA)交叉**多暴露口径差异(干/鲜、加糖/无糖、品种)而非错误→**不盲从他源改中国食材值**(中国成分表是主来源)。价值在补缺字段(satFat/矿物质)。
- **同口径源(nlc)交叉**才是揪中国食材真录入错的主力(同源差异更可信)。
