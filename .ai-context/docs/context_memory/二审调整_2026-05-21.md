## 二、变动的 3 项确认项

### 1. 热度（喜爱度）计算规则改为自动累加

**原决策**：`dish.preference` 是 0-5 整数，由用户在 NewDishScreen 手动评分。

**二审改为**：
- 字段类型 `INTEGER` → **`REAL`**，范围 0-100
- 每次菜品被添加到 `meal_record_dish` 时，由 SQLite 触发器 `trg_dish_popularity_after_insert` **自动 +0.1**，上限 100
- UI 上显示为 5 颗星，**每颗星 20 分**（用户原话"每颗星 10 分"是笔误，按 5×20=100 校正，已确认）
- 删除 `meal_record_dish` 时**不扣回**热度（保留历史热度）
- **新建/编辑菜品界面均不暴露此字段**，UI 自动累加
- 热度展示位置：DishesScreen DishRow 行尾 + 菜品查看（详情页）顶部

### 2. HomeScreen "🔥 热门" + DishesScreen "🔥 热度" 计算规则

**原决策**：30 天内出现 ≥ 3 次，按次数倒序，6 个。

**二审改为**：
```sql
SELECT * FROM dish ORDER BY preference DESC, name COLLATE NOCASE ASC LIMIT 6
```
- 不限时间窗口
- 不限次数阈值
- 直接按累计热度排序

副作用：`user_preferences` 表里的 `home_popular_days` / `home_popular_threshold` 两个键**不再有意义**，可保留但 MVP 不读不写（或一并清理）。

### 3. 本餐评分（`meal_record.rating`）删除

**原决策**：AddDayFoodScreen 有 ☆☆☆☆☆ 本餐评分输入，存入 `meal_record.rating`。

**二审改为**：
- AddDayFoodScreen 去掉评分输入项
- `meal_record.rating` 字段**从数据库 schema 中删除**
- 原因：该字段是 dead-end，UI 任何位置未展示，也不参与计算

## 三、撤销的 1 项自主决定

### B3：DayMealCard 内横滑菜品"主料排首位"

**原自主决定（明日审核清单 二.B.B3）**：DayMealCard 横滑菜品**不带主料角标**，主料角标只在 NewDishScreen。

**二审用户提出**："内横滑菜品确实不需要带主料角标，但在排序上需要把主料放在首位"

**追问澄清**：因 DayMealCard 横滑的是 `dish`（菜品），不是 `ingredient`（食材），"主料"语义不明确。

**用户最终答复**："看错了，不需要添加，就按你现在的来" → **撤销该提议，维持 B3 原样**（不带主料角标，按 `meal_record_dish.sort_order` 排序）。

## 四、新增的自主决定

### 新 C7：删除菜品记录时不扣回热度

数据库设计方案 §2.3 dish 表注释和触发器附近已明确：
- 当用户从某餐中删除一道菜（DELETE meal_record_dish）时，**不触发热度 -0.1**
- 理由：避免用户清空记录后菜品热度归零；保留历史热度更符合"热度是累计积分"的语义
- 如未来需要扣回：增加 `AFTER DELETE ON meal_record_dish` 触发器即可，逻辑对称

**用户审核此项时若不同意，告知即可加触发器**。
