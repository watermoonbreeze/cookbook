## 二、C#F3 无库存单餐兜底 —— 产品层分析（结论：核心已覆盖·仅剩可选 UX）

**核实结论（承交接 D5·`Explore` 已核实）**：**非真 gap，现有 `RandomMode` 即"无库存/想吃什么"的独立入口，已覆盖。**

- `HealthRuleEngine.evaluate` 首行 `if (onHandNonSeasoning.isEmpty()) return@mapNotNull null` 会剔除"没用到在手食材的菜"——但 **RANDOM 模式把全库食材当"在手"**（`selectAllDishesForRandom`/`listAllDishMinis`·commit `34e49d3`），故该剔除**不触发**、不空不退化，忌口/限量/慢病软约束全生效。
- 库存空时的用户路径：PANTRY 模式空态"库存里还没有能用到的食材"→用户手动切"随机推荐"→全库推荐。库存挂钩关时 PANTRY 不可达、强制 RANDOM。
- 原设想的 `requireOnHand` 重构**无必要**。

**产品层如何处理更顺手（可选·非必需·体验加分）**：
- **库存空时自动提示切随机**（auto-prompt）：PANTRY 模式候选为空时，空态直接给一个"换随机推荐"的主 CTA（一步切到 RANDOM），省去用户自己找模式切换。守苹果"少操作·空态给下一步"。
- 属**可选 UX 打磨**，需 Apple-UX 门禁（空态交互）。**建议**：并入首页/推荐页空态优化批择机做，非算法项、无数据风险。
- **本项不需算法改动**——结论=产品层加一个空态 CTA 即可，算法侧已闭环。

## 三、A#4 菜级营养字段打散高钠/高GI —— 得失分析（algorithm_engineer 交付）

**结论：最小化做——只做 GI 一维、只进 MMR 相似度维度。钠/高脂/PlanDish/组合硬约束都不做。或"不做"也站得住。**

**不改造代价（低-中）**：现 `dishSimilarity` 五维（主料0.45/重油族0.15/荤素0.15/做法0.13/菜系0.12）**无菜级营养**。"重油族"是烹饪代理≠营养：卤/炖高钠菜落"清淡族"识别不到、高GI主食（米/面/馒头主料各异）主料维当"已多样"不打散。坏 case=一批全高GI主食/全高钠扎堆。**但频率中低**（一批仅10道、四维已打散，需多维同时失效）；**且真正危险的"忌口菜进一餐"由硬约束层已守住**，A#4 缺失只是"体验层一批视觉偏同质"、**不构成健康红线破口**。

**改造收益（中偏低）**：补重油族的语义缺口。**最实在是 GI**——高GI主食是"主料维打散不到的盲区"，营养维唯一能补处；钠与重油族部分重叠、价值次之。五维已占满权重，新维只能匀权（≤0.15）、主料0.45仍主导→"锦上添花"级。

**成本/风险（低·关键发现）**：
- **性能≈零**：`dishNutrition(candidateIds)` **已在每次 gather 调用**（算 nutritionBalanceScores·一条批量查询无 N+1）→A#4 复用其结果，**零新查询**。
- 契约改动小：`DishCandidate` 加 `highGiStaple:Boolean=false`，**唯一构造点 `HealthRuleEngine.kt:160`（命名参数·安全）**，末尾追加带默认值向后兼容（仍需 grep 测试 helper 位置参数）。
- 覆盖率：GI 数值覆盖仅 75%（1/4空洞）→**改用 `ingredients.json` 的 `gi_high` 分类标签**（米/面/糖已打标·更稳·绕开空洞）；钠99%但菜级阈值属惯例口径+免责风险；饱脂仅41%→不做高脂。数据缺→**中性退化 false**（只漏打散不误打散·安全）。
- 免责：GI 有 FAO/WHO 口径、仅作**内部打散信号不外显**→风险低；钠"高钠菜"无菜级国标阈值→不做。

**与慢病软降关系=互补非重叠**：软降=单道菜减分排后（仅登记病种触发·"该不该少推这道"）；A#4=一批候选间相似度打散（全用户·"这批够不够错落"）。A#4 **只打散不减分**（进 MMR 非 score）→天然不与软降罚分双重叠加。软降只在病种触发、A#4 补健康人多样性空档。

**推荐落地（若做）**：`DishCandidate.highGiStaple`（主食类+主料含 `gi_high` 标签）→ `dishSimilarity` 加"同为 highGiStaple→相似"一维（权重从做法/菜系匀出~0.10·维持 `MMRWeightSumTest` 和≈1.0）+ 派生纯函数单测（含缺数据退化）+ 打散断言。**不做**：钠维/高脂维/PlanDish加字段/组合硬约束。**或接受"不做"**（现"重油族+荤素+主料+慢病软降"已守健康红线·A#4 只是体验小缺陷可延后）。→ **待你拍板：做 GI 一维 / 完全不做。**

## 四、A#6 当日能量目标 —— 方案（algorithm_engineer 交付）

**核心缺口**：推荐唯一营养因子 `NutritionBalance.score` **只比宏量占比结构**（蛋白/脂肪/碳水20/28/52）、`energyRatios()` 归一化丢弃总能量量级→"今天已吃2500 vs 300 kcal"只要宏量结构同，对候选加分**完全相同**（"吃多了还推高热量菜"算法看不见）。

**当日能量按谁算**：复用今日卡口径=`observeViewingMember()` 单人 × `share`（饭量系数折算），**非全家总量**，与今日卡"今日X千卡/目标Y"同一人同份额、不产生第二套口径。

**三选项**：
- **选项 A（轻·推荐先做·零风险）**：不动算法，`status==ABOVE` 时推荐页/今日卡入口显一条陈述提示"今天吃得不少了，这餐清淡些也不错"（复用今日卡已算 `TodayNutrition.status`）。守不操纵（陈述非责备·禁"你超标了")。成本极低。
- **选项 B（中·算法正解·排 A2 gate 后）**：`HealthRuleEngine` 加与 `chronicDiseaseNutrition` **同构软因子**——仅关注单成员+身体数据齐（`dailyTarget!=null` 含成人 gate）+当日已吃 ≥0.85×目标 时，对高热量候选轻度减分。**封顶≈0.4**（同慢病软降量级·低于核心因子·不碾压物尽其用/忌口）、**暗因子对用户不可见**、缺数据/没吃多/多成员歧义→**恒0向后兼容**。数据全现成（todayTotals/dishNutrition/dailyTarget 已在取数层）→**无新查询**。**前置**：①C组9 A2 孕期/哺乳 gate 先落地（否则误压孕期成员=红线）②观察真机身体数据填写率。
- **选项 C（重·明确不做）**：周计划/单餐按能量额度硬约束→**最易造节食焦虑**（把吃饭变卡路里预算游戏·违 App 少决策/家庭定位）+多成员口径无解+能量覆盖率不足。当前不做。

**红线**：热量个人概念（色系墙不关联·仅个人卡+暗因子）、成人/合理域 gate 复用 `dailyTarget`、孕哺 gate 继承 C组9 A2、健康免责（禁减肥/达标断言）、暗因子不可见不制造焦虑、缺数据恒0。**DRIs 权威值不编造**（Mifflin 公开公式已标非医嘱·国标 EER 用已 verified 的 `DriEnergyReference`）。

**推荐**：**A 现在做**（零风险补"清淡些"提示）→ **B 排 A2 gate 之后**（用现成 chronicDiseaseNutrition 同构范式落·成本可控）→ **C 不做**。B 目标口径**直接复用 C组9 `CalorieTarget.dailyTarget`**（同一数·今日卡与推荐不打架）。→ **待你拍板：A 立即做否 / B 是否排期（依赖 A2 gate）。**

## 五、C#F2 早餐软硬搭配透传单餐 —— 实施方案（就绪·待确认后实现）

**问题**：周计划 `mealPool` 有"早餐偶数位取硬(主食/蛋)、奇数位取软(粥/饮)"软硬搭配；单餐 `RecommendationOrchestrator` 无此逻辑→糖尿病早餐可能推"白粥+豆浆"两软食无蛋（升糖快·缺蛋白）。

**为何本批未直接做**：需**多点数据契约改动**（触"改 data class 字段/全构造点/位置参数 helper"红线），value/risk 对这个窄边界（仅早餐、仅候选全软食时）偏低，宜单独一批稳做。

**精确实施步骤**（确认后按此做）：
1. `DishCandidate` 末尾加 `breakfastSoft: Boolean = false`（默认值·防位置参数构造点崩）。同源判定复用 `RecommendationDataSource.BREAKFAST_SOFT_KEYWORDS`（粥/豆浆/豆奶/牛奶/燕麦/蛋羹/面）——**收敛为单一真相源**（现只 PlanDish 用，抽成共享判定函数供两处调用，防漂移）。
2. `RuleDish` 加 `breakfastSoft`（或在 `HealthRuleEngine.evaluate` 构造 DishCandidate 时按 `dish.name` 判——但 engine 无关键词表·倾向 RuleDish 带字段、gather 时算好透传，保持 engine 纯粹）。
3. 早餐上下文透传：`RecommendationInput` 加 `isBreakfastMeal: Boolean = false`（或复用已有 mealSlot 信号·gather(mealSlot=BREAKFAST) 时置 true）；`recommend()` 读它传入 `combineScore`/`fallback`/`supplementComposition`。
4. `combineScore`（及 fallback 组合、C#F1 supplement）在**早餐上下文**下加"软硬搭配"补分：本餐已选全软(`breakfastSoft`)时，给硬/含蛋白候选补分（复用周计划 `mealPool` 软硬口径·抽共享，防漂移）；非早餐照旧。
5. 单测：早餐候选全软 vs 有蛋，验证补进硬/蛋；非早餐上下文不受影响（gate）；`PeriodPlannerTest`/`RecommendationOrchestratorTest` 风格。
6. 门禁：Google 质量审（契约改动面·全构造点·确定性）。

**红线**：加字段末尾追加带默认值；全构造点/位置参数 helper 逐个查改命名参数；软硬判定与周计划共用单一真相源（`MealCompositionScorer`/`ChronicDiseasePenalty` 同款抽法）。
