---

## 一、核心目标（为什么做、怎么用）

1. **掌握全貌**：一份文档看懂"有哪些模块、每个模块干什么、整体架构、当前状态"。
2. **可反查定位**：界面/行为出问题时，能从文档**反查到它的操作逻辑、数据来源、代码位置**，据此判断是 **bug 还是需求**。
   - 典型用法：`看到某页某处不对 → 查 00 索引 → 定位到 03 界面 或 05 数据 → 看它设计逻辑 → 对照现象判定 bug/需求 → 指派我修/改`。
3. **审核抓手**：你审核我产出时，用文档核对"实现是否符合既定业务/技术方向"。

## 二、通用 vs 专属（关键分层）

- **通用说明书体系**（可复用技能产出，**任何项目都适用**，不含业务专有逻辑）：架构/业务流程/界面/数据/约定/对照表。
- **本项目专属文档**（cookbook 独有、**不进通用模板**）：健康评级 + 推荐算法 + 慢病维度等**核心业务逻辑与权威口径**。单独成册，由项目自身维护。
- 理由：健康/算法是本项目的独特价值与复杂度所在，口径/免责/权威来源属业务知识，放进通用模板会污染其可迁移性。

## 五、可复用技能设计 `/项目说明书`（通用方法）

**目标**：一条命令扫描当前代码库，(重)生成/刷新上述**通用分册**（`01/02/03/04/06/99` + `00` 索引），保持与代码同步；专属 `05` 由项目手工维护、技能只留占位与链接。

**技能行为（拟）**：
1. 扫描：模块结构(gradle/包树)、页面(Screen/Composable 清单)、路由(Destinations)、DB(.sq 表+查询)、DI(module)、Repository/UseCase、交互模式文档(§九)。
2. 生成：按分册模板填充；页面/表/流程清单自动列全，逻辑描述由 AI 归纳（人读语言，非代码搬运）。
3. 维护模式：
   - `全量刷新`：重扫重生成通用册（结构性变化后）。
   - `增量`：只更新指定分册/指定流程（日常小改）。
   - `对照表维护`：`99` 表随功能增改更新。
4. 可迁移：模板不含业务词，换项目即用；识别到"健康/算法类专属内容"时提示单列，不塞进通用册。

**触发**：`/项目说明书`（全量）/`/项目说明书 02`（单册）/"更新项目文档"（自然语）。

**与提交流程的关系**（可选加严）：每完成一个功能提交时，顺手 `增量` 更新受影响分册的一节 + `99` 对照表一行（保证文档不腐化）。
