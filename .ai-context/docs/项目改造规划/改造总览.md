# Project Graph 总体设计方案 V1.0

## 1. 背景

随着项目持续发展，项目中的信息通常会逐渐分散到：

* 代码；
* Bug；
* Todo；
* 开发方案；
* 架构决策；
* 测试；
* 真机验证；
* 当前工作交接；
* 项目现状；
* 功能路径索引。

这些信息单独存在没有问题。

真正的问题是：

> 它们之间的关系通常依赖人或 AI 自己理解，而不是项目显式维护。

最终容易出现：

* Bug 已修复，但 Bug 列表还是 Open；
* 方案已经完成，但项目现状仍写“待开发”；
* 功能路径索引还是旧代码结构；
* SESSION 已进入下一阶段，但 Todo 索引没有同步；
* 真机验证已经通过，但功能状态仍显示验证中；
* 新 AI 每次进入项目都需要重新阅读大量文档建立上下文。

Project Graph 的目标就是解决这些问题。

---

# 2. 核心目标

Project Graph 要实现：

```text
代码
↓
功能
↓
Work Item
↓
方案
↓
验证
↓
项目状态
```

所有内容形成明确关系。

最终达到：

### 从 Feature 出发

能够知道：

* 功能代码在哪里；
* 当前处于什么状态；
* 有哪些 Bug；
* 有哪些 Todo；
* 哪些开发任务正在进行；
* 有哪些方案；
* 哪些验证未完成；
* 当前风险是什么。

### 从 Bug 出发

能够知道：

```text
Bug
→ Feature
→ Plan
→ Code
→ Verify
→ Result
```

### 从方案出发

能够知道：

```text
Plan
→ 解决哪些 Work Item
→ 影响哪些 Feature
→ 修改哪些代码
→ 需要哪些验证
```

### 从代码出发

能够知道：

```text
Changed Files
→ Feature
→ Current Work Item
→ Project Graph
```

---

# 3. 最核心原则

## One Truth, Multiple Views

允许同一个项目状态展示在多个地方。

但：

> 同一个事实只能维护一次。

例如：

```text
AI记一餐当前处于真机验证
```

可以出现在：

* 人类项目全景图；
* AI_INDEX；
* Feature Graph；
* 验证汇总。

但不能让 AI 手工修改四遍。

真正维护：

```text
Project Graph
```

其余内容：

```text
由 Project Graph 自动生成。
```

---

# 4. 谁维护 Project Graph

本体系的基本假设：

> 项目状态完全由 AI 维护。

人类：

* 提供需求；
* 报告 Bug；
* 提供产品判断；
* 提供真机验证结果；
* 阅读项目全景；
* 审核重大设计。

人类不负责：

* 修改 Graph；
* 修改 Bug 状态；
* 修改 Todo 索引；
* 修改 Feature 索引；
* 修改项目状态表；
* 同步多个文档。

原则：

> AI Maintained, Human Read-Only.

# 5. 三种 Truth

Project Graph 不取代代码，也不取代设计文档。

整个项目存在三种 Truth。

## 5.1 Runtime Truth

来源：

```text
Code
Database Schema
Configuration
```

回答：

> 系统实际上如何运行？

优先级最高。

---

## 5.2 Project Truth

来源：

```text
Project Graph
```

回答：

> 项目当前处于什么状态？

包括：

* Feature；
* Work Item；
* Bug；
* Todo；
* Plan；
* Verification；
* Current Work；
* Blocker；
* Relation。

---

## 5.3 Decision Truth

来源：

```text
Plan
ADR
专项方案
设计文档
```

回答：

> 为什么这样设计？

# 8. Declared / Observed / Derived

这是 Project Graph 的重要设计。

## 8.1 Declared Facts

由 AI 根据业务语义维护。

例如：

```text
K1b.status = parked
K1b.feature = F-AI-MEAL
K1b.plan = PLAN-AI-K1B
```

---

## 8.2 Observed Facts

工具直接观察。

例如：

```text
git diff 中修改了 StreamingMealParser.kt
Gradle exit code = 0
当前 commit = abc123
某 Verification 在设备 X 上测试通过
```

AI原则上不应该手填这些可自动获取的数据。

---

## 8.3 Derived Facts

由程序计算。

例如：

```text
open_bug_count
pending_verify_count
activity
health
affected_features
```

禁止 AI 重复维护。

例如不得维护：

```yaml
pending_verify_count: 97
```

应该从 Verification 节点自动统计。

# 10. Feature

Feature 是整个系统最重要的主键。

Feature 表示：

> 长期稳定的产品或系统能力。

Feature 不应该表示：

* 页面；
* ViewModel；
* 类；
* 某个临时开发阶段；
* 某一个实施方案。

例如 Cookbook：

```text
F-MEAL
F-AI-MEAL
F-TIMELINE
F-INGREDIENT
F-DISH
F-PANTRY
F-RECOMMEND
F-NUTRITION
F-HEALTH
F-FAMILY
F-WEEKPLAN
F-SYNC
F-TOOLS
```

Feature ID 一旦正式启用，应尽量永久稳定。

---

# 11. WorkItem

Bug、Todo、新功能、重构等统一为 WorkItem。

通过：

```text
kind
```

区分。

支持：

```text
feature
bug
todo
tech_debt
refactor
compliance
research
maintenance
```

Cookbook 当前已有：

```text
I*
J*
K*
L*
```

继续保留。

不得为了 Project Graph 重编号。

没有 ID 的旧事项再补新 ID。

---

# 12. Plan

Plan 表示：

> WorkItem 的实施设计。

关系：

```text
WorkItem
   │
 implemented_by
   │
   ▼
 Plan
```

一个 Plan 可以解决多个 WorkItem。

例如：

```text
PLAN-AI-NDJSON
├── K1g
├── AF-ARCH-01
└── AF-ARCH-02
```

---

# 13. Verification

Verification 是闭环实体。

关系：

```text
WorkItem
     │
 verified_by
     │
     ▼
Verification
```

验证可以是：

* Unit Test；
* Integration Test；
* Build；
* 真机；
* 手工流程；
* 数据检查；
* 文档检查。

WorkItem 如果标记：

```text
done
```

原则上必须存在：

```text
Verification = pass
```

或者：

```text
not_required + reason
```

---

# 14. Relation

Project Graph 必须正式定义 Relation。

核心关系：

```text
belongs_to
implemented_by
verified_by
depends_on
blocks
affects
supersedes
related_to
```

例如：

```text
K1g
--belongs_to-->
F-AI-MEAL
```

```text
K1g
--implemented_by-->
PLAN-AI-NDJSON
```

```text
K1g
--verified_by-->
E-B4
```

---

# 15. Typed Reference

内部引用需要能够明确实体类型。

逻辑上：

```text
feature:F-AI-MEAL
work:K1g
plan:PLAN-AI-NDJSON
verify:E-B4
```

具体 YAML 为了简洁可以写：

```yaml
feature: F-AI-MEAL
plan: PLAN-AI-NDJSON
```

Validator 内部将引用标准化为 Typed Reference。

# 22. Code Mapping

Feature 必须拥有 Code Mapping。

例如：

```yaml
match:
  - shared/**/ai/meallog/**
  - androidApp/**/AiMeal*
```

同时记录关键路径：

```yaml
code:
  entry:
  ui:
  viewmodel:
  domain:
  data:
  core:
  tests:
  other:
```

Code Mapping 有两个目的。

---

## 22.1 Feature → Code

生成：

```text
功能路径索引
```

供 AI快速定位代码。

---

## 22.2 Code → Feature

分析：

```text
git diff
```

自动识别：

```text
Affected Feature
```

例如：

```text
StreamingMealParser.kt changed
→ F-AI-MEAL
```

---

# 23. Affected Model

Project Graph 借鉴项目依赖图的思想。

未来：

```text
pg affected
```

输出：

```text
Changed Files
Direct Features
Dependent Features
Related WorkItems
```

这样可以发现：

> AI声称只修改同步模块，但实际修改了 AI记一餐核心代码。

# 24. Machine Source 格式

数据文件：

```text
YAML
```

原因：

* Token相对低；
* AI编辑稳定；
* 人类也能阅读；
* Git diff清晰。

---

# 25. Schema 标准

Schema 不自创。

采用：

```text
JSON Schema
```

结构：

```text
YAML Data
   ↓
YAML Parser
   ↓
JSON-compatible Object
   ↓
JSON Schema
```

JSON Schema负责：

* 类型；
* 必填字段；
* enum；
* 数据结构；
  -格式。

Python Validator负责：

* 跨文件引用；
* ID唯一；
* Relation；
* 循环；
* Code Mapping；
* 生命周期规则；
* Graph语义。

# 29. 功能路径索引

正式定位：

> AI-only Generated Code Index。

不承担：

* 项目状态；
* 开发阶段；
* 测试统计；
* 人类介绍。

只回答：

> 这个功能代码在哪里？

例如：

```text
F-AI-MEAL AI记一餐
E androidApp/.../AiMealInputSheet.kt
VM androidApp/.../AiMealInputViewModel.kt
C shared/.../StreamingMealSession.kt
C shared/.../StreamingMealParser.kt
T shared/.../StreamingMealParserTest.kt
FLOW Sheet>VM>Runtime>Session>Parser
GRAPH project_graph/features/F-AI-MEAL.yaml
```

100%自动生成。

# 32. AI 自动维护生命周期

  ↓

# 33. BEGIN

AI收到任务后：

```text
pg begin
```

完成：

1. 读取 AI_INDEX；
2. 定位 Feature；
3. 定位已有 WorkItem；
4. 必要时创建；
5. 写入 CurrentWork。

不得默认直接开始编码。

---

# 34. RESOLVE

根据 Feature：

读取：

```text
Feature Graph
功能路径索引
关联 Plan
必要 Code
```

避免读取整个项目知识库。

---

# 35. CHANGE

AI修改：

```text
Code
Plan
Graph Declared Facts
Tests
```

Project Graph 的“实时”定义：

> 语义状态变化时更新。

包括：

* 开始任务；
* 进入方案；
* 开始编码；
* 进入Review；
* 测试失败；
* 测试通过；
* 进入真机；
* 真机失败；
* 完成；
* Parked；
* Blocked。

不是每次保存文件都更新。

---

# 36. VERIFY

自动测试尽量通过工具执行：

```text
pg verify <id> -- <command>
```

工具记录：

```text
command
exit_code
timestamp
result
```

这些属于 Observed Facts。

---

# 37. 人工真机验证

人类提供事实：

> 华为真机 E-B4 通过。

AI负责更新 Graph。

人不直接修改验证文档。

---

# 38. RECONCILE

```text
pg reconcile
```

比较：

```text
Git Diff
↕
Project Graph
```

识别：

* 修改了哪些 Feature；
* 是否关联当前 WorkItem；
* 是否出现未映射代码；
* 是否修改跨 Feature 代码但 Graph 未声明。

---

# 39. 未映射代码

如果出现：

```text
NewEngine.kt
```

没有任何 Feature Mapping：

```text
UNMAPPED CODE
```

AI必须：

* 归入已有 Feature；
* 或创建 Feature；
* 或明确基础设施例外。

---

# 40. RENDER

```text
pg render
```

生成所有 View。

重复执行两次必须：

```text
0 diff
```

保证 deterministic。

---

# 41. CHECK

```text
pg check
```

至少检查：

### Schema

是否合法。

### References

是否断链。

### Relations

是否合法。

### Code Mapping

是否匹配。

### WorkItem

是否属于 Feature。

### Done规则

Done 是否有 Verification。

### Generated Views

是否最新。

---

# 42. FINISH

```text
pg finish
```

只有：

```text
check pass
```

AI才允许宣布任务完成。

---

# 43. 自动维护不是靠 Prompt

真正可靠的自动维护依赖四层：

```text
Agent Rule
+
Project Graph Tool
+
Git Guard
+
CI Guard
```

---

# 44. Agent Rule

PROJECT.md规定：

任何代码或项目状态任务必须遵循：

```text
begin
→ change
→ verify
→ reconcile
→ render
→ check
→ finish
```

---

# 45. Git Guard

Pre-commit：

```text
pg check --staged
pg render --check
```

失败：

```text
commit blocked
```

---

# 46. CI Guard

远端再次执行：

```text
pg check
pg render --check
```

防止：

* AI绕过本地 hook；
* 手工 commit；
* 不同 AI行为不一致。

# 55. 最终理念

Project Graph 不是文档系统。

它是：

> AI开发时代的项目结构化记忆层。

代码回答：

> 系统现在怎么运行。

Plan / ADR回答：

> 为什么这么设计。

Project Graph回答：

> 项目现在发生了什么。

生成视图分别服务：

> AI 与人类。

最终结构：

```text
             CODE
              │
       Runtime Truth
              │
              ▼
         Project Graph
              │
        Project Truth
              │
        ┌─────┴─────┐
        ▼           ▼
    AI Views     Human View
        │           │
       AI          Human
```

核心原则：

> One Truth, Multiple Views.

> AI Maintained, Human Read-Only.

> Declare what matters, Observe what can be measured, Derive what can be calculated.

> Reconcile continuously.
