# Cookbook Project Graph 分阶段实施计划 V1

## 目标

在不破坏 Cookbook 现有 `.ai-context` 知识体系的前提下，逐步建立：

**Code → Project Graph → AI 索引 / 人类全景图**

最终实现：

* Project Graph 由 AI 自动维护；
* 人类只阅读，不维护任何项目状态文档；
* `07_项目现状.md` 面向人类；
* `功能路径索引.md` 纯 AI 使用，并自动生成；
* Bug / Todo / Plan / Verify 全部关联 Feature；
* AI 修改代码后自动检查 Project Graph 是否同步；
* 所有动态索引均可重新生成；
* Project Graph 可从 Cookbook 中提取为通用方案，用于其他项目。

---

# 总体目标架构

```text
                     真实代码
                        │
                  Runtime Truth
                        │
                        ▼
                  Project Graph
                        │
                   Project Truth
                        │
       ┌────────────────┼────────────────┐
       │                │                │
       ▼                ▼                ▼
   AI_INDEX       功能路径索引       07_项目现状
       │                │                │
  AI状态导航        AI代码导航          人类阅读
       │
       ├── Bug
       ├── Todo
       ├── Plan
       └── Verify
```

其中：

* Project Graph 是唯一动态状态真相；
* Plan / ADR 保存设计原因；
* Code 保存运行事实；
* 所有索引均是可重新生成的 View。

# 第一阶段：Project Graph 基础模型

## 目标

只解决：

> Project Graph 到底是什么、有哪些实体、字段是什么、状态怎么流转。

本阶段**不迁移整个项目状态**，不大规模修改现有文档。

## 建立目录

```text
.ai-context/project_graph/
├── README.md
├── schema.yaml
├── project.yaml
├── features/
└── tools/
```

此时标记：

```text
Project Graph Mode: DRAFT
```

不得成为当前正式真相源。

---

## 定义核心实体

冻结：

```text
Project
Feature
WorkItem
Plan
Verification
Relation
CurrentWork
```

---

## Feature

Feature 是整个 Graph 的第一主键。

例如：

```text
F-MEAL

F-TIMELINE
F-INGREDIENT
F-DISH
F-PANTRY
F-RECOMMEND
F-NUTRITION

```

第一阶段允许根据真实 Cookbook 再调整。

一旦正式启用后：

> Feature ID 原则上永久稳定。

---

## WorkItem

统一表示：

```text
feature
bug
todo
tech-debt
compliance
refactor
research
```

保留 Cookbook 现有：

```text
J*
K*
L*
I*
```

编号。

不得为了 Project Graph 重新给已有事项编号。

没有 ID 的历史 Bug / Todo 才补新 ID。

---

## 状态机

### WorkItem

```text
backlog
ready
in_progress
blocked
review
verifying
done
parked
cancelled
```

### Plan

```text
draft
reviewing

implementing
completed
superseded
```

### Verification

```text
pending
pass
fail
blocked

```

### Feature Lifecycle

```text
planned
active
mature
deprecated
```

```text
developing

```

属于动态 activity，原则上以后由程序计算，不人工维护。


```text

```

---

## 第一阶段验收标准

只有满足以下条件才能进入第二阶段：

1. Schema 足够表达当前 Cookbook。
2. 现有 J/K/L/I 编号可以无损接入。
3. Feature 与 WorkItem 是明确的 N:1 关系。
4. Plan 可以关联一个或多个 WorkItem。
5. Verification 可以关联 WorkItem。
6. Code Path 可以关联 Feature。
7. Schema 不依赖 Cookbook 特有概念。
8. Cookbook 特殊的 CODE/ARCH 双模型协议可作为扩展，而非写死到通用 Schema。
9. Validator 能发现断链和非法状态。
10. 没有修改生产行为。

# 第二阶段：Cookbook 初始 Graph 迁移

## 目标

把 Cookbook 当前真实状态迁入 Project Graph。

这是第一次真正建立：

> Cookbook Project Truth。

---

## 数据来源

## 第二阶段验收标准

1. Graph 能完整表达 Cookbook 当前核心状态。
2. 所有主要 WorkItem 都关联 Feature。
3. 所有仍活跃的重要方案都有 Plan 节点。
4. 真机验证可以反查对应 Feature / WorkItem。
5. `AI_INDEX` 能让一个新 AI 快速定位当前工作。
6. `功能路径索引` 的代码位置与真实代码一致。
7. `07` 与 Graph 一致。
8. Graph render 连续运行两次必须无 diff。
9. 旧文档中的冲突状态得到清理或明确标记为历史信息。
10. 不允许出现 Graph 说完成而生成视图说未开始的情况。

# 第三阶段：AI 自动维护生命周期

## 目标

从：

> AI记得顺便更新文档

升级成：

> AI任务生命周期强制经过 Project Graph。

---

## 标准生命周期

```text
BEGIN
  ↓
RESOLVE
  ↓
CHANGE
  ↓
VERIFY
  ↓
RECONCILE
  ↓
RENDER
  ↓
CHECK
  ↓
FINISH
```

---

## pg begin

负责：

* 定位 Feature；
* 定位已有 WorkItem；
* 必要时创建 WorkItem；
* 设置当前工作；
* 标记开始时间/阶段。

---

## pg reconcile

读取：

```text
git diff --name-only
```

根据 Feature 的：

```yaml
match:
```

判断实际改动影响哪些 Feature。

例如：

```text
StreamingMealParser.kt
```

自动匹配：

```text
F-AI-MEAL
```

如果当前任务却属于：

```text
F-SYNC
```

则报关系异常。

---

## pg verify

统一记录：

```text
测试命令
结果
验证类型
Verification状态
```

自动化测试尽量由工具获得退出码。

不要让 AI仅写：

```text
测试通过
```

---

## pg render

生成：

```text
AI_INDEX
功能路径索引
07_项目现状
Bug索引
Todo索引
Plan索引
Verify汇总
```

---

## pg check

检查：

```text
Schema
Relations
Code Mapping
Current Work
Verification
Generated Views
```

---

## pg finish

只有 `pg check` 通过才允许任务结束。

---

# 第四阶段：Git Guard + 自动一致性保护

## 目标

即使 AI忘记维护 Graph，也不能悄悄提交错误状态。

---

## Local Guard

提交前执行：

```text
pg check --staged
pg render --check
```

检查：

### 代码变了但没有 WorkItem

失败。

### 修改了未映射代码

失败或强警告。

### WorkItem Done 但没有 Verify

失败。

除非：

```text
verification = not_required
reason = ...
```

### Graph修改后生成视图没刷新

失败。

### Feature Code Mapping过期

失败。

---

## Commit规则

建议未来提交信息关联 WorkItem：

```text
feat(K1g): ...
fix(I8): ...
docs(PLAN-AI-xxx): ...
```

Graph 不强制保存每个 commit hash。

Git 本身负责历史。

通过 WorkItem ID 即可关联提交历史。

---

## CI Guard

未来如果仓库已有 CI，再加入：

```text
pg check
pg render --check
```

作为第二道保险。

# 我们双方的协作门禁

每个阶段严格遵循：

```text
我给阶段方案
↓
本地AI只实施这一阶段
↓
本地测试
↓
commit + push
↓
你给我commit hash
↓
我复审
↓
ACCEPT / REWORK
↓
通过后才进入下一阶段
```

禁止本地 AI：

> “第一阶段完成了，所以顺手把第二三阶段也做了。”

每个阶段必须有独立审核点。

---

本地 AI 最终必须输出：

```text
阶段：
基准commit：
完成commit：

新增文件：
修改文件：

实现内容：

测试命令：
测试结果：

未完成项：

```

然后把 commit push。

我根据这个 commit 做远端复审。

# 最终完成标准

Project Graph 完成后，应满足：

```text
任何Bug
→ 知道属于哪个Feature

任何Todo
→ 知道属于哪个Feature

任何Plan
→ 知道解决哪些WorkItem

任何Verify
→ 知道验证哪个WorkItem

任何主要Code
→ 知道属于哪个Feature

任何Feature
→ 知道当前状态、Bug、Todo、Plan、Verify

任何AI
→ 通过AI_INDEX快速进入正确上下文

任何人类
→ 通过07项目现状快速理解整个项目

任何AI修改
→ 无法在Graph失配的情况下静默结束
```

这就是 Cookbook Project Graph 的最终目标。
