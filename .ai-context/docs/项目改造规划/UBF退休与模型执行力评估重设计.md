- **UBF（Universal Blueprint Framework）M0～M3 支线正式退休**，不再派生新批次。已产生的记录保留在 `14_模型执行力评估.md` 作为历史存档，不删除、不覆盖。
- **ARCH 角色即日起由本机 Claude 直接承担**，不再经远程 ChatGPT 网页版复核；`REMOTE_READ_ONLY_ARCH` review mode 停用。
- **模型执行力评估回到 UBF 出现之前已验证有效的做法**：拿真实 Cookbook 蓝图任务当评估载体，走 `blueprint_protocol.md` 现成的 Level/GC 体系，ARCH 用可重复执行的构建/测试命令复核，不再发明平行框架。
- **Phase 3A 的 `GOV-BP-P3-01` 治理升级审计本次不裁决**，留到下一批单独处理，不受本次退休决定影响。

## 1. 为什么退休 UBF（证据）

| 证据 | 数值 |
|---|---|
| 支线跨度 | 2026-08-11（GOV-BP-P3-01 触发）～ 2026-08-15（M3 最后一批） |
| 提交数 | 142 个提交，全部 `docs(governance):` 前缀 |
| 产品代码改动 | **0**（最后一次 `androidApp`/`shared` 改动是 08-08 的 `d7240d6f`，K1i） |
| Universal Level 数量/名称/阈值/映射 | 全程 = **0**（每一批自己的台账都写 "Level/Profile/Selector decisions=0"） |
| H4 假设 | 全程 `H4_INSUFFICIENT_EVIDENCE`，未收敛 |
| Project Graph Phase 3 | 全程 `NOT AUTHORIZED`，即 UBF 声称要服务的目标也没有因此推进 |

**根因不是"方法论选错"，是"验证手段没有落地却被当成已落地在用"**：

1. 全仓（`.ai-context/project_graph` 及其子目录）搜索 `hashlib`/`sha256`/`commitment`/`blind`/`Reveal`，**没有任何脚本或代码**。M3 阶段反复出现的 `Commitment: d653784f...`、`SHA-256 b3d053f2...` 全部是 ARCH 与 CODE 在 Markdown 表格里手写的十六进制文本，从未被程序计算或校验过。"盲测/密码学承诺-揭示"这套机制**没有工具背书**，本质是两个 LLM 互相用密码学词汇给对方的文字背书，可以自洽地无限滚雪球而不触及任何地面真相。
2. 台账内多次出现执行者身份自相矛盾（"Response 自报 model=GPT-5，但 package/ledger 上执行者标的是 GPT-5.6 Luna"），说明**连"这批到底是哪个模型跑的"这个最基础的事实都没能稳定确认**——这本应是评估的第一个前提。
3. 没有停止/收敛规则：每一批结尾都写"下一步交给独立 ARCH 判定"，但没有任何一批设定"N 轮不收敛则终止"的门槛，导致 M1→M2→M3 可以无限派生子协议（Family/Cell/Seal……）。
4. 测试载体脱离真实项目：Family-A/B/C 用的是自造场景（"结构化澄清""父级不匹配 STOP"），不是 Cookbook 真实会遇到的任务类型，测出来的能力画像迁移到真实排期决策上的效度存疑。
5. **讽刺的是**，`Universal-Blueprint-Framework-Architecture-Review.md`（同样出自 ARCH 之手，早于 M0 启动）已经明确诊断过"Level 职责混杂导致文档膨胀"的病灶，M0→M3 却是这个病灶最极端的复发版本。

> 关于你提出的"python 脚本兼容性导致 coder 自由调整、只匹配结果"的猜测：实情可能更直接——**这套协议里从一开始就没有可运行的脚本**，不存在"脚本坏了所以放宽"的过程，而是"从未有脚本，只有文本模拟"。跨环境兼容性问题在本项目是真实存在的（`scripts/build-cli.bat` 要显式钉 JDK 17 就是同类教训），但这次不是它的直接肇因。

## 3. 新的评估循环（替代 UBF）

```text
1. 真实 Cookbook 任务需要 CODE 执行（bug/功能/重构，来自待办或真机验证反馈）
      ↓
2. ARCH（Claude）按 blueprint_protocol.md 现有 Level 体系出蓝图（FULL/LITE + Lk，Lk 取现有基线，不新开级别除非命中 §4 的"开新级"条件）
      ↓
3. CODE（当前 = DeepSeek V4 Flash）独立执行；执行期间不实时纠偏（这条方法论原则是对的，予以保留）
      ↓
4. ARCH 复核：diff 逐文件走查 + 实跑 `scripts/build-cli.bat :shared:testDebugUnitTest` / `:androidApp:assembleDebug` 等可重复命令，不使用无工具支撑的"承诺哈希"
      ↓
5. 结果原样追加进 14_模型执行力评估.md 一行（批次/角色/模型/commit/任务特征/一次交付结果/ARCH简评）
      ↓
6. 达到"≥3批次+复杂度有差异"门槛后才允许下边界结论；结论只能触发 blueprint_protocol.md §4 的复发/扩容/开新级，不建平行框架
```

角色对照（沿用你已认可的"架构闭环 + 独立执行观测"原则，只是把执行方从远程 ChatGPT+虚构测试场景，换回本机 Claude+真实任务）：

|---|---|
| Blueprint Designer / ARCH | Claude（本机） |
| Executor / CODE | DeepSeek V4 Flash |
| Reviewer | Claude（本机，同 ARCH） |

| 评估任务来源 | 仅限真实 Cookbook 蓝图任务，不构造合成协议场景 |

## 4. 三条硬护栏（防止重蹈 UBF）

1. **只用真实交付物做评估载体**。不允许再发明脱离项目的合成测试场景（如 UBF 的 Family-A/B/C）。
2. **任何自称"验证/哈希/完整性"的机制必须有可运行、已提交进仓库的脚本**，且优先走 `project_graph/tools/` 已验证的"零依赖纯标准库"路子（`yaml_lite.py`/`schema_checker.py` 已证明可行，不依赖 PyYAML 之类容易跨环境炸的库）。脚本产出的结果直接写进台账；不接受 LLM 手写的哈希/校验文本作为证据。
3. **止损闸门**：任何"评估/治理"性质的支线，批次数超过 5、或跨度超过 3 天仍未产出可用结论，强制回到 DELIVERY——优先清真机验证积压和已挂起的架构裁决（如 Phase 3A），再决定要不要继续该支线。

## 4.5 自优化闭环（2026-08-17 三次修订，经独立 Opus 挑战后定稿）

第一版（三步）被独立挑战指出核心问题：它只回答"蓝图该怎么改"，没有区分"蓝图有缺口"和"蓝图已闭合但模型在这个细度上就是执行不稳"——真实案例是 K1i 批次改了 allowlist 外文件，按第一版会被错误记成"某条 allowlist 规则复发"，而那条规则本身完好、只是模型没照做。这里定稿为四步，前置一层归因，把"提升颗粒度"和"完善蓝图内容"两条线彻底分开：

```text
每次 ARCH 复核收尾，必须依次完成四件事（缺一不得转 TURN）：

① 逐项归因（AT-10 闸门，判据见 12_多模型协作与实施蓝图规范.md §14.2）
   AF数/返工轮数/越界数 全为 0 → 记「无偏差」+ 模型能力画像表登记正样本，②③跳过，直接④
   否则对每个偏差项填：BP（蓝图侧）/ EXEC（执行侧）/ NON-BP（环境/需求/ARCH自身缺陷）
   EXEC 再分 OMISSION（遗漏枚举项）/ SCOPE（越界改动）/ SURFACE（字面满足但语义未达成）
   + 正交 INTEGRITY 标记（台账自评与实况不符）

② BP 类 → blueprint_protocol.md §4 三分支处置
   复发 → 对应 GC 复发计数 +1（计数达 2 升"自动检查项"，且须 2 批内脚本落地，否则降级）
   扩容 → 现有 Level 追加一条 GC
   开新级 → 走 §2.1 判定式冻结新 Lk

③ EXEC 类 → 14_模型执行力评估.md「模型能力画像」表
   加严阈值：同类偏差第 2 次（INTEGRITY 第 1 次）
   提升最低 Level：仅当同一任务族 SURFACE 型 ≥2 次（AT-07）——
   OMISSION/SCOPE 提 Level 无效，对症对策是外部核验/blueprint_check.py 机械核对
   每条加严项须同时写退出条件；单组合加严项 ≤3 条（AT-08/09 止损）

④ 台账追加一行（格式不变）+ 检查放宽方向门槛
   （同一模型 ≥3 批次+复杂度有差异 且 ≥2 模型都满足才可下"边界结论"；
    达标则按 §4.5 附则执行反哺，未达标只追加台账）
```

**放宽方向反哺**（触及 ④ 门槛时执行，此前设计里唯一保留不变的部分）：在 `14_模型执行力评估.md`「边界结论」章节新增一条具体可判定的结论；若结论具备跨项目复用性（不依赖 Cookbook 具体目录/文件/业务），提交为 `MODEL_ROUTING.md` 候选修订（须标注样本批次数与混杂说明），由用户或旗舰复核后落地，不自动生效；不具复用性的留在项目 experience 分册。

**本节自身的成本上限**（对治"机制本身也会膨胀"——UBF 的原始病灶）：单批执行 ①~④ 若需要新建或改写超过 2 份文档，即视为超出常规复核开销，须先停下走护栏 3 的止损判断，不得默认继续往下做。**认识论边界**：模型能力画像是运营用的保险清单，不是科学结论——小样本观察性数据无法排除"蓝图写得好/差"这类混杂因素，禁止写成"某模型能力边界是 X"这类因果断言，这条红线直接对治 UBF 用不足证据做 H1-H4 假设检验、最终收不了场的失败模式。

**下一个真实 CODE 批次的 ARCH 复核，必须显式执行①②③④四步**，不能像过去几批那样默认跳过归因和反哺——这正是把"自动优化升级"从"文档里写了但没人做"变成"每批强制执行"的关键差别。
