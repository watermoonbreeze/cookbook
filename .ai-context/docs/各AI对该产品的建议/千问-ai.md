## 一、记菜软件与嵌入式 AI 的关联（非常紧密）

你的记菜软件不是"和嵌入式 AI 无关"，而是**嵌入式 AI 恰好能解决记菜软件最核心的几个痛点**。

### 痛点 → 嵌入式 AI 解法

| 记菜软件痛点 | 嵌入式 AI 解法 | 技术实现 |
|------|------|------|
| 家庭主妇**记录饮食太麻烦**，坚持不下来 | 拍照自动识别菜品 → 自动记录营养 | 端侧菜品识别模型（YOLOv8-nano） |
| 不知道**冰箱里还有什么食材** | 智能冰箱摄像头识别食材 → 推荐菜谱 | 端侧目标检测 + 库存管理 |
| **忌口提醒**不够智能，要手动查 | 识别到菜品后自动匹配家庭成员禁忌 | 规则引擎 + 端侧推理 |
| 厨房**网络差/不想联网** | 离线端侧推理，不依赖云端 | RK3588 NPU 本地推理 |
| 家庭**健康数据隐私敏感** | 数据不出家门，端侧处理 | 嵌入式 AI 天然优势 |
| 老人/儿童**不会用手机 App** | 语音交互 + 大屏显示 | 端侧语音识别 + 本地 LLM |
| 不知道**这顿饭营养够不够** | 实时计算 + 可视化反馈 | 端侧计算 + 本地数据库 |

### 为什么"嵌入式"而不是"纯云端"？

| 维度 | 云端 AI | 嵌入式 AI | 记菜场景需要 |
|------|---------|-----------|:---:|
| 隐私 | 数据上传服务器 | 数据留在本地 | ✅ 家庭健康数据极敏感 |
| 延迟 | 200-500ms | 30-80ms | ✅ 实时反馈体验 |
| 离线 | ❌ 不可用 | ✅ 完全可用 | ✅ 厨房WiFi差 |
| 成本 | 按调用付费 | 一次性硬件成本 | ✅ 家庭用户不想月付 |
| 适老化 | 需要手机 | 语音+大屏 | ✅ 老人友好 |

> 💡 **核心洞察：你学嵌入式 AI 不是"转行"，而是给记菜软件构建技术壁垒。** 纯 App 谁都能做，但"App + 端侧 AI 硬件"的组合是有门槛的。

## 二、健康饮食推荐的算法/模型现状

### 坦诚说：目前没有一个"开箱即用"的成熟模型

这个领域是**多技术组合**，不是单一模型能解决的。但好消息是：各个组件已经有成熟方案，你需要做的是**把它们组装起来**。

### 现有可用技术组件

| 组件 | 成熟度 | 具体方案 | 你能怎么用 |
|------|:---:|------|------|
| **食物识别** | ⭐⭐⭐⭐⭐ | YOLOv8 / Food-101 / 中国菜品数据集 | 拍照识别菜品 |
| **营养数据库** | ⭐⭐⭐⭐⭐ | 中国食物成分表（第6版）、USDA FoodData Central | 食材营养查询 |
| **膳食指南规则** | ⭐⭐⭐⭐⭐ | 中国居民膳食指南2022、DRIs | 推荐/忌口规则引擎 |
| **知识图谱** | ⭐⭐⭐⭐ | Neo4j / 自研 | 食材-营养素-疾病-禁忌关联 |
| **推荐算法** | ⭐⭐⭐⭐ | 协同过滤 + 约束满足 + 多目标优化 | 菜谱推荐 |
| **LLM + RAG** | ⭐⭐⭐ | GPT/通义千问 + 营养学知识库 | 自然语言问答 |
| **个性化模型** | ⭐⭐ | 基于用户历史+体检数据微调 | 长期方向 |
| **血糖预测** | ⭐⭐⭐ | CGM数据 + 时序模型 | 糖尿病人群 |

## 三、在职 → 创业过渡规划

### 核心原则：**不要跳崖，要搭桥**

```
在职状态                                         全职创业
────────────────────────────────────────────────────────────→
│  搭桥期（12-24个月）                            │
│  ┌─────────────────────────────────────────┐   │
│  │ 晚上/周末做产品                          │   │
│  │ 验证需求 → 积累用户 → 产生收入          │   │
│  │ 收入覆盖生活费 → 辞职                    │   │
│  └─────────────────────────────────────────┘   │
```

### 分阶段过渡计划

| 阶段 | 时间 | 状态 | 核心任务 | 收入来源 |
|------|------|------|------|------|
| **Phase A** | 现在~M6 | 在职 | 记菜 MVP + 嵌入式 AI 学习 | 工资 |
| **Phase B** | M7~M12 | 在职 | 记菜上线 + 种子用户 + 反馈迭代 | 工资 + 微量用户收入 |
| **Phase C** | M13~M18 | 在职 | 验证商业模式 + 嵌入式 AI 原型 | 工资 + 订阅收入增长 |
| **Phase D** | M19~M24 | 评估 | 收入达到工资 60%+ → 准备离职 | 产品收入 |
| **Phase E** | M24+ | 全职创业 | 全力投入 | 产品收入 + 融资（可选） |

### 每个阶段的具体行动

#### Phase A（现在~M6）：打地基

**记菜软件：**
- 完成 MVP 核心功能
- 找 10-20 个家庭主妇做用户测试
- 建立食材营养数据库（至少覆盖 500 种常见食材）
- 实现基础的忌口规则引擎（糖尿病、高血压、孕妇）

**嵌入式 AI 学习：**
- 按之前的 12 个月计划执行
- Phase 1-2 的 C++ / ONNX / 模型部署

**关键指标：**
- [ ] 记菜 App 有 20+ 活跃用户
- [ ] 收到 50+ 条真实反馈
- [ ] 明确最核心的 3 个功能需求

#### Phase B（M7~M12）：验证需求

**记菜软件：**
- 根据反馈迭代 2-3 个版本
- 加入拍照识别（调用云端 API 先验证需求）
- 建立用户社群（微信群/小红书）
- 开始内容营销（营养科普 + 产品植入）

**嵌入式 AI：**
- 完成 Phase 2（模型部署到 RK3588）
- 做一个"厨房小屏"原型（树莓派/RK3588 + 摄像头 + 小屏幕）
- 验证端侧菜品识别的准确率

**关键指标：**
- [ ] 100+ 注册用户，30+ 周活跃
- [ ] 用户 NPS > 40
- [ ] 有人愿意付费（哪怕 ¥9.9/月）

#### Phase C（M13~M18）：验证商业模式

**记菜软件：**
- 推出付费功能（高级营养分析 / 家庭多人管理 / AI 菜谱推荐）
- 测试定价：¥9.9/月 或 ¥99/年
- 探索 B 端：社区健康管理 / 月子中心 / 养老机构

**嵌入式 AI：**
- 完成 Phase 3（系统集成）
- 做出"智能厨房终端"工程样机
- 申请 1-2 个实用新型专利

**关键指标：**
- [ ] 付费转化率 > 5%
- [ ] 月收入 > ¥2000
- [ ] 硬件原型可演示

#### Phase D（M19~M24）：决策点

**评估是否离职的标准：**

| 条件 | 达标线 | 你的情况 |
|------|--------|---------|
| 产品月收入 | ≥ 工资的 60% | ? |
| 用户增长趋势 | 月环比 > 10% | ? |
| 存款 | ≥ 12 个月生活费 | ? |
| 技术壁垒 | 有 1-2 个别人短期做不出的功能 | ? |
| 身心状态 | 在职已严重影响产品迭代速度 | ? |

> ⚠️ **如果以上 5 条满足 3 条以上，可以考虑离职。否则继续在职。**

#### Phase E（M24+）：全职创业

- 全力迭代产品
- 考虑是否需要融资（硬件需要资金）
- 或者走"独立开发者"路线，不融资，靠订阅收入

## 一、核心判断：先软件，后硬件，但不是二选一

**不是"纯软件还是软硬件"的选择题，而是"什么时候加硬件、加什么硬件"的节奏题。**

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   时间轴                                                        │
│   ─────────────────────────────────────────────────────────→    │
│                                                                 │
│   M0-M12          M13-M18          M19-M24          M24+       │
│   ┌──────┐       ┌──────┐        ┌──────┐        ┌──────┐    │
│   │纯软件│──→──→│软件+ │──→──→│软件+ │──→──→│生态  │    │
│   │ App  │       │轻量硬件│       │专用硬件│       │矩阵  │    │
│   └──────┘       └──────┘        └──────┘        └──────┘    │
│                                                                 │
│   验证需求       验证付费意愿     验证硬件需求    规模化        │
│   零成本启动     ¥500以内/台     ¥1000-2000/台   融资或利润    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**为什么不能一上来就做硬件：**
- 你在职，精力有限，硬件开发周期长（3-6个月）
- 硬件一旦开模，库存就是沉没成本
- 用户需求还没验证，硬件方向可能选错
- 软件可以快速迭代试错，硬件不行

**为什么最终一定要做硬件：**
- 2026年智能厨房行业已经从"单品智能"走向"场景智能"（海尔、方太都在做）
- 京东×香山刚推出AI营养秤，28小时卖1300台——**市场验证了"厨房+营养+AI"的需求**
- 纯App没有壁垒，谁都能抄；硬件+数据+算法的组合才是护城河
- 家庭主妇/老人对"放在厨房里的设备"接受度远高于"打开手机App"

## 二、产品形态演进路线（4个阶段）

### Stage 1：纯软件 App（M0-M12）

| 维度 | 内容 |
|------|------|
| 产品 | 记菜 App（iOS/Android） |
| 核心功能 | 饮食记录 → 营养分析 → 忌口提醒 → 菜谱推荐 |
| AI能力 | 调用云端API做菜品识别（百度/阿里视觉API） |
| 成本 | ¥0（开发时间成本） |
| 目标 | 验证核心需求，积累100+种子用户 |
| 推出方式 | 微信小程序（零安装门槛）+ App |

**为什么先做微信小程序而不是App：**
- 家庭主妇不会主动下载新App
- 小程序分享到家庭群，传播成本为零
- 开发周期短（2-3个月 vs App 4-6个月）
- 后续可以平滑迁移到App

**Stage 1 关键动作：**
```
M1-M3:  微信小程序 MVP（记录+营养查询+忌口规则）

M7-M9:  加入家庭多人管理（爸爸高血压、奶奶糖尿病）
M10-M12: 加入AI菜谱推荐（基于约束满足算法）
```

## 五、载体 4：可穿戴设备对接（数据级）

### 不自研！对接现有设备

| 设备类型 | 对接方式 | 获取数据 | 用途 |
|------|------|------|------|
| 血糖仪（CGM） | 蓝牙/API | 实时血糖 | 糖尿病饮食动态调整 |
| 血压计 | 蓝牙 | 血压值 | 高血压忌口阈值动态调整 |
| 运动手环 | API | 步数/消耗 | 能量摄入推荐调整 |
| 体脂秤 | 蓝牙/API | 体重/体脂 | 长期趋势追踪 |

### 对接策略

```
不做硬件，做"连接器"：

1. 接入主流品牌的开放API
   - 华为运动健康、小米健康、苹果HealthKit
   - 鱼跃、欧姆龙血压计SDK
   - 雅培瞬感/德康CGM API

2. 你的价值：
   把分散的健康数据 → 统一汇入记菜系统
   → 驱动个性化饮食推荐

3. 用户体验：
   "爸今天血压145/95，比昨天高了"
   → 自动调整今日推荐：低钠菜谱优先
   → 忌口阈值收紧：钠 < 4g/天（平时6g）
```

## 十、一句话总结

> **记菜的硬件载体不是一步到位的"完美产品"，而是分四层逐步搭建的"积木塔"：秤是底座（验证付费），屏是主体（建立壁垒），摄像头是延伸（扩展场景），可穿戴是对接（数据闭环）。每一层都在上一层验证成功后才搭建，永远不在地基不稳的时候盖楼顶。** 你的嵌入式AI学习就是在造"搭积木的手"——每学会一项技能，就多一块能稳稳放上去的积木。
