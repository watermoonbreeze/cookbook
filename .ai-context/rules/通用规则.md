# 双模式通用规则（Claude Code 与 Codex 均强制遵守）

> 更新时间：2026-07-03。[AI生成] 由 AGENTS.md / CLAUDE.md 中的等价规则统一抽取，此文件为唯一来源；入口文件只做引用。

## 一、语言与沟通

- **必须使用中文**与用户对话；代码注释跟随项目语言（中文）。

## 二、任务编排强制门禁

- 只要用户下达的是一个**任务**（开发、修复、优化、调研、文档、配置、审核等），执行前必须先走自动任务编排的**阶段0评估定级**（微任务/轻量/标准/深度），并**先告知用户**本次采用的模式/级别、原因、是否分派智能体，不得未声明就自行处理。
- 流程定义按各自全局配置读取：Claude 读 `~/.claude/workflow_auto_orchestration.md`，Codex 读 `~/.codex/memories/workflow_auto_orchestration.md`。
- 标准/深度任务按流程分派 DEV 角色智能体参与，不得由主线程默默跳过分派。
- 用户可用关键词覆盖级别（"改个xxx"=微任务，"快速改下"=轻量，"仔细看下"=深度）；无人值守关键词（"无人值守""自动执行""我先走了"）激活无人值守模式。

## 三、上下文保护机制

- 会执行命令、修改文件或产生项目决策的任务：阶段0声明之后、实质操作之前，先写**任务前上下文快照**到 `.ai-context/docs/context_memory/`（记录：需求、模式/级别、计划角色、已知状态、预计涉及文件、风险、待验证项）。
- 纯问答且不改文件不产生决策时可不写快照，但需说明原因。
- 长对话中每完成一个重要节点，把阶段性结论保存到 `.ai-context/docs/context_memory/`。
- 文件按主题/任务命名（`YYYY-MM-DD_主题.md`），只存结论、决策、待办、关键路径；单文件 ≤100 行，超过按子主题拆分；读取按需加载；新任务涉及相关主题时顺带清理过时内容。
- 本目录为双端共写共读；无需再向 `.claude/docs/` 或 `.codex/docs/` 另存副本。

## 四、工程一致性

- 开发前按需读取 `.ai-context/docs/experience/09_工程统一规范.md`（KMP 分层、Android/iOS UI、数据库、代码风格、日志规范）。
- Android UI 采用 Material Design 3 与既有 Theme/ExtendedColors；iOS UI 采用 SwiftUI 原生风格。
- 新增跨平台业务能力优先进 `:shared`；平台模块只承接 UI 与平台适配。
- 修改数据库、主题、架构边界或公共组件时，同步更新 `.ai-context/docs/feature/` 对应文档。

## 五、单元测试

- 单元测试是基础开发流程的一环：功能完成后必须补充/更新对应单元测试并运行相关任务，不能只依赖编译通过。
- 暂无法单元测试的功能，必须说明原因、记录剩余风险，并至少用 Repository/UseCase 层测试覆盖核心业务规则。
- shared 测试位于 `shared/src/androidUnitTest/`，运行命令：`./gradlew :shared:testDebugUnitTest`。

## 六、AI 代码注释规范

- AI 生成/修改的代码必须加中文注释并标 AI 标识：新建文件用类注释模板（`@Author : {作者}-AI`、`[AI生成]` 原因），修改已有文件在类注释末尾追加 `[AI修改]`，具体改动行加 `// [AI生成]` / `// [AI修改]`。
- 注释只解释复杂业务决策或平台限制，不复述代码含义。

## 七、临时目录

- Claude Code 临时文件放 `temp/claude/`；Codex 临时文件放 `temp/codex/`。除用户明确要求外不得散落到其他位置。

## 八、构建与环境（2026-07-03 实测更新）

- **标准构建路径是命令行脚本**（用户当前 AS Hedgehog 打开本项目会报 `Module entity with name: cookbook should be available`，IDE 不作为构建路径）：
  - Windows：`scripts\build-cli.bat :androidApp:assembleDebug`、`scripts\build-cli.bat :shared:testDebugUnitTest`
  - macOS/Linux：`./scripts/build-cli.sh <任务>`
- 脚本原理：AGP 8.2.2 要求 Gradle daemon 跑在 **JDK 17**；脚本显式设置 `JAVA_HOME` 后调用 gradlew，不依赖全局 `~/.gradle/gradle.properties`（该文件当前也配置了 `org.gradle.java.home=jdk-17`，直接 `./gradlew` 同样可用，但以脚本为准防漂移）。换机时改脚本顶部 `CLI_JDK_HOME` 即可。
- 每次功能改动完成后必须用上述命令做编译+单元测试验证；本机已实测两者均可用（Gradle 8.2 + JDK 17）。
- 不得擅自升级 Gradle/AGP/Kotlin 版本来"适配环境"。

## 九、公共目录维护

- 公共规范/文档/记忆只维护 `.ai-context/` 一份，见 `.ai-context/README.md` 的分工原则与维护规则。
- **项目全景图为全局任务首读入口**：本项目唯一入口是 `.ai-context/docs/projectReview/00_导读与索引.md`。凡涉及整体架构、产品方向、主流程、界面/路由、算法真相源、数据与资料来源、AI/网络策略或公共复用能力，先读该册并按阅读路径下钻，不得只依据局部代码判断全局。新增、删除或实质改变这些内容时，同任务更新受影响分册、`05_诊断地图.md` 与 `.ai-context/docs/功能路径索引.md`。

## 十、无人值守模式特有决策（2026-07-16 用户追加）

- **核心决策原则——不确定则"多角色相互验证得最优方案再执行"**（用户 2026-07-16 定，无人值守时不停下等拍板）：方案有不确定点时，不靠单一视角拍脑袋、也不停下问用户，而是 **spawn 多个身份角色 agent（如系统分析/架构/UX/安全/资深工程师/领域专家）从不同角度相互验证、讨论、挑刺**，收敛出**最优方案**后按其执行；只要**不违背大逻辑前提**（北极星/架构/数据模型/免责红线等），过程中发现更优设计也可自主改用。角色分歧由主线程据各方论据裁决。**最终方案与状态落地成文档**给用户回看（"先做一版看效果"，做出来再迭代优于空谈）。
- **每完成一项走完整仪式**：审核验证测试 → 保存上下文快照 → 总结经验 → 飞书通知用户 → 下一项（不攒批）。
- **非界面类功能（算法/数据类）的落地文档必须写清"操作逻辑 + 用户验证方法"**（用户 2026-07-16 定）：界面功能用户能直接看到效果，但算法（如推荐打分、评级）/数据（如营养来源、口径）类改动用户"看不见内部逻辑"，故落地文档除方案外**必须列**：①**具体操作逻辑**——算法怎么算（公式/阈值/因子/权重/分层）、数据从哪来（来源/口径/覆盖率/回填规则）、何时生效（gate/默认/开关）；②**用户验证方法**——用户在真机/数据上**怎么判断它对不对**，列出可操作的验证步骤 + 判断标准（如"选X风格后，含Y主料的菜应排在Z之后"、"adb pull 库跑某 SQL 应得某结果"、"某来源可回查某权威页"）。让用户能自行验证，而非只看"已完成"。
- 双门禁与红线不因无人值守放宽：UI 先 Apple-UX 设计门禁、每批编码后 Google 代码审查门禁（阻断必修）；健康数据守免责红线；高风险/禁止操作仍入待确认队列不擅自执行。
